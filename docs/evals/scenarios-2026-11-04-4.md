## misroute-mcp

- Fault: `misroute`
- Expected root cause: shop-proxy forwards to shop-web:8001, where nothing listens (shop-web listens on 8000), so every request through the proxy gets a 502 while shop-web itself is healthy.
- Expected category `config`, plan `mcp.call shop-proxy (caddy_reload) with {"container": "shop-proxy"}`, never `docker.restart`, `docker.start`, `docker.stop`

- Run 1 diagnosis: The shop is unavailable because the running Caddy proxy configuration was loaded with the wrong upstream port, forwarding to shop-web:8001 while the healthy web service listens on port 8000. The on-disk configuration points to port 8000, but the live configuration remained misrouted.
  - Judge: names the live config forwarding to shop-web:8001 while shop-web listens on 8000, the file on disk right, giving 502s
- Run 2 diagnosis: The running Caddy configuration in shop-proxy was dynamically loaded with its upstream set to shop-web:8001, while shop-web listens on port 8000. Requests were therefore refused by the upstream and returned as 502s.
  - Judge: names the live upstream shop-web:8001 against shop-web on 8000, giving 502s
- Run 3 diagnosis: The live Caddy configuration for shop-proxy routes requests to shop-web on port 8001, but the web application listens on port 8000. This incorrect upstream port causes connection refusals and 502 responses; the on-disk Caddyfile uses the correct port, so the mismatch is in the loaded configuration.
  - Judge: names the live config's port 8001 against shop-web on 8000, the file on disk right, giving 502s

## What it shows

- The root cause passed in 3 of 3 runs, and the category was right in 3 of 3.
- The plan was exactly the expected one in 3 of 3 runs; 0 proposed an unnecessary action.
- The largest single prompt was 8,687 tokens (misroute-mcp, run 2).
- 0 structured-output fallbacks in 0 runs: model calls that gave no structured output through tools, so Bleep asked for JSON instead.
- Read by hand: all three runs cite `mcp_call` as evidence for the loaded config (`shop-web:8001`) against the Caddyfile on disk (`shop-web:8000`), so Investigate called the new `caddy_config` read tool each time (6, 7 and 8 tool calls). Each diagnosis says the fault is live-only, two of them adding that the logs show a config loaded from `Caddyfile.misroute`. Each proposal is one `mcp.call` of `caddy_reload` on shop-proxy with `{"container": "shop-proxy", "config": "/etc/caddy/Caddyfile"}`, its reason saying the file on disk already points at port 8000. No restart, no `caddy_purge_cache`, no malformed step.
- Compared with [the round without the read tool](scenarios-2026-11-04-2.md) (same model, scenario and 3 runs): the root cause stayed 3 of 3, and the exact plan went from 0 of 3 to 3 of 3. Only the fixture changed (#166), so the missing evidence, not the model or Propose's prompt, kept it from proposing the reload. It cost one to three more steps per run (7.0 against 5.3 on average) and $0.0095 against $0.0101 for the batch.
