# Scenario evals, 2026-11-03 (2): bad-deploy with the GitHub tools

> **Answer:** Yes. With the GitHub tools reading the shop's repo, `openai/gpt-6-luna` tied bad-deploy's 500s to the deploy. The repo is a fixture: the deploy of shop 2, and the commit before it that reads `price_cents` in `/api/items` and adds its migration. On the final code, the root cause passed in **3 of 3** runs, scoring 0.85 to 1.00. Every run cited the commits for version 2 and its migration, and 2 of 3 said in the root cause that the migration was not applied. In the [baseline](scenarios-2026-11-03.md#bad-deploy), where the logs were the only evidence, it scored 0.80 to 0.85 and named neither in any run. A first round before the review fixes gave the same result: 3 of 3, 0.95 to 1.00, all naming both. The plan was exact (no action) in all 9 runs. The category is still wrong: `code` in 0 of 6 runs (1 of 3 in the baseline), `config` or `dependency` instead. That is the undefined taxonomy #108 is about, not the evidence.

## Question

Can Bleep tie bad-deploy's 500s to the deploy when it reads the service's recent commits and diffs (#37)? The logs alone never let it.

## What it shows

- **The commits gave the diagnosis its missing half.** The logs show only the missing column. Version 2 and the migration that adds `price_cents` are only in the fixture: the compose diff sets `SHOP_VERSION` to 2, and the commit before it adds `0002_price_cents.sql`. Every one of the 6 runs used them, against 0 of 3 in the baseline. 5 of 6 put both in the root cause (Round 2 run 2 says "the shop-web app version now queries", not "version 2"); Round 2's run 1 left the unapplied migration in its evidence and scored 0.85, the baseline's best.
- **The model flagged honest commits as planted.** These commits hold no orders, yet the diagnosis's `planted_in` named `commits` in 3 of 6 runs (Round 1 run 2, Round 2 runs 1 and 2), alongside `logs` twice. The flag is hidden from the human since #112, but it means the model's `commits` flag in the [commit injection runs](injection-commits-2026-11-03.md) is weak evidence (#105).
- **Round 2 names its sources better.** In Round 1, two runs credited the commit facts to `gather`, which reads no commits. In Round 2 all three named `commits` or a GitHub tool. The scenario data does not record each run's tool calls, so this reading comes from the diagnoses. The injection rounds do record them, and there every run called both GitHub tools ([injection, commits](injection-commits-2026-11-03.md)).
- **It costs no more.** With the GitHub calls in place of some Docker reads, runs used 7 to 8 tool calls and 40,000 to 53,000 tokens, against 5.3 calls and 60,051 tokens in the baseline. The largest prompt was 9,000 to 12,000 tokens, against 19,830, because a commit list and a short diff are small beside a 200-line log.
- **The category did not improve.** It came out `config` (the deployment setting) three times and `dependency` (a schema the app depends on) three times. Each is a defensible reading of an undefined word; #108 defines the categories.

## Limits

- **Not like for like with the baseline.** The baseline ran on a shop that was never reset; these rounds recreated it before every run (#104). The prompts also changed in between (#35, #112), and #37 adds a mention of the commits in Investigate and the `commits` planted source in Diagnose.
- **A fixture, not the repo's history.** The commits were written for the scenario and served by `evals.github`; nothing reached github.com. They say what changed, never that the migration did not run: that link is the model's.
- **3 runs a round.** That shows the version and the migration named, not a rate.
