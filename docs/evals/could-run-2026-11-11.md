## Why this round

#365 changes Propose's prompt and its structured output, so a lean round covers the case that asked for it (the Coolify spike, where Bleep closed an incident whose fix its enabled actions could have run) and one that must not change (a fix only a Compose-file edit makes, with the same actions enabled).

"Could run right" is what #365 measures; "Said it right" is the look scorer's diagnosis check (a failing case needs a category other than `unknown` and one of the case's words).

- **Coolify env var:** runs 1 and 3 name `TESTAPP_FAIL_AFTER_S=180` as the cause, category `config`, plan no action with `could_run: [coolify.set_env, coolify.redeploy]`; both say the safe value is unknown and ask the person for it, which is what the waiting incident lets them answer. Run 2 also saw the URL's 404 (Traefik stops routing to an unhealthy container), could not tie it to the setting, chose `unknown` and named no actions, so that incident would have closed as before #365.
- **Compose edit:** all three runs name `DATABASE_URL`'s host `db` that shop-web cannot resolve, plan no action with an empty `could_run`, and ask the person to check shop-web's database host or its network. All three chose `unknown`, hedging between a wrong host name and a missing network alias, so the scorer fails them; the closing behaviour #365 must keep held in 3 of 3.

## Limits

- Three runs a case, one model, no baseline: the cases are new with this change.
- The cases run on a scripted host without the Coolify plugin, and a look opens them, not the watcher; Propose's prompt is the same either way ([evals design](../design/evals.md)).
- Diagnose's `unknown` on the Compose case is Diagnose's own choice, not part of #365; it also makes Propose less likely to fill `could_run`, as run 2 of the Coolify case shows.
