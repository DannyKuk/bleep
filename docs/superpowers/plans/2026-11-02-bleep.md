# Bleep Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Bleep, an on-call agent for Docker hosts that detects incidents, diagnoses them with evidence, asks before acting, executes approved actions, verifies, reports and remembers.

**Architecture:** A FastAPI backend runs one watcher per host. The watcher reads Docker events, polls containers, checks URLs and probes the host. Its signals feed a detector that opens one incident per service or host. Each incident is a LangGraph thread checkpointed in SQLite: gather → investigate → diagnose → propose → approval (interrupt) → execute → verify → report. Approvals come from Telegram or the Next.js dashboard, whichever answers first, and the dashboard streams every node and tool call over SSE. Act tools run only with an HMAC approval grant over the hashed plan, and the guard keeps log, web and commit content labelled as untrusted data.

**Tech Stack:** Python 3.14 + uv, FastAPI, LangGraph + LangChain (`langchain-openrouter`, `langchain-openai` for local OpenAI-compatible servers), `langgraph-checkpoint-sqlite`, `docker` SDK, `asyncssh`, `httpx`, `sse-starlette`, `fastembed`, numpy, DeepEval (evals only), Langfuse. Next.js 16 + Tailwind 4 + shadcn/ui, Vitest. Docker Compose. SQLite.

**Spec:** `docs/superpowers/specs/2026-11-02-bleep-design.md` (section numbers below as §x.y). Quality bar and conventions: `~/Desktop/molecula` (layout, prompts as files, tests never touch the network, decision docs, dated eval reports) and `~/Desktop/ai-interview` (dev panel, jailbreak tests, benchmarks).

## Global Constraints

- Hosts are reached over SSH with a key; nothing is installed on the hosts. Danny's two servers run Coolify; the demo stack is plain Compose. Both must work. (§3)
- The agent itself runs in Docker (Compose). (§3)
- Models through OpenRouter by default, with a local option (Ollama or LM Studio). Must degrade gracefully on a weaker local model. (§3)
- No paid services required to run or demo it. Telegram bot and OpenRouter key are the only external accounts needed; Coolify and others are optional plugins. (§3)
- Stack: Python 3.14 + uv, FastAPI, LangGraph + LangChain, Next.js 16 + Tailwind + shadcn/ui, Docker Compose, SQLite for state and memory. (§3)
- Standalone portfolio project: the repo talks about Bleep and its users only. (§3)
- The agent changes nothing on a host without an explicit yes; every write is gated in v1; never auto-approve. (§2, §4.4)
- No generic shell with write access, ever. Act tools refuse to run without an approval grant for the approved plan. (§4.5, §4.6)
- Secrets (SSH keys, Telegram token, Coolify/GitHub tokens, model API keys) never live in the database and never reach the model. (§4.6, §4.10)
- Never claim "fixed" without verification: service healthy again and URL answering. (§2)
- Reports say what happened; they never paste raw logs. (§2)
- Every prompt is a `.md` file under `backend/src/bleep/prompts/`, loaded through `prompts.load(name, **vars)`; tool docstrings are the only LLM-facing text in Python (molecula rule).
- Tests never touch the network or a real Docker engine: fakes for engines, SSH, LLMs and HTTP (`httpx.MockTransport`), recorded fixtures for GitHub/Coolify/Telegram. Real-model and real-engine checks live in `backend/evals/` and in docs/spikes.
- One task = one GitHub issue = one branch = one PR. A PR that makes or changes a decision updates `docs/` in the same PR: big questions with evidence get `docs/decisions/<topic>.md` (Answer, Question, What we tried, Result, What it shows, Limits, Reproduce); measured numbers go to dated `docs/evals/<topic>-YYYY-MM-DD.md`.
- Docs follow the Documentation standard below: a PR that builds or changes something updates `docs/` in the same PR.
- Commit messages: one plain sentence saying what changed and why, ending with the issue number. No `Co-Authored-By` or other AI attribution lines in commits, PRs or issues.

## Review Focus

1. **Bleep crashes or restarts mid-Execute.** The resumed run must not restart a container twice: every step is written to `action_log` as `started` before the call and `done` after it, and a resumed Execute skips `done` steps and re-validates `started` ones instead of repeating them. Test in Task 28.
2. **The SSH host is macOS (the spare M1).** There is no `/proc` and no `free`, and the non-interactive `PATH` lacks `docker`. Host basics must parse Darwin output (`vm_stat`, `sysctl`), and Docker must work through the forwarded socket. Test in Task 7.
3. **A host goes unreachable or its event stream drops.** The watcher reconnects with backoff and marks the host unreachable, and after 5 min it opens one host incident. Service URL failures on that host attach to the host incident instead of opening one incident per service. Test in Task 15.
4. **Bleep watches the machine it runs on.** Its own containers (`bleep.self=true`) never open incidents and are never targets of act tools, even if a proposal names them. Tests in Task 5 and Task 19.
5. **Huge or hostile tool output.** Multi-megabyte logs, ANSI and binary bytes, tokens in log lines, and a log line that closes the untrusted wrapper tag must all be handled: output is capped at 8,000 chars, control bytes are stripped, secrets are redacted, and the wrapper tags are escaped. Tests in Task 6 and Task 17.
