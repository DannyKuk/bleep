# Plugins

How Bleep takes on tools that share one connection, such as a Coolify instance (`backend/src/bleep/plugins/`, `api/plugins.py`). A plugin is switched on and off as a whole from the dashboard; its settings are stored with the other settings ([settings](settings.md)), its secrets never are (spec §4.8, §4.10).

| Piece | Path | What it does |
|---|---|---|
| **Plugin** | `plugins/base.py` | The base class: `name`, `title`, `settings_model` (non-secret), `secrets` and `optional_secrets` (environment variable names), `tools(ctx)`, `act_handlers(ctx)` and `async health(ctx)`, each given a `PluginContext`. |
| **Registry** | `plugins/registry.py` | Which plugins are switched on, with what settings; their tools, act handlers and actions, read at every use; the view the API shows. |
| **Routes** | `api/plugins.py` | `GET /api/plugins` and `PUT /api/plugins/{name}` (`{enabled, settings}`, either part optional). |
| **MCP server by URL** | `plugins/mcp_url.py` | One MCP server over Streamable HTTP at `MCP_URL`, through `langchain-mcp-adapters`: the read tools `mcp_tools` and `mcp_call` for the server tools allowed as read, and the act action `mcp.call` for those allowed as act. |
| **List** | `wiring.py` (`PLUGINS`) | Every plugin Bleep has. |

## Choices

- **A plugin's methods take one `PluginContext`: its settings, its secrets by env name, `BLEEP_SECRET` and the guard log.** The plan had `tools(settings, secrets)` and `act_handlers()`. Reason: an act handler checks approval grants exactly as the Docker act tools do, so it needs the key the grants are signed with; one context keeps the three methods alike (#36).
- **A secret is the name of an environment variable, read when the plugin is switched on.** `GET /api/plugins` shows each one as `{env, set, required}`, never its value (`required` is false for an `optional_secrets` entry, handed over only when set, #43); the plugin's tools get it as a `SecretStr`, whose repr hides it. Reason: secrets never live in the database or reach the API or the model (§4.10) (#36).
- **A plugin's settings model must forbid unknown fields and may not have a field named like a secret** (`token`, `api_key`, `Password`; the [settings](settings.md) check), or the registry refuses the plugin when Bleep starts. Reason: settings are stored and shown, so a plugin author cannot put a token there by mistake (#36).
- **Every plugin is off until a person switches it on, and switching on needs valid settings and every secret set**; the refusal names the missing variable. Reason: a half-configured plugin would offer tools that fail on every call (#36).
- **The plugin's tools, act handlers and actions are read from the registry every time they are used.** `ToolRegistry` reads the switched-on plugins' tools on every read, `SettingsStore.enabled_actions` adds their actions to the core Docker ones, and Execute's act tools are a live view over the core ones and the plugins'. Reason: switching a plugin off takes its tools out of the next Investigate round, makes its actions fail the plan check as `disabled_action`, and leaves Execute without a handler even for a plan approved while it was on (#36).
- **A plugin's name is lower-case letters and digits and never `docker`; its tool names start with `<name>_` and its actions with `<name>.`, and each action must be one Bleep knows (`schemas.graph.Action`).** A core tool keeps its name over a plugin's, and a core action its handler. Reason: a plugin can neither shadow a core tool nor add a Docker action that would skip the Docker act tools' checks, and with no `_` in a name one plugin's prefix is never inside another's (#36).
- **A plugin whose own code fails while it is switched on is refused with its error's type only** ("plugin coolify could not be switched on (RuntimeError)"), as a 422 from the API and a warning on boot. Reason: the error's text could quote a setting or a secret, and a plugin that broke in a new version must not stop Bleep from starting (#36).
- **A plugin whose secret is unset at boot starts off, and its stored toggle stays on, also through a change of its settings alone.** Reason: Bleep must start without it, and the plugin is on again once the variable is back, without a person switching it again (#36).
- **A change that cannot be saved puts the plugin back exactly as it was.** Settings and the toggle are applied in memory only after they validate and the plugin builds, then stored; a failed write restores the snapshot. Reason: the dashboard must never show a plugin as off while its tools are still offered, or the other way round (#36).
- **The health check is bounded to 5 s, and its text is redacted and has the plugin's own secret values replaced.** A check that raises or times out reads "the health check failed" or "timed out". Only the secret as it is gets replaced; a plugin must not put a transformed secret in its health text. Reason: a slow or broken plugin must not hang or break the plugins page, and a health message that quotes the token it used must not show it (#36).
- **`plugins` builds on `tools`' types (`ToolSpec`, `ActHandler`) and `guard`'s known actions; `tools` reads the plugins only through the `ToolSource` protocol and never imports them.** Reason: a plugin hands Bleep tool specs and act handlers, so it needs their shapes, while the dependency still points one way (#36).

## MCP server by URL

The plugin `mcp` connects one MCP server. Where it is and how Bleep logs in come from the environment: `MCP_URL` (the Streamable HTTP endpoint, required) and `MCP_TOKEN` (a bearer token, used when set). Its stored settings only say which of the server's tools Bleep may run: `read_tools` (run by the model with `mcp_call`, no approval) and `act_tools` (only as an approved `mcp.call` step). Built on `langchain-mcp-adapters` 0.3.2 (`MultiServerMCPClient.session`, `load_mcp_tools`) and `mcp` 1.30.0, read from their installed source. Tests run the `mcp` package's own `FastMCP` server in-process, reached through an `httpx.ASGITransport`, so no socket is opened.

**Example: Coolify's own MCP server.** Coolify serves MCP at `https://<your-coolify-domain>/mcp` over Streamable HTTP. It must be enabled under **Settings > Advanced > API and MCP > MCP server** and for the token's team, and the API token goes in as a bearer token ([Coolify: Set up MCP](https://coolify.io/docs/mcp/setup)). A token with only the `read` permission ("Inventory and inspection") makes it read-only; `deploy` and `write` add lifecycle and change tools. So: create a `read` token, set `MCP_URL=https://coolify.example.com/mcp` and `MCP_TOKEN=<the token>` in `.env`, restart the backend, and switch the plugin on with the tools to allow in `read_tools` and no act tools.

- **Only the tools a person lists may run: `read_tools` without approval, `act_tools` with one; every other tool is listed by `mcp_tools` as "not allowed" and refused.** A name in both lists is refused when the settings are applied, so the plugin is never switched on with it. This replaces the issue's "every MCP tool is read unless listed as act". Reason: a server's tools can change things without saying so, and a write tool nobody listed as act would otherwise run with no human asked; allowing reads one by one keeps "the agent changes nothing without an explicit yes" true for any server (#43, Danny).
- **A `read_tools` entry the server annotates `readOnlyHint: false` or `destructiveHint: true` is refused, and the health check names it.** Annotations only make Bleep stricter: a tool without them is judged by the settings alone. Reason: the annotations are the server's word, so they can take a permission away but never grant one (#43, Danny).
- **The endpoint and the token are environment variables, not settings**, and a settings body with `url` (or any field beyond the two lists) is refused as unknown. `GET /api/plugins` shows both as `{env, set, required}`; `MCP_TOKEN` is the first `optional_secrets` entry, handed to the plugin only when it is set. A changed `MCP_URL` takes effect when the plugin is next switched on (Bleep reads the environment then). Reason: the connection fields stay in the environment (#36, [settings](settings.md)); a URL a dashboard session could change would let it point Bleep's requests, and its token, at the socket proxy or any other host Bleep can reach (#43).
- **One MCP server per plugin, named `mcp`.** A plugin's name is fixed on its class, and its action must be one Bleep knows, so a second server would need a second class and a second fixed action. Reason: the narrowest form that keeps the plugin rules from #36 as they are (#43).
- **The server's tools are not turned into tools of their own: the model gets `mcp_tools`, which lists them (name, whether Bleep may run it, description, input schema), and `mcp_call`, which runs an allowed read tool by name.** Reason: a server's tool descriptions are its own text, and as tool definitions they would reach the model as if they were Bleep's; as `mcp_tools` output they are wrapped as untrusted data like a log. It also needs no renaming to `mcp_<tool>` (no collisions, no length limits), and the list is read live, where `Plugin.tools` is synchronous and could not discover the tools without blocking Bleep (#43).
- **Each call opens one session, lists the tools with the adapters (`load_mcp_tools`) and calls the tool on that same session (`ClientSession.call_tool`), never through the adapters' LangChain tools.** Whether the tool may run is judged against that same listing. Reason: an adapter tool is a LangChain runnable, which would report the server's raw output, token echoes included, to every tracer of the incident's run (Langfuse, LangSmith); calling the session directly leaves only Bleep's own `mcp_call`, with its guarded output, in the trace (#43).
- **Everything a server returns is untrusted**: tool output, error text and the listing go through `guard_text` (capped at 8,000 characters, stripped, redacted, wrapped with source `mcp`). An echo of `MCP_TOKEN` is replaced first, also where ANSI sequences, control or invisible characters or line breaks split it, before and after those are stripped. A token sent back transformed (base64, reversed, in pieces far apart) is not caught. A server that cannot be reached is reported by the error's type only. Reason: the same path as every other tool's output, and an error message can quote the URL or the server's words (#43).
- **MCP act tools are one fixed action, `mcp.call`, whose params are `tool` (one of `act_tools`) and `arguments` (a JSON object), and whose target is the container the call is for.** The plugin adds the action only when `act_tools` is not empty. Reason: the only change to the guard is one name in `schemas.graph.Action`; the plan check's target rules (on the host, found, not protected, not Bleep's own) apply unchanged because the target is a container, and the grant covers the params, so other arguments are another plan (#43).
- **`McpCall` checks before every call, as the Docker act tools do**: the step is the approved plan's, the grant matches the plan's hash, the target passes `check_target`; then the params name an act tool and a JSON object, and no argument mentions a protected container or one of Bleep's own on the step's host, by name, id or short id. Every refusal is logged as `blocked_action`. **These checks only cover what Bleep can recognise.** What an MCP tool does with its arguments is opaque: a tool that acts on a container named some other way, or on another host, or on Bleep itself without naming it, is not caught, so the protection of Bleep's own containers cannot be enforced for an MCP tool as it is for the Docker actions. The human approving the step, who sees the tool and its arguments, is the gate (#43).
- **A failed act call is a failed step in Bleep's words** ("the MCP tool reported an error", "the MCP server has no tool …", "the call to the MCP server failed (ConnectError); it may have run"); the server's text is not kept. Execute's restart check cannot tell whether an MCP call took effect, so a step left `started` by a crash is never run again and counts as not confirmed (#43).
- **A plugin step's params are shown in the Telegram proposal too** ([notify](notify.md)), as the dashboard already shows them. Reason: the human approves the tool and its arguments, not only the action's name (#43).
- **Propose's prompt does not describe `mcp.call` yet**; it appears in the enabled actions once `act_tools` is set, and `McpCall` refuses at Execute a step that does not fit. Describing it, with the act tools' argument schemas, and refusing a malformed step before the human is asked, is #118.
- **Calls are bounded**: 5 s for each HTTP request, 10 s to open the session and list the tools, 30 s more for the tool call itself. Reason: an endpoint that is not an MCP server fails within seconds instead of holding an Investigate round (#43).
- **The health check lists the tools within the registry's 5 s**: how many Bleep may run as read and as act, the listed names the server does not offer, and the read tools refused for their annotations (#43).
