# Plugins

How Bleep takes on tools that share one connection, such as a Coolify instance (`backend/src/bleep/plugins/`, `api/plugins.py`). A plugin is switched on and off as a whole from the dashboard; its settings are stored with the other settings ([settings](settings.md)), its secrets never are (spec §4.8, §4.10).

| Piece | Path | What it does |
|---|---|---|
| **Plugin** | `plugins/base.py` | The base class: `name`, `title`, `settings_model` (non-secret), `secrets` (environment variable names, or `secret_envs(settings)` when the settings name one), `tools(ctx)`, `act_handlers(ctx)` and `async health(ctx)`, each given a `PluginContext`. |
| **Registry** | `plugins/registry.py` | Which plugins are switched on, with what settings; their tools, act handlers and actions, read at every use; the view the API shows. |
| **Routes** | `api/plugins.py` | `GET /api/plugins` and `PUT /api/plugins/{name}` (`{enabled, settings}`, either part optional). |
| **MCP server by URL** | `plugins/mcp_url.py` | One MCP server over Streamable HTTP, through `langchain-mcp-adapters`: the read tools `mcp_tools` and `mcp_call`, and the act action `mcp.call` for the tools the settings list as act. |
| **List** | `wiring.py` (`PLUGINS`) | Every plugin Bleep has. |

## Choices

- **A plugin's methods take one `PluginContext`: its settings, its secrets by env name, `BLEEP_SECRET` and the guard log.** The plan had `tools(settings, secrets)` and `act_handlers()`. Reason: an act handler checks approval grants exactly as the Docker act tools do, so it needs the key the grants are signed with; one context keeps the three methods alike (#36).
- **A secret is the name of an environment variable, read when the plugin is switched on.** `GET /api/plugins` shows each one as `{env, set}`, never its value; the plugin's tools get it as a `SecretStr`, whose repr hides it. Reason: secrets never live in the database or reach the API or the model (§4.10) (#36).
- **A plugin's settings model must forbid unknown fields and may not have a field named like a secret** (`token`, `api_key`, `Password`; the [settings](settings.md) check), or the registry refuses the plugin when Bleep starts. Reason: settings are stored and shown, so a plugin author cannot put a token there by mistake (#36).
- **Every plugin is off until a person switches it on, and switching on needs valid settings and every secret set**; the refusal names the missing variable. Reason: a half-configured plugin would offer tools that fail on every call (#36).
- **The plugin's tools, act handlers and actions are read from the registry every time they are used.** `ToolRegistry` reads the switched-on plugins' tools on every read, `SettingsStore.enabled_actions` adds their actions to the core Docker ones, and Execute's act tools are a live view over the core ones and the plugins'. Reason: switching a plugin off takes its tools out of the next Investigate round, makes its actions fail the plan check as `disabled_action`, and leaves Execute without a handler even for a plan approved while it was on (#36).
- **A plugin's name is lower-case letters and digits and never `docker`; its tool names start with `<name>_` and its actions with `<name>.`, and each action must be one Bleep knows (`schemas.graph.Action`).** A core tool keeps its name over a plugin's, and a core action its handler. Reason: a plugin can neither shadow a core tool nor add a Docker action that would skip the Docker act tools' checks, and with no `_` in a name one plugin's prefix is never inside another's (#36).
- **A plugin whose own code fails while it is switched on is refused with its error's type only** ("plugin coolify could not be switched on (RuntimeError)"), as a 422 from the API and a warning on boot. Reason: the error's text could quote a setting or a secret, and a plugin that broke in a new version must not stop Bleep from starting (#36).
- **A plugin whose secret is unset at boot starts off, and its stored toggle stays on, also through a change of its settings alone.** Reason: Bleep must start without it, and the plugin is on again once the variable is back, without a person switching it again (#36).
- **A change that cannot be saved puts the plugin back exactly as it was.** Settings and the toggle are applied in memory only after they validate and the plugin builds, then stored; a failed write restores the snapshot. Reason: the dashboard must never show a plugin as off while its tools are still offered, or the other way round (#36).
- **The health check is bounded to 5 s, and its text is redacted and has the plugin's own secret values replaced.** A check that raises or times out reads "the health check failed" or "timed out". Only the secret as it is gets replaced; a plugin must not put a transformed secret in its health text. Reason: a slow or broken plugin must not hang or break the plugins page, and a health message that quotes the token it used must not show it (#36).
- **`plugins` builds on `tools`' types (`ToolSpec`, `ActHandler`) and `guard`'s known actions; `tools` reads the plugins only through the `ToolSource` protocol and never imports them.** Reason: a plugin hands Bleep tool specs and act handlers, so it needs their shapes, while the dependency still points one way (#36).

## MCP server by URL

The plugin `mcp` connects one MCP server by its URL. Its settings are `url` (the Streamable HTTP endpoint), `auth_env` (optional: the environment variable holding a bearer token) and `act_tools` (the server's tools that change something). Built on `langchain-mcp-adapters` 0.3.2 (`MultiServerMCPClient`, a new session for every call, `handle_tool_errors=False`) and `mcp` 1.30.0, read from their installed source; tests run the `mcp` package's own `FastMCP` server in-process, reached through an `httpx.ASGITransport`, so no socket is opened.

**Example: Coolify's own MCP server.** Coolify serves MCP at `https://<your-coolify-domain>/mcp` over Streamable HTTP once **Settings > Advanced > API and MCP > MCP server** is enabled (and MCP for the token's team), with the API token as a bearer token ([Coolify: Set up MCP](https://coolify.io/docs/mcp/setup)). A token with only the `read` permission makes it read-only ("Inventory and inspection"); `deploy` and `write` add lifecycle and change tools. So: create a `read` token, put it in `MCP_COOLIFY_TOKEN` in `.env`, and switch the plugin on with `{"url": "https://coolify.example.com/mcp", "auth_env": "MCP_COOLIFY_TOKEN"}` and no act tools.

- **One MCP server per plugin, named `mcp`.** A plugin's name is fixed on its class, and its action must be one Bleep knows, so a second server would need a second class and a second fixed action. Reason: the narrowest form that keeps the plugin rules from #36 as they are; more servers wait until one is needed (#43).
- **The server's tools are not turned into tools of their own: the model gets `mcp_tools`, which lists them (name, read or act, description, input schema), and `mcp_call`, which runs a read one by name.** Reason: a server's tool descriptions are its own text, and as tool definitions they would reach the model as if they were Bleep's; as `mcp_tools` output they are wrapped as untrusted data like a log. It also needs no renaming to `mcp_<tool>` (no collisions, no length limits), and the list is read live, so a server that changes its tools needs no switching off and on, where `Plugin.tools` is synchronous and could not discover them without blocking Bleep (#43).
- **Every MCP tool is read unless `act_tools` lists it.** `mcp_call` refuses an act tool without calling the server; an act tool runs only as an `mcp.call` step of an approved plan. Reason: the issue's rule, and MCP's own `readOnlyHint` annotation is the server's word, not Bleep's (#43).
- **Everything a server returns is untrusted**: tool output, error text and the listing are scrubbed of the plugin's own token, then go through `guard_text` (capped at 8,000 characters, stripped, redacted, wrapped with source `mcp`). A server that cannot be reached is reported by the error's type only. Reason: the same path as every other tool's output, and an error message can quote the URL or the server's words (#43).
- **The token is named by `auth_env`, which must match `MCP_[A-Z0-9_]+`, and the registry asks the plugin which variables it needs with these settings (`Plugin.secret_envs`).** `token_env` would fail the secret-name check of #36. The variable must be set before the plugin can be switched on, its value is sent only as `Authorization: Bearer`, and `GET /api/plugins` shows it as `{env, set}`. Reason: the name is a setting, but an `MCP_` prefix keeps a stolen session from pointing it at `BLEEP_SECRET` or a model key and sending that to a URL of its choosing (#43).
- **MCP act tools are one fixed action, `mcp.call`, whose params are `tool` (one of `act_tools`) and `arguments` (a JSON object), and whose target is the container the call is for.** The plugin adds the action only when `act_tools` is not empty. Reason: the only change to the guard is one name in `schemas.graph.Action`; the plan check's target rules (on the host, found, not protected, not Bleep's own) apply unchanged because the target is a container, and the grant covers the params, so other arguments are another plan (#43).
- **`McpCall` checks before every call, as the Docker act tools do**: the step is the approved plan's, the grant matches the plan's hash, the target passes `check_target`; then the params name an act tool and a JSON object, and no argument mentions a protected container or one of Bleep's own by name or id. Every refusal is logged as `blocked_action`. Reason: an MCP tool's arguments are opaque to Bleep, so a mention anywhere in them is refused rather than guessed about (#43).
- **A failed act call is a failed step in Bleep's words** ("the MCP tool reported an error", "the call to the MCP server failed (ConnectError); it may have run"); the server's text is not kept. Execute's restart check has no way to tell whether an MCP call took effect, so a step left `started` by a crash is never run again and counts as not confirmed (#43).
- **A step's params are shown in the Telegram proposal too** ([notify](notify.md)), as the dashboard already shows them. Reason: the human approves the tool and its arguments, not only the action's name (#43).
- **Propose's prompt does not describe `mcp.call` yet**; it appears in the enabled actions once `act_tools` is set, and the plan check and `McpCall` refuse a step that does not fit. Describing it, with the act tools' argument schemas, is a prompt change that needs its own evals (#118).
- **Calls are bounded**: 10 s for each HTTP connect and write, 30 s for a whole listing or call; the health check lists the tools within the registry's 5 s and names any act tool the server does not have (#43).
