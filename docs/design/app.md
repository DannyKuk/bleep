# App

The dashboard and the API it reads. One bullet per choice, with the reason and the issue number.

## Login, sessions and the read API

How the dashboard signs in and what it reads (`auth/`, `api/`).

- **One admin password, compared in constant time.** `hmac.compare_digest` against `BLEEP_ADMIN_PASSWORD`. Reason: a plain `==` leaks how many leading characters matched (#8).
- **Bleep refuses to start with an admin password under 12 characters,** with a message naming the variable. Reason: the login is the only thing between a LAN and a tool that can restart containers, and a short password is quick to guess (#8).
- **Sessions are random 32-byte tokens, stored as a sha256 hash.** The cookie holds the token; the `sessions` table holds only its hash. Reason: a leaked database file or backup cannot be replayed as a login (#8).
- **Seven-day sliding expiry.** `last_seen_at` and `expires_at` move forward on use, at most once a minute, and the cookie is renewed with them. Reason: a dashboard used daily should not log out mid-week, and one write per request is needless database churn (#8).
- **Cookie flags: `HttpOnly`, `SameSite=Lax`, `Path=/`, 7 days, `Secure` when `BLEEP_COOKIE_SECURE=true`.** Reason: HttpOnly keeps the token away from page scripts, Lax stops cross-site POSTs from carrying it, and Secure is opt-in because plain-http LAN use would otherwise never get a cookie (#8).
- **Login is rate limited: 5 failures per minute per client address.** A sixth attempt gets 429 with `Retry-After`, even with the right password, until the oldest failure leaves the window. Successful logins do not count. The state is in memory with an injectable clock. Reason: it stops guessing without locking the admin out for long, and a restart only forgives an attacker one minute (#8).
- **The client address is the direct peer, never `X-Forwarded-For`.** Reason: a header the client controls would let anyone reset their own limit; Bleep is LAN-only for now, so there is no trusted proxy to read it from (#8).
- **`require_session` guards every `/api` route except login,** through one router dependency, so a new route is protected by default. `/health` stays open and outside `/api`. A test walks the OpenAPI document and expects 401 on every other path. Reason: the safe default beats remembering to add a check (#8).
- **Response models are pydantic schemas (`schemas/api.py`).** Reason: `/openapi.json` gives the dashboard exact types. No model carries env values or labels, so a secret in a container's environment cannot reach a response (#8).

### Health rules

One pure function per level (`api/hosts.py`), table-tested for every state.

- **Container.** Running with health `healthy` or `none` is `ok`. Running and `starting`, or state `restarting`, is `degraded`. Running and `unhealthy`, `dead`, `created`, `paused`, or `exited` with a crash exit code (anything but 0 and 143, or none known), is `down`. `exited` with 0 or 143 (SIGTERM, what `docker stop` leaves) is `stopped`. Any other state is `unknown`. Reason: degraded means "may fix itself", down means "needs someone"; a paused container serves nothing; a clean exit is somebody's choice, not a fault. 137 stays a crash because the OOM killer leaves it too (#8, #13).
- **Service.** The worst of its containers and its URLs, where a `failing` URL counts as `down`. With no data it is `unknown`. A finished one-shot (exited 0, restart policy `no` or empty, e.g. Molecula's `fetch` init job) is left out while another container is there. When everything has exited cleanly the service is `stopped`, whatever its URLs say, because a failing URL is expected when it was shut down. One container stopped on purpose among running ones makes the service `degraded`. Crashes stay `down`. Reason: one dead dependency makes the service unusable, but a finished job or a deliberate stop is not an outage (#8, #13).
- **Host.** `unknown` when unreachable with no snapshot yet, `down` when unreachable, otherwise the worst of its services (`ok` with none); a `stopped` service counts as `ok`. Reason: an unreachable host's old containers say nothing about now, but with no snapshot there is nothing to call down; a host with a service shut down on purpose is not unhealthy (#8, #13).
- **`stopped` is grey (`--health-stopped`, a blue-grey) with a pause icon and the word "Stopped",** and a cleanly exited container chip uses the same tone. `ContainerView` carries `exit_code` for this. Reason: it must read differently from `unknown` without relying on colour (#13).
- **URL status stays `unknown`** until the watcher records checks; `basics` is `null` until the host probe exists. Reason: the dashboard shape is fixed now so those land without an API change (#8).

## Incidents API and the live stream

What the dashboard reads about incidents and how it answers an approval (`api/incidents.py`, `api/stream.py`). Every route is under `/api` and needs a session, like the rest.

| Route | Returns |
|---|---|
| `GET /api/incidents?status=&service_id=&limit=&offset=` | `Incident[]`, newest first; `limit` 1 to 200 (default 50); `service_id` keeps one service's |
| `GET /api/incidents/{id}` | `IncidentDetail`: the incident, `diagnosis`, `proposal`, `approval` (the latest, pending or decided), `outcome`, `report`, each null until the run has it, and `feedback`, the human's votes |
| `GET /api/incidents/{id}/events?after=` | `IncidentEvent[]` with `seq > after`, in seq order |
| `POST /api/incidents/{id}/decision` | body `{approval_id, kind, text?}`; 200 with the recorded `Decision`, or 409 `{detail, decided_via}` |
| `POST /api/incidents/{id}/feedback` | body `{target: "diagnosis" \| "proposal", vote: "up" \| "down", note?}`; 200 with the stored `Feedback`, 409 when the run has no such finding yet |
| `GET /api/recoveries?limit=` | `RecoveryEvent[]`, newest first; `limit` 1 to 200 (default 50) |
| `GET /api/stream?incident_id=&after=` | `text/event-stream` of `IncidentEvent` JSON |

- **The detail reads the run's findings from its checkpoint.** `diagnosis`, `proposal`, `outcome` and `report` come from the graph state (`IncidentRunner.state`), the approval from `ApprovalStore.current`. Reason: the checkpoint is the one place the run keeps them, so the dashboard cannot show a diagnosis the run no longer holds (#21).
- **The approval is shown with its status and decision, never its snapshots.** `status` is `pending`, `approved`, `rejected` or `instructed`, and `decision` says who answered and when. Reason: the dashboard must show "approved on Telegram" after the fact, and the container snapshots are only for Execute (#21).
- **A dashboard decision names the approval it answers (`approval_id`).** A decision for a plan that has since been replaced gets 409 "That plan was replaced by a newer one; reload to see it" and decides nothing; the id is passed on to `resolve`. Reason: after an instruction Propose writes a new plan, and a stale page must not approve a plan the human has not seen (§2, #20, #21).
- **The first answer wins; a later one is 409 naming the winner.** The body is `{"detail": "Already decided on Telegram", "decided_via": "telegram"}` (or "the dashboard"), whether the other channel won before the request or inside `resolve`, between the route's read and its write. Only the winner resumes the run, with the approval id it decided (`IncidentRunner.resume`), so the resume cannot answer a newer plan. Reason: Telegram and the dashboard can answer at the same moment, and the loser should know who decided (§4.9, #21).
- **Other refusals are 409 too, with `decided_via: null`:** nothing asked yet ("Nothing is waiting for a decision"), or the incident already resolved, closed or failed. An unknown incident is 404. Reason: one error shape for every "this decision did not count" (#21).
- **An instruction needs text; an approve or reject drops it.** Text is trimmed, at most 2,000 characters; an empty instruction is 422. Reason: the text goes into Propose's prompt as the human's instruction, and only an instruction has a use for it (#21).
- **Feedback needs the finding it rates.** A vote on the diagnosis or the plan before the run has one is 409 "There is no diagnosis to rate yet" (or "plan"). The note is trimmed, an empty one dropped, at most 200 characters, the length memory keeps (#87). A second vote on the same target replaces the first, and the memory record gets the votes now or when Report writes it ([memory](memory.md)). Reason: a vote on nothing would be remembered as a judgement on a finding nobody saw (#30).
- **Recoveries are newest first.** `IncidentRepo.recoveries` orders by time descending. Reason: with a limit, oldest first would show the same old rows forever (#21).

### Services and their memory

The service page's reads and a service's facts (`api/hosts.py`, `api/memory.py`).

| Route | Returns |
|---|---|
| `GET /api/services/{id}` | `ServiceDetail`: the `ServiceView` the overview shows, its `rules` and its host's `host_rules`; 404 for a service the registry does not know, or whose host is gone |
| `GET /api/services/{id}/facts` | `ServiceFact[]`, oldest first: `{id, text, source: "human" \| "report", created_at, incident_id}` |
| `POST /api/services/{id}/facts` | body `{text}`; 200 with the new `ServiceFact` (`source: "human"`); 404 for an unknown service |
| `DELETE /api/services/{id}/facts/{fact_id}` | 204; 404 when the service has no such fact |

- **A service id is a path: `demo/compose:shop`.** The routes take it with `{service_id:path}`, and the facts router is registered before the hosts router, because `GET /services/{id:path}` would also match `.../facts`. The dashboard encodes the id (`demo%2Fcompose%3Ashop`); the backend sees it decoded either way. Reason: the id is the registry's own key, and a second, URL-safe id would have to be kept in step with it (#30).
- **The service page reuses the overview's view and the incident list.** `ServiceDetail` wraps the same `ServiceView` (containers, URLs, health, open incident) and adds only the rules; past incidents are `GET /api/incidents?service_id=`. Reason: one shape per thing, so the page and the overview cannot disagree (#30).
- **A fact needs a service Bleep knows, and text.** Trimmed, at most 200 characters (the length memory keeps, #87), empty is 422; it is cleaned like every memory text. Listing and deleting work for a service that is gone, so its memory can still be cleared. Reason: a fact for a typo'd id would never reach an incident (#30).

### The stream

- **Server-sent events through `sse-starlette`, one JSON `IncidentEvent` per message, no event name.** Reason: the browser's `EventSource` reconnects by itself, and one `onmessage` handler reads every kind; the dashboard serves the stream through a route handler (#21, #23).
- **`id:` is the event's seq, and a reconnect replays from `Last-Event-ID`.** With `incident_id` the stream sends that incident's history after the cursor, then live events. The cursor is the `Last-Event-ID` header the browser sends on a reconnect, else `after` from the query (the first connect, after the page loaded `/events`), else 0. Reason: nothing published while the browser was away is lost, and nothing is sent twice (#21).
- **Subscribe first, then read the history, then de-duplicate and fill gaps by seq.** `follow(bus, incident_id, after)` skips a live event already sent, and when the bus has dropped a slow subscriber's oldest events (a seq gap) it reads the missing ones from the history. Reason: the stream must be complete and in order even when the client is slower than the agent (#11, #21).
- **Without `incident_id`, every incident's events, live only and without `id:`.** Reason: seq counts per incident, so it is no cursor across incidents; the overview does not use the stream and keeps polling its lists (#21, #23).
- **A ping comment every 15 s (`PING_S`).** Reason: proxies may close a connection that stays silent, and an incident can wait hours for a human with nothing on its stream (#21).
- **The session is checked when the stream opens.** An open stream outlives that check; every reconnect is a new request and is checked again. Reason: re-checking an open stream would need a timer per connection for little gain on a single-admin LAN tool (#21).
- **Closing the stream unsubscribes from the bus.** Reason: a closed tab must not leave a queue filling forever (#11, #21).

## Dashboard

How the Next.js dashboard (`frontend/`) is built.

- **Rewrite proxy, not CORS.** `next.config.ts` rewrites `/api/:path*` to the backend, so the browser only talks to the dashboard's origin and the `bleep_session` cookie (HttpOnly, SameSite=Lax) is same-origin. Reason: no CORS config, no cross-site cookie, and the backend port is never exposed to the browser (#9).
- **`BACKEND_URL` is a build argument.** Next bakes rewrite destinations into `routes-manifest.json` at `next build`; setting the variable only when the server starts has no effect (checked by running the standalone server with a different value). The Dockerfile takes `ARG BACKEND_URL` with the default `http://backend:8000`, the Compose service name. Compose (Task 10) must therefore pass `build.args.BACKEND_URL` for the frontend service. Reason: a silent runtime variable that does nothing is worse than a documented build argument (#9).
- **A 401 sends the browser to `/login?next=<path>`.** `apiFetch` does this once for every call, except on the login page itself, where a 401 means "wrong password". The login form only follows a `next` that the URL parser resolves to the same origin (a prefix check misses `/\t/evil.com`, because parsers drop tabs and newlines). Reason: one place handles an expired session, and `next` cannot be used as an open redirect (#9).
- **Polling every 10 s until live events.** `usePoll` fetches `/api/hosts` and `/api/services` on an interval and keeps the last good data when a refresh fails, with a small "refresh failed" line. It pauses while the tab is hidden (so an idle tab does not slide the session) and refetches when it becomes visible; each tick aborts the previous one and carries a sequence number, so a slow old response never overwrites newer data; hosts and services come from one `Promise.all` and are committed together. Reason: the simplest thing that works against the M1 API (#9). The overview, the recoveries and the incident list still poll; only an incident's own page streams, with a slow poll of its findings beside it (#23).
- **Health colours: green, amber, red, grey, never alone.** `--health-ok`, `--health-degraded`, `--health-down` and `--health-unknown` are CSS variables with a light and a dark value, used as text on a 12% tint of themselves. Every health also has its own icon (check, triangle, cross, question mark) and a word, so colour-blind readers and greyscale prints lose nothing. Reason: an ops screen is read under stress and at a glance; colour is a quick cue, not the only one (#9).
- **Quiet when all is well.** Healthy rows use small tinted badges and no borders or alarms; only down and degraded things use stronger colour, plus the incident link. Reason: the eye should land on what is wrong (#9).
- **The Bleep tokens live in `app/globals.css`: `--bg`, `--surface`, `--soft`, `--line`, `--ink`, `--ink-2`, `--accent`, `--accent-ink`, `--ok`/`--warn`/`--down`/`--stop` with their `-bg` tints, and Bleep's `--blob`, `--hand`, `--cup`, `--screen`,** each with a light value in `:root` and a dark one in `.dark`, and a Tailwind utility of the same name (`bg-surface`, `text-ink-2`, `border-line`, `bg-ok-bg`). The old names stay as aliases onto them so screens not yet restyled keep working: `background`=bg, `foreground`=ink, `card`=surface, `muted`=soft, `muted-foreground`=ink-2, `border` and `input`=line, `primary` and `ring`=accent, `health-ok`/`degraded`/`down`/`stopped`/`unknown` = ok/warn/down/stop/stop, each with a `-bg` tint. Reason: new code uses the spec's names, old code changes screen by screen, and nothing breaks in between. One catch: shadcn's `accent` was a hover tint and is now the brand colour, so the hover on list rows and the ghost button use `soft` instead (#90).
- **Dark tints are `color-mix` of the text colour (13 to 14%) over `surface`, not a second hex.** Reason: the spec defines them as "the colour at 13%"; mixing keeps that rule in one place, and the contrast test resolves it (#90).
- **A test checks the contrast of the colour pairs in the design from `globals.css` itself** (`lib/contrast.test.ts`): ink, ink-2, accent and the four health colours on `surface`, `bg` and `soft`, each health colour on its own tint, and `accent-ink` on `accent`, in both themes, at least 4.5:1. Reason: parsing the stylesheet keeps one source of truth for the values, so a colour tweak that breaks readability fails the build instead of shipping (#90).
- **Nunito (400 to 800) is the sans font and JetBrains Mono (400, 500) the mono font, both through `next/font/google`** as `--font-nunito` and `--font-jetbrains-mono`; `font-mono` is for names, ids and URLs and is not used bold. Reason: same loading path as the fonts before it, so the build needs the network exactly as it did (#90).
- **Shapes: `rounded-card` (28 px) and `rounded-card-sm` (22 px, phone) for cards, `rounded-row` (20 px) for rows inside them, `rounded-field` (14 px) for inputs; buttons, badges and pills are `rounded-full`.** `Button` is 44 px tall (`sm` is 36 px with a fine pointer and 44 px on a touch screen), `Input` 44 px. `Panel` takes `awaitingYou` for the 2 px accent border of the card that waits for the human. Reason: touch targets of at least 44 px, and the awaiting card must stand out without colour alone being its only cue, since its Needs your yes pill and buttons stay (#90).
- **An incident waiting for the human reads "Needs your yes";** every other status word is unchanged (#90).
- **Monospace for container names, ids and URLs.** Reason: they are copied into terminals and compared character by character (#9).
- **Theme: system, light or dark, kept across reloads.** The pick lives in `localStorage` (`bleep:theme`); an inline script in `<head>` sets the `dark` class on `<html>` before the first paint, so there is no flash. "System" follows the OS setting live. Reason: same approach as the owner's other projects; reading storage only after hydration would flash the wrong theme on every load (#9).
- **Unit tests mock `fetch`, nothing else.** Vitest with Testing Library and jsdom; the poll and login tests stub the global `fetch`, so no test needs a backend or network. Reason: the dashboard is built against the API contract in parallel with the backend (#9).
- **Types are written by hand for now.** `lib/api-types.ts` follows the contract of #8 and #21; `npm run gen:api` replaces it with types generated from the backend's `/openapi.json` once that is running. The names `HostView`, `ServiceView`, `ContainerView`, `UrlStatus` and `Health` stay (#9).

### Incident pages (#23)

The incident list (`/incidents`), one incident's page (`/incidents/[id]`) and the recoveries on the overview (`frontend/components/incident/`, `components/overview/recoveries.tsx`, `lib/use-incident-stream.ts`).

- **The live stream is a route handler, not the rewrite.** `app/api/stream/route.ts` pipes the backend's `/api/stream` with `Cache-Control: no-cache, no-transform`, forwarding only the cookie, `Last-Event-ID` and `Accept`. Through the rewrite, Next gzips `text/event-stream` and held every event until the stream ended, under `next start` and the standalone server alike. `next.config.ts` inlines `BACKEND_URL` for the handler at build time, the same build argument as the rewrite. Reason: a live view that shows nothing until the incident ends is not live ([evidence](../decisions/sse-through-next.md)) (#23).
- **`useIncidentStream(id)` reads the history, then streams after its last seq.** It loads `/events`, then opens `EventSource` with `after=<last seq>`. A dropped connection is retried by the browser with `Last-Event-ID`; a stream the browser gives up on (a 401, 404 or 5xx closes it) is reopened after 5 s by reading the history again from the last seq, through `apiFetch`, so a lost session goes to the login page. Every event is kept once by seq (`mergeEvents`), however the replays overlap. Reason: the backend's replay and the page's own history read can both send an event twice, and nothing may be shown twice or lost (#23).
- **The page reloads the incident when a step event arrives, not on tool events.** Diagnose publishes no event of its own and the findings live in the run's checkpoint, so every event except `tool_call` and `tool_result` (`node_finished`, `proposal`, `approval_requested`, `decision`, a notice) reads `GET /api/incidents/{id}` again; the newest read wins. It is also read every 10 s while the tab is visible, because the runner sets the status after the run's last event (Awaiting approval, Resolved) and publishes nothing for it. Reason: one read per step keeps the cards in step with the run, a long investigation does not cause a read per tool call, and the slow poll catches what has no event (#23).
- **Live reasoning is the tool calls, each with its arguments and its result folded under it.** A result is matched to the oldest open call of the same tool. Only the result's size and first line are on the bus, so that is what the fold shows. Reason: what the model looked at is the part a human checks; the full output stays with the run and its guard (#23).
- **The timeline merges a node's start and finish into one line** ("Investigating", then "Investigated") and lists the question, the answer with its channel, and notices. Reason: a list of raw start and finish events doubles its length and says less (#23). Each step of a plan gets a line per status change (`docker.start shop-web-1: started`, then `done`, `failed` or `skipped`, red when failed) and each verification check one ("Check 1 failed", amber, "Check 2 passed"). Reason: what Bleep did to a host must be visible as it happens, not only in the report (#25).
- **An unsure diagnosis carries an "I am not sure" banner** above the cause, in amber with its own icon. Reason: a plan built on a guess must not look as solid as one built on evidence (§4.4, #23).
- **The proposal card shows the plan the pending approval put to the human, and the decision bar sends that approval's id.** When the run holds a newer plan than a decided approval (after an instruction), the card shows the newer plan and one line for the earlier answer. Reason: the human approves what is on the screen, and the backend refuses a decision for a plan that was replaced (#21, #23).
- **After any answer the buttons lock and the outcome stays on screen.** A 409 shows its message ("Already decided on Telegram") and locks too; any other error keeps the buttons, so the human can try again. A decision made on another channel shows as decided, with who and when. The bar is keyed by the approval id, so a new plan gets fresh buttons. Reason: a second click must not look like it might count, and the loser of a race must know who won (§4.9, #23).
- **Bleep's own advice in a plan gets its own block.** `human_instructions` is Bleep's text to the human, so the card shows it at normal weight under "What to do" (the fix to make for a no-action plan, such as the setting to change and the command that applies it) or "Why nothing will run" (Bleep's checks refused the plan twice). The human's own instructions stay on the timeline and in the "Earlier plan answered with an instruction" line. Reason: for a no-action incident that text is the one actionable output, and it must not read as an echo of something the human said (#72).
- **"Tell Bleep something" is the instruction.** It opens a text box (2,000 characters at most, empty is refused) and says that nothing runs until a plan is approved. Reason: an instruction leads to a new plan, never to an action (#23).
- **A plan Bleep's own checks refused has no Approve button.** The decision bar shows "Tell Bleep something" (the instruction, which Bleep plans again with) and "Let it go" (a reject), and the card says why nothing will run. Reason: nothing can run from a refused plan, so offering Approve would only be refused (#113).
- **An incident's status uses the health colours:** red when it waits for a human or failed, amber while Bleep works, green when resolved, grey when closed; each with its word and icon. Reason: the same visual language as the overview, where red means "needs someone" (#23).
- **The report sits on top of the incident's page once the run has written it** (`components/incident/report-view.tsx`): the outcome line, the summary, the cause, the action ("Nothing ran."), the decision ("You were not asked."), the follow-ups and the report's own timeline. The outcome is green only for `resolved`, amber for `unverified` and `budget`, grey otherwise (`replan_limit` included, #25). Reason: how it ended is the first thing a human looks for, and an action nobody confirmed must not look like good news (#27).
- **Every diagnosis and plan asks "Was this right?" with Right and Wrong buttons** (`components/incident/feedback.tsx`) once the run has it. A vote is sent at once and shown pressed; "Add a note" opens a box whose text goes with the next vote; a failure says so and keeps the buttons. The service in the incident's header links to the service's page. Reason: one click is all a human gives in the middle of an outage, and the note is there when they have more to say (#30).
- **Recoveries go on the overview, the 10 newest, polled every 30 s,** with the container, host, time and the one-line explanation. Reason: a self-recovery is not an incident, but a container that keeps recovering is worth a glance (#14, #23).

### Service page (#30)

One service's page (`/services/[id]`, `components/service/`), reached from the service's name on the overview and from an incident's header.

- **The page shows the service's containers and URLs, its rules, its memory and its past incidents.** Rules come in two groups, the service's own and its host's, as the hosts file gives them; past incidents are the 20 newest. Reason: before a human approves a plan, what Bleep already knows and has been told about the service is one click away (#30).
- **Memory is a list of facts, each with where it came from, and a box to add one.** A person's fact reads "Added by you"; a report's reads "Learned from an incident's report" and links that incident. Each has a delete button; a failed add or delete keeps the list and says why. Reason: a fact Bleep learned is trusted on every later incident, so the human must see where it came from and be able to remove it (#30).
- **A service Bleep does not see any more still shows its memory and incidents,** with one line saying it is gone from its host. Reason: the facts of a removed or renamed service should be readable and deletable, not stranded (#30).
- **The page's parts are small and take their data as props** (`FactList`, `RuleList`, the shared `Panel`), with the reads in `MemoryPanel` and `ServicePage`. Reason: the dashboard is being restyled, and a new look should not have to touch the data code (#30).

### Settings page (#41)

The settings page (`/settings`, `components/settings/`). What it may change and how a save is built is in [settings](settings.md).

- **A failed read of the services Bleep sees is shown as an alert above the hosts**, which then list only the services with settings of their own. Reason: a host with no services listed would otherwise look empty rather than unread (#41).
- **One panel per host, then thresholds, plugins, Telegram and models**, in the existing look (`Panel`, `Badge`, `Button`, `Input`, the health colours for "set" and "missing"). Reason: the dashboard is being restyled separately, so this page adds no style of its own (#41).
- **Every list is edited as a draft and saved as a whole, with Save and Cancel shown only once something changed.** Each editor is keyed by the values it was built from, so a save that returns new values starts a fresh draft. Reason: one save per list matches one override per list, and a form that always shows Save invites saving nothing (#41).
- **A plugin's form is built from its `settings_schema`**: a text input for a string, a decimal input for a number, a checkbox for a boolean, a box with one entry per line for a list of strings; any other type is shown read-only. An empty field is left out, so the plugin's default holds and shows as the placeholder; a checkbox shows its default until the plugin has settings, and an untouched one sends that default, never `false`. A field typed as a secret gets no input at all. Switching on and saving the settings are separate requests, each showing the API's refusal ("needs COOLIFY_TOKEN set in the environment first"). Reason: a plugin author adds settings without touching the dashboard (#41).
