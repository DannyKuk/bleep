# App

The dashboard and the API it reads. One bullet per choice, with the reason and the issue number.

## Login, sessions and the read API

How the dashboard signs in and what it reads (`auth/`, `api/`).

- **One admin password, compared in constant time.** `hmac.compare_digest` against `BLEEP_ADMIN_PASSWORD`. Reason: a plain `==` leaks how many leading characters matched (#8).
- **Bleep refuses to start with an admin password under 12 characters,** with a message naming the variable. Reason: the login is the only thing between a LAN and a tool that can restart containers, and a short password is quick to guess (#8).
- **Sessions are random 32-byte tokens, stored as a sha256 hash.** The cookie holds the token; the `sessions` table holds only its hash. Reason: a leaked database file or backup cannot be replayed as a login (#8).
- **Seven-day sliding expiry.** `last_seen_at` and `expires_at` move forward on use, at most once a minute, and the cookie is renewed with them. Reason: a dashboard used daily should not log out mid-week, and one write per request is needless database churn (#8).
- **Cookie flags: `HttpOnly`, `SameSite=Lax`, `Path=/`, 7 days, `Secure` when `BLEEP_COOKIE_SECURE=true`.** Reason: HttpOnly keeps the token away from page scripts, Lax stops cross-site POSTs from carrying it, and Secure is opt-in because plain-http LAN use would otherwise never get a cookie (#8).
- **Login is rate limited: 5 failures per minute per client address.** A sixth attempt gets 429 with `Retry-After`, even with the right password, until the oldest failure leaves the window. Successful logins do not count. The state is in memory with an injectable clock. Reason: it stops guessing without locking the admin out for long, and a restart only forgives an attacker one minute (#8).
- **The client address is the direct peer, never `X-Forwarded-For`.** Reason: a header the client controls would let anyone reset their own limit; Bleep is LAN-only, so there is no trusted proxy to read it from (#8).
- **`require_session` guards every `/api` route except login,** through one router dependency, so a new route is protected by default. `/health` stays open and outside `/api`. A test walks the OpenAPI document and expects 401 on every other path. Reason: the safe default beats remembering to add a check (#8).
- **Response models are pydantic schemas (`schemas/api.py`).** Reason: `/openapi.json` gives the dashboard exact types. No model carries env values or labels, so a secret in a container's environment cannot reach a response (#8).

### Health rules

One pure function per level (`watcher/health.py`, shared by the API, the watcher's recheck after a quiet and its stored health with its "since", #232), table-tested for every state.

- **Container.** Running with health `healthy` or `none` is `ok`. Running and `starting`, or state `restarting`, is `degraded`. Running and `unhealthy`, `dead`, `created`, `paused`, or `exited` with a crash exit code (anything but 0 and 143, or none known), is `down`. `exited` with 0 or 143 (SIGTERM, what `docker stop` leaves) is `stopped`. Any other state is `unknown`. Reason: degraded means "may fix itself", down means "needs someone"; a paused container serves nothing; a clean exit is somebody's choice, not a fault. 137 stays a crash because the OOM killer leaves it too (#8, #13).
- **Service.** The worst of its containers and its URLs, where a `failing` URL counts as `down`. With no data it is `unknown`. A finished one-shot (exited 0, restart policy `no` or empty, such as a migration job) is left out while another container is there. A service of finished jobs only is `done`; when everything else has exited cleanly it is `stopped`, whatever its URLs say, because a failing URL is expected when it was shut down. One container stopped on purpose among running ones makes the service `degraded`. Crashes stay `down`. Reason: one dead dependency makes the service unusable, but a finished job or a deliberate stop is not an outage (#8, #13).
- **Host.** `unknown` when unreachable with no snapshot yet, `down` when unreachable, otherwise the worst of its services (`ok` with none); a `stopped` service counts as `ok`. Reason: an unreachable host's old containers say nothing about now, but with no snapshot there is nothing to call down; a host with a service shut down on purpose is not unhealthy (#8, #13). A host that may sleep and does not answer is `asleep`, whether it was seen before or not, and so is every service on it (not judged from its last listing or its failing URL checks). Reason: a laptop with its lid closed is not down and has no service that is down, and after a restart of Bleep it is still most likely asleep (#85).
- **Done.** A container that exited 0 and is a one-shot (no restart policy) or named in its service's `exits` is `done`; a service of `done` containers only is `done`, `done` beside running containers changes nothing, and a host counts a `done` service as `ok` ([watcher](watcher.md#expected-exits-and-this-is-expected-84-256)). Reason: a finished job is the normal end of its day, not something somebody stopped (#256).
- **Quiet.** A service view keeps its real `health` and carries `quiet` (`scope` is `host` when it is quiet through its host). A host's `health` is judged over its non-quiet services only, so a host whose only down service is quiet is `ok`; a quiet host keeps its real health and carries `quiet`, and `quiet_service_ids` lists its quiet services. One `QuietStore.active()` read serves each request. A quiet state for a service that is gone has no row and does no harm. Reason: the dashboard decides how to show it and nothing loses information, but the host is what the overview tints (#220).
- **`stopped` is grey (`--health-stopped`, a blue-grey) with a pause icon and the word "Stopped",** and a cleanly exited container chip uses the same tone. `ContainerView` carries `exit_code` for this. Reason: it must read differently from `unknown` without relying on colour (#13).
- **A URL with no stored check is `unknown`, and a host's `basics` is `null` until the first read.** Reason: the dashboard shows "not checked yet" rather than a guess (#8).

## Incidents API and the live stream

What the dashboard reads about incidents and how it answers an approval (`api/incidents.py`, `api/stream.py`). Every route is under `/api` and needs a session, like the rest.

| Route | Returns |
|---|---|
| `GET /api/incidents?status=&service_id=&fold_of=&limit=&offset=` | `IncidentListItem[]`: each `Incident` with `votes` `{diagnosis, proposal}`, each `"up"`, `"down"` or null; newest first; `limit` 1 to 200 (default 50); `service_id` keeps one service's, `fold_of` the repeats of one incident; each item also carries `fold_of` and `repeats` |
| `GET /api/incidents/{id}` | `IncidentDetail`: the incident, `diagnosis`, `proposal`, `approval` (the latest, pending or decided), `outcome`, `report`, each null until the run has it, and `feedback`, the human's votes; also `fold_of`, `repeats` and `expectation` |
| `GET /api/incidents/{id}/events?after=` | `IncidentEvent[]` with `seq > after`, in seq order |
| `POST /api/incidents/{id}/decision` | body `{approval_id, kind, text?}`; 200 with the recorded `Decision`, or 409 `{detail, decided_via}` |
| `POST /api/incidents/{id}/feedback` | body `{target: "diagnosis" \| "proposal", vote: "up" \| "down", note?}`; 200 with the stored `Feedback`, 409 when the run has no such finding yet |
| `GET /api/recoveries?limit=` | `RecoveryEvent[]`, newest first; `limit` 1 to 200 (default 50) |
| `GET /api/stream?incident_id=&after=` | `text/event-stream` of `IncidentEvent` JSON |

- **The detail reads the run's findings from its checkpoint.** `diagnosis`, `proposal`, `outcome` and `report` come from the graph state (`IncidentRunner.state`), the approval from `ApprovalStore.current`. Reason: the checkpoint is the one place the run keeps them, so the dashboard cannot show a diagnosis the run no longer holds (#21).
- **The approval is shown with its status and decision, never its snapshots.** `status` is `pending`, `approved`, `rejected` or `instructed`, or `closed` when the incident finished before anyone answered ([graph](graph.md#approval), #277), and `decision` says who answered and when. Reason: the dashboard must show "approved on Telegram" after the fact, and the container snapshots are only for Execute (#21).
- **A dashboard decision names the approval it answers (`approval_id`).** A decision for a plan that has since been replaced gets 409 "That plan was replaced by a newer one; reload to see it" and decides nothing; the id is passed on to `resolve`. Reason: after an instruction Propose writes a new plan, and a stale page must not approve a plan the human has not seen (#20, #21).
- **The first answer wins; a later one is 409 naming the winner.** The body is `{"detail": "Already decided on Telegram", "decided_via": "telegram"}` (or "the dashboard"), whether the other channel won before the request or inside `resolve`, between the route's read and its write. Only the winner resumes the run, with the approval id it decided (`IncidentRunner.resume`), so the resume cannot answer a newer plan. A yes that loses to an outside close (quiet, a removed host) gets 409 "The incident was closed before anyone answered" (#277). Reason: Telegram and the dashboard can answer at the same moment, and the loser should know who decided (#21).
- **Other refusals are 409 too, with `decided_via: null`:** nothing asked yet ("Nothing is waiting for a decision"), or the incident already resolved, closed or failed. An unknown incident is 404. Reason: one error shape for every "this decision did not count" (#21).
- **An instruction needs text; an approve or reject drops it.** Text is trimmed, at most 2,000 characters; an empty instruction is 422. Reason: the text goes into Propose's prompt as the human's instruction, and only an instruction has a use for it (#21).
- **Feedback needs the finding it rates.** A vote on the diagnosis or the plan before the run has one is 409 "There is no diagnosis to rate yet" (or "plan"). The note is trimmed, an empty one dropped, at most 200 characters, the length memory keeps (#87). A second vote on the same target replaces the first, and the memory record gets the votes now or when Report writes it ([memory](memory.md)). Reason: a vote on nothing would be remembered as a judgement on a finding nobody saw (#30).
- **The list carries the human's votes, not their notes.** `votes` comes from `incident_feedback` in one query per page (`MemoryStore.votes`); an incident nobody rated has both null. Reason: the service page shows right or wrong per past incident without a detail read for each, and a note is free text that belongs on the incident's own page (#232).
- **Recoveries are newest first.** `IncidentRepo.recoveries` orders by time descending. Reason: with a limit, oldest first would show the same old rows forever (#21).

### Services and their memory

The service page's reads and a service's facts (`api/hosts.py`, `api/memory.py`).

| Route | Returns |
|---|---|
| `GET /api/services/{id}` | `ServiceDetail`: the `ServiceView` the overview shows, its `rules` and its host's `host_rules`, `health_since` (null when not known) and `recent_checks`, per configured URL its last checks oldest first (`ok`, `status_code`, `latency_ms`, `checked_at`); 404 for a service the registry does not know, or whose host is gone |
| `GET /api/services/{id}/facts` | `ServiceFact[]`, oldest first: `{id, text, source: "human" \| "report", created_at, incident_id}` |
| `POST /api/services/{id}/facts` | body `{text}`; 200 with the new `ServiceFact` (`source: "human"`); 404 for an unknown service |
| `DELETE /api/services/{id}/facts/{fact_id}` | 204; 404 when the service has no such fact |

- **A service id is a path: `demo/compose:shop`.** The routes take it with `{service_id:path}`, and the facts router is registered before the hosts router, because `GET /services/{id:path}` would also match `.../facts`. The dashboard encodes the id (`demo%2Fcompose%3Ashop`); the backend sees it decoded either way. Reason: the id is the registry's own key, and a second, URL-safe id would have to be kept in step with it (#30).
- **The service page reuses the overview's view and the incident API.** `ServiceDetail` wraps the same `ServiceView` (containers, URLs, health, open incident) and adds only the rules; past incidents are `GET /api/incidents?service_id=`, drawn on the page as rows with the shared status badge (#97). Reason: one shape per thing, so the page and the overview cannot disagree (#30).
- **"Since" and the recent checks are on the detail only.** `GET /api/services` and `GET /api/hosts` keep their shape; `ServiceDetail` gains `health_since` and `recent_checks`. Reason: the overview polls every service every 10 s and shows neither, so it should not pay for 30 rows per URL (#232).
- **`health_since` is given only when the stored health is the one judged now.** It is the `since` of the watcher's `service_health` row ([watcher](watcher.md#health-since-and-recent-checks-232)); when that row's health differs from the view's (the watcher has not judged the change yet, or the view is `unknown` after a restart before the first listing), it is null. Reason: "healthy since" next to a `down` pill, or a time from before an outage, would be a wrong answer, and null lets the page say nothing (#232).
- **A recent check is the result and its numbers only:** `ok`, `status_code`, `latency_ms`, `checked_at`, no error text and no body. Each configured URL is listed, with an empty list before its first check; results for URLs no longer configured are left out. Reason: the error text can carry what a server wrote, the latest check's status already says why it failed, and the strip only needs green or red with a time (#232).
- **A fact needs a service Bleep knows, and text.** Trimmed, at most 200 characters (the length memory keeps, #87), empty is 422; it is cleaned like every memory text. Listing and deleting work for a service that is gone, so its memory can still be cleared. Reason: a fact for a typo'd id would never reach an incident (#30).

### The stream

- **Server-sent events through `sse-starlette`, one JSON `IncidentEvent` per message, no event name.** Reason: the browser's `EventSource` reconnects by itself, and one `onmessage` handler reads every kind; the dashboard serves the stream through a route handler (#21, #23).
- **`id:` is the event's seq, and a reconnect replays from `Last-Event-ID`.** With `incident_id` the stream sends that incident's history after the cursor, then live events. The cursor is the `Last-Event-ID` header the browser sends on a reconnect, else `after` from the query (the first connect, after the page loaded `/events`), else 0. Reason: nothing published while the browser was away is lost, and nothing is sent twice (#21).
- **Subscribe first, then read the history, then de-duplicate and fill gaps by seq.** `follow(bus, incident_id, after)` skips a live event already sent, and when the bus has dropped a slow subscriber's oldest events (a seq gap) it reads the missing ones from the history. Reason: the stream must be complete and in order even when the client is slower than the agent (#11, #21).
- **Without `incident_id`, every incident's events, live only and without `id:`.** Reason: seq counts per incident, so it is no cursor across incidents; the overview does not use the stream and keeps polling its lists (#21, #23).
- **A ping comment every 15 s (`PING_S`).** Reason: proxies may close a connection that stays silent, and an incident can wait hours for a human with nothing on its stream (#21).
- **The session is checked when the stream opens.** An open stream outlives that check; every reconnect is a new request and is checked again. Reason: re-checking an open stream would need a timer per connection for little gain on a single-admin LAN tool (#21).
- **Closing the stream unsubscribes from the bus.** Reason: a closed tab must not leave a queue filling forever (#11, #21).

## Dashboard

How the Next.js dashboard (`frontend/`) is built.

- **Rewrite proxy, not CORS.** `next.config.ts` rewrites `/api/:path*` to the backend, so the browser only talks to the dashboard's origin and the `bleep_session` cookie (HttpOnly, SameSite=Lax) is same-origin. Reason: no CORS config, no cross-site cookie, and the backend port is never exposed to the browser (#9).
- **`BACKEND_URL` is a build argument.** Next bakes rewrite destinations into `routes-manifest.json` at `next build`; setting the variable only when the server starts has no effect (checked by running the standalone server with a different value). The Dockerfile takes `ARG BACKEND_URL` with the default `http://backend:8000`, the Compose service name. Compose passes `build.args.BACKEND_URL` for the frontend service. Reason: a silent runtime variable that does nothing is worse than a documented build argument (#9).
- **A 401 sends the browser to `/login?next=<path>`.** `apiFetch` does this once for every call, except on the login page itself, where a 401 means "wrong password". The login form only follows a `next` that the URL parser resolves to the same origin (a prefix check misses `/\t/evil.com`, because parsers drop tabs and newlines). Reason: one place handles an expired session, and `next` cannot be used as an open redirect (#9).
- **The overview polls every 10 s.** `usePoll` fetches `/api/hosts` and `/api/services` on an interval and keeps the last good data when a refresh fails, with a small "refresh failed" line. It pauses while the tab is hidden (so an idle tab does not slide the session) and refetches when it becomes visible; each tick aborts the previous one and carries a sequence number, so a slow old response never overwrites newer data; hosts and services come from one `Promise.all` and are committed together. Reason: the simplest thing that works (#9). The overview, the recoveries and the incident list still poll; only an incident's own page streams, with a slow poll of its findings beside it (#23).
- **Health colours: green, amber, red, grey, never alone.** `--health-ok`, `--health-degraded`, `--health-down` and `--health-unknown` are CSS variables with a light and a dark value, used as text on a 12% tint of themselves. Every health also has its own icon (check, triangle, cross, question mark) and a word, so colour-blind readers and greyscale prints lose nothing. Reason: an ops screen is read under stress and at a glance; colour is a quick cue, not the only one (#9).
- **Quiet when all is well.** Healthy rows use small tinted badges and no borders or alarms; only down and degraded things use stronger colour, plus the incident link. Reason: the eye should land on what is wrong (#9).
- **The Bleep tokens live in `app/globals.css`: `--bg`, `--surface`, `--soft`, `--line`, `--ink`, `--ink-2`, `--accent`, `--accent-ink`, `--ok`/`--warn`/`--down`/`--stop` with their `-bg` tints, and Bleep's `--blob`, `--hand`, `--cup`, `--screen`,** each with a light value in `:root` and a dark one in `.dark`, and a Tailwind utility of the same name (`bg-surface`, `text-ink-2`, `border-line`, `bg-ok-bg`). The older names stay as aliases onto them, and components still use them: `background`=bg, `foreground`=ink, `card`=surface, `muted`=soft, `muted-foreground`=ink-2, `border` and `input`=line, `primary` and `ring`=accent, `health-ok`/`degraded`/`down`/`stopped`/`unknown` = ok/warn/down/stop/stop, each with a `-bg` tint. Reason: new code uses the token names, and no component had to change at once. One catch: shadcn's `accent` was a hover tint and is now the brand colour, so the hover on list rows and the ghost button use `soft` instead (#90).
- **Dark tints are `color-mix` of the text colour (13 to 14%) over `surface`, not a second hex.** Reason: the spec defines them as "the colour at 13%"; mixing keeps that rule in one place, and the contrast test resolves it (#90).
- **A test checks the contrast of the colour pairs in the design from `globals.css` itself** (`lib/contrast.test.ts`): ink, ink-2, accent and the four health colours on `surface`, `bg` and `soft`, each health colour on its own tint, and `accent-ink` on `accent`, in both themes, at least 4.5:1. Reason: parsing the stylesheet keeps one source of truth for the values, so a colour tweak that breaks readability fails the build instead of shipping (#90).
- **Nunito (400 to 800) is the sans font and JetBrains Mono (400, 500) the mono font, both through `next/font/google`** as `--font-nunito` and `--font-jetbrains-mono`; `font-mono` is for names, ids and URLs and is not used bold. Reason: same loading path as the fonts before it, so the build needs the network exactly as it did (#90).
- **Shapes: `rounded-card` (28 px) and `rounded-card-sm` (22 px, phone) for cards, `rounded-row` (20 px) for rows inside them, `rounded-field` (14 px) for inputs; buttons, badges and pills are `rounded-full`.** `Button` is 44 px tall (`sm` is 36 px with a fine pointer and 44 px on a touch screen), `Input` 44 px. `Panel` takes `awaitingYou` for the 2 px accent border of the card that waits for the human. Reason: touch targets of at least 44 px, and the awaiting card must stand out without colour alone being its only cue, since its Needs your yes pill and buttons stay (#90).
- **Every enabled button shows the pointer cursor,** from one base rule in `globals.css` (`button:not(:disabled)` and `[role="button"]`). Reason: Tailwind v4's preflight resets buttons to the default arrow, which makes them look inert (#218).
- **Every page has its three states, and keyboard focus is always visible.** Each page shows a loading line (`role="status"`) until its first read answers, an alert in the existing voice ("Could not load the incident: ...") when it fails, and an empty text that says what will show up here. A refresh that fails after a good read keeps the data and adds one line. Names from a host or a label wrap (`wrap-anywhere`, `min-w-0`) so nothing scrolls sideways at 375 px. Focus: `Button` has a 2 px accent ring with a 2 px offset in the page colour, because the "Yes, go ahead" button is itself accent and a flush ring would not show; a base rule in `globals.css` gives every other focusable element a 2 px outline, which the components' own `focus-visible` classes override. A test per page stubs `fetch` for pending, down and empty (`components/page-states.test.tsx`), and the decision bar has a keyboard-only test (Tab to "Yes, go ahead", Enter, one POST). Reason: a dashboard used at 3 a.m. on a phone must say what it is doing when the backend is slow or gone, and an approval that cannot be seen focused cannot be trusted to be the one pressed (#240).
- **An incident waiting for the human reads "Needs your yes";** every other status word is unchanged (#90).
- **Monospace for container names, ids and URLs.** Reason: they are copied into terminals and compared character by character (#9).
- **Theme: system, light or dark, kept across reloads.** The pick lives in `localStorage` (`bleep:theme`); an inline script in `<head>` sets the `dark` class on `<html>` before the first paint, so there is no flash. "System" follows the OS setting live. Every toggle on the page (the app header's and the incident page's own) reads and writes one shared store with one OS-setting listener, so they always agree and a toggle that is hidden never applies a stale "system" over an explicit pick (#207). Reason: reading storage only after hydration would flash the wrong theme on every load (#9).
- **Unit tests mock `fetch`, nothing else.** Vitest with Testing Library and jsdom; the poll and login tests stub the global `fetch`, so no test needs a backend or network. Reason: the dashboard's tests run without a backend (#9).
- **Types are written by hand.** `lib/api-types.ts` follows the API's schemas; `npm run gen:api` would replace the whole file with types generated from the backend's `/openapi.json`, so a new type is added by hand beside the others. The names `HostView`, `ServiceView`, `ContainerView`, `UrlStatus` and `Health` stay (#9).
- **Bleep is one component, `Bleep` in `components/bleep/bleep.tsx`, with a `mood` and a `size` in px** (plus `className`, and `title` for a screen reader; without a title it is decorative, since the state is always written beside it). From 40 px up it draws the full figure of the spec's drawing; below, the head only (no headset, hands or body), for the header logo and the favicon (`app/icon.svg`). The moods are `needs_you`, `not_sure`, `working`, `all_good` and `resting` (`Mood` in `lib/mood.ts`); the per-mood poses are data in `components/bleep/poses.ts`. Reason: every screen shows the same bot by passing a mood, and the screens never draw SVG themselves (#91).
- **Bleep always breathes and blinks; a mood changes its pose, not the drawing.** Breathing is on a group of its own that no mood replaces; each hand sits in a group whose place moves with a transition, inside a group that plays the mood's motion around a fixed point; the eyes are remounted on a new mood and open on the new expression. Motion is CSS keyframes on SVG groups in `bleep.module.css`, with `transform-box: view-box` so each group turns around the drawing's point, and `prefers-reduced-motion: reduce` turns every animation and transition off, leaving the mood's pose. Reason: a mood change should read as the same bot reacting, and motion must be possible to turn off (#91).
- **The moods come from pure functions in `lib/mood.ts`:** `incidentMood(status, unsure)` for an incident's page, `reportMood(outcome)` for a report, `overallMood(incidents, hosts, unsureIds)` for the overview and `overallState(incidents, hosts)` (red, amber, green) for the header; the order is Needs you, Not sure, Working, All good. `paused` counts as Working, since Bleep tries the run again by itself. Reason: one table, tested for every status and outcome, decides the mood on every screen (#91).
- **A failed run keeps the overall state red for 24 hours after it ended** (`FAILED_NEEDS_YOU_MS`), then counts as nothing. Reason: nothing reopens a failed incident, so counting it for ever would leave the header red for good, while a day is long enough for the human to see it (#91).
- **The header's state comes from one poll in the app layout:** `OverallProvider` (`components/overall-state.tsx`) reads `GET /api/incidents?limit=200` and `GET /api/hosts` together every 10 s through `usePoll`, so it pauses while the tab is hidden. Any page inside the layout reads the incidents, hosts and state with `useOverall()` instead of polling the same endpoints again. Until the first read answers, the logo's eyes are grey. Reason: no new endpoint, and one request pair per tick however many parts of the page need the state (#91).
- **The header is the head-only Bleep and "Bleep" as the home link, the nav as one pill group (Home, Incidents, Settings, the active item filled with `ink`), and one round theme button** that steps through system, light and dark. The logo's state is also in the link's title and its screen-reader text. The developer panel is not in the nav; Settings links to it while `GET /api/dev` answers. The header is hidden in print. Reason: the nav lists the pages a human uses on call, and colour is never the only cue (#91).
- **The overview starts with a hero that answers what failed:** Bleep at 132 px (76 px on a phone) in the overall mood, a status tag and one headline, picked in the order of the moods. A plan waiting for the human comes first ("shop is down. I know why, and I have a fix." with the plan in one line and "Show me the plan"), then a run that failed in the last day, then a waiting plan Bleep is unsure of ("I am not sure why, but I have a plan."), then an unreachable host ("I cannot reach coolify-main."), then an incident Bleep works on ("I am on it." with "Follow along"); otherwise "Nothing needs you right now." Each incident's place is the overall mood of that incident alone, so the headline always agrees with Bleep's face; more incidents that need the human are one link under it ("1 more incident needs you"). A plan with nothing to run or one Bleep's own checks refused never reads "I have a fix". Reason: the first second must say what failed and whether the human is needed, and a promise of a fix must be true (#92).
- **The plan line comes from `GET /api/incidents/{id}`, read only for incidents waiting for the human, on the overview's 10 s poll together with `GET /api/services`.** It names each step's verb and target ("I want to start shop-db-1, then restart shop-api-1."), at most two steps and a count of the rest, and says nothing runs until the human says yes. A detail that cannot be read is left out, and the hero shows the incident's title instead. A new waiting incident restarts the poll, so its detail is read at once. Reason: the plan is in the detail, not the list, and there is normally none or one waiting incident (#92).
- **The hero asks `isRefused` (`components/incident/headline.ts`) whether a plan was refused, as the decision bar does,** so a plan refused before the `refused` flag existed never reads "I have a fix". Reason: one rule for a refused plan across the dashboard (#98).
- **The overview takes its incidents and hosts from the shared poll (`useOverall`) and reads only the services and the waiting details itself,** so the hosts and the services may be up to one tick (10 s) apart, where before they were read together. Reason: one request pair per tick for the header and the page, and a service's row and its host's tile catch up on the next tick (#92).
- **"Your hosts" is one tile per host, with its services as rows (name linking to the service's page, an "Incident" link while one is open, and the health pill) and its basics in mono** (load, memory used, the fullest disk; "last seen" and the error when unreachable). A host that is unreachable, down or degraded is tinted `down` with a `down` border, unless it is quiet (see Quiet services and hosts, #221). The line above says how far a problem reaches: "Only Demo stack is hurting: 1 of its 3 services. The other two are fine.", "coolify-main is out of reach as a whole.", or "All three are fine." Containers and URLs moved to the service's page. Reason: at a glance the eye lands on the one tinted tile, and the words say whether it is one service, a whole host or several hosts (#92).
- **A round + at the right end of the "Your hosts" row opens the add-host form in a dialog;** the empty state offers the same dialog next to `config/hosts.yaml`. It is the settings page's `HostForm` with the same "only SSH hosts" note, under its own save lock: Esc, the backdrop and the close button do nothing while the save is in flight, the form unmounts when the dialog closes so a typed key does not outlive it, and a save calls `refresh()` on both polls (`usePoll` reads at once and restarts its interval) so the new tile shows without waiting up to 10 s. Reason: adding a host is the first thing on an empty overview and should not need a trip to Settings (#218). Under the key box the add form recommends a new key just for Bleep, with the `ssh-keygen` line on its own and where its `.pub` goes, and says a key with a passphrase is not supported. Reason: a pasted personal key hands Bleep every server that key opens; a key of its own is revoked by deleting one line in `authorized_keys` (#218).
- **Dialogs are shadcn's Dialog in the "base-nova" style on Base UI (`@base-ui/react`), copied into `components/ui/dialog.tsx` and styled with the Bleep tokens** (`surface` card, `rounded-card`, a black 40% scrim in both themes). Reason: focus trap and return, scroll lock, Esc and backdrop dismissal and exit animations are easy to get subtly wrong by hand, and `components.json` already chose this style; the code is ours to restyle (#218).
- **"Fixed themselves" restyles the recoveries as rows: the container in mono, linked to its service's page when the recovery names one, its host, the time and the explanation as it comes.** Reason: a recovery is a quiet "this happened", one click from the service it belongs to (#92).
- **An incident's page reads as one story** (`components/incident/incident-page.tsx`): a hero with Bleep at 112 px in the incident's mood (`incidentMood`), a headline for the moment, the incident's title, its subject, time and cost, and the status pill; then the progress bar; then, in the main column, the report when there is one, the plan with the decision bar, "What I found" and "How I got there", with the timeline beside them. The plan card has the 2 px accent border only while its approval waits. Reason: the page answers what happened, what Bleep wants and what is left for the human, in that order (#94).
- **The headline comes from the status alone** (`headline()` in `components/incident/headline.ts`): "shop is in trouble. Can I fix it?" while a plan waits (a not-sure variant for an unsure diagnosis, and no question for a refused plan), "I am looking into it.", "On it.", "Almost there.", "Fixed and checked." only for `resolved`, and a line per outcome for `closed`. It names a Compose project or container by its own name, a host as "Host demo", and a service id it cannot read (a Coolify uuid) as "This service". The name is shown in mono, with characters that draw nothing marked and cut at 40 characters, since it comes from a label anyone starting a container can set. Reason: the page must never say fixed before the checks passed, a uuid is no name to put in a sentence, and host text must not pass as Bleep's own words (#94).
- **The progress bar (Gather, Investigate, Diagnose, Plan, Your yes, Fix, Check, Report) is computed from the `node_started` and `node_finished` events** (`progressSteps()`): a step is done once its node finished, the running node is current, and a node that starts again clears the steps from there on (a failed check sends the run back to Investigate). Fix is red with a cross when a step of the plan failed, and Check is red with a cross unless its last check passed, so an `unverified` or `budget` end never shows green there; a no on Your yes is grey with a cross. Steps that never ran stay grey, a `failed` incident marks in red, with a cross, the step it stopped at (none while its history is still loading), and `closed` or `resolved` shows the report done. Each segment also says its state to a screen reader. Reason: the same events the timeline reads, so the bar never disagrees with it; a step the run has not reached again is never shown done, and a fix nobody confirmed never looks like one that was (#94).
- **A running plan shows each step's progress and then the checks as pills,** from the `action` and `verification` events since the last `proposal` (`planRun()`): a step's number turns into a spinner, then a check (a cross when it failed, a dash when skipped), and while Verify runs the planned targets show as "checking" pills until the latest check's results replace them. Reason: what Bleep does to a host must be visible as it happens, and events of an earlier plan must not show on a new one (#94).
- **"How I got there" says each tool call as a plain sentence** ("I read a container's logs") with the tool's name and time in mono beside it, the arguments in mono under it, and the result folded; a tool the dashboard has no sentence for shows its name. The sentences never quote the arguments. Reason: the model chose the arguments, possibly from a hostile log, and they must stay visibly data, never read as Bleep's own words (#94).
- **The timeline has a coloured dot per line:** red for what opened the incident, for "Waiting for your answer" and for a failed step, amber while something runs, accent for the human's answer, green for a passed check, a done step and Resolved; the words say the same. With the incident it starts with the incident's title and ends with how it ended; once it ended nothing shows as running, and the wait for the human stops running as soon as the answer arrives. Reason: the colour finds the line, the words carry the meaning (#94).
- **The decision bar reads "Yes, go ahead", "No, leave it" and "Tell Bleep something"** ("Let it go" for a refused plan, which still has no yes). A plan counts as refused by `isRefused()`, which also knows a refused plan stored before the `refused` flag by its text, so the bar, the card and the headline agree; such a plan has no steps. Otherwise only the words and the look changed; every rule of the bar under "Incident pages" below holds (#94).
- **Below the desktop breakpoint (1024 px) an incident's page is the phone layout,** chosen with `usePhone()` (a `matchMedia` query) rather than by hiding a second copy with CSS: a small header (back, subject and time, theme), Bleep at 76 px beside the status pill and the headline, the report when there is one, "What I found" in short, the plan, and "How I got there" and the timeline folded; the progress bar is left out. Both layouts are one tree with the plan card at the same place in it, so crossing the breakpoint (a tablet turned) moves the decision bar rather than mounting a new one. Reason: one decision bar and one copy of each text in the page, and an answer in flight, the lock after it and a typed instruction survive a turn; the page draws only after the incident's first read, after hydration, so nothing flashes (#95).
- **"What I found" and the plan swap places across the breakpoint as keyed siblings,** so crossing it moves both panels instead of mounting new ones, and a feedback note being typed or a vote in flight survives a turned tablet like the decision bar does. Reason: before, the panel sat in a different slot per layout and remounted, losing the draft (#208).
- **On an incident's page below the desktop breakpoint the app's header is hidden** (`AppHeader`, `max-lg:hidden` on `/incidents/<id>` only), since the page's small header has the way back and the theme button. Every other page, and every page on a desktop, keeps the app's header. Reason: on a phone nothing else competes with the plan and its bar (#95).
- **The root layout's viewport is `viewport-fit=cover`,** and the body pads by the left and right safe-area insets. Reason: without it iOS reports every `env(safe-area-inset-*)` as 0, and the pinned bar would sit on the home indicator (#95).
- **On a phone, "What I found" is the cause's first two sentences,** with the rest, the evidence and the affected services folded under "More"; the unsure banner stays. A sentence ends at a stop followed by a space, so "1.2.3" or "db:5432." stay whole. Reason: the plan must come soon on a small screen, without hiding what the human may want to read before a yes (#95).
- **The phone's decision bar is the same `DecisionBar` with `pinned`:** fixed to the bottom of the screen and padded by the safe-area insets (at least 16 px), a region named "Your answer", "Yes, go ahead" full width at 56 px, "No, leave it" and "Tell Bleep" side by side at 48 px (its name stays "Tell Bleep something"). "Tell Bleep" opens the instruction box inside the bar, focused, with 16 px text so iOS does not zoom, and the bar rises by the on-screen keyboard's height (read from `visualViewport`), so Send stays in view. Reason: the rules live in one component, and a bar fixed to the bottom otherwise stays behind the keyboard on iOS and Chrome for Android (#95).
- **After an answer the bar says, in one line, who answered, where, when and what it led to:** "You said yes on the dashboard, …" then "Running the plan.", "Checking it worked." or "Fixed and checked." (only once resolved); "You said no on Telegram, … Nothing ran." ("This plan did not run." unless the history has loaded and shows no step of any plan ran); "You let it go …" for a refused plan; "You told me …: “…”. I am planning again." On a phone the buttons go and only this line, or the 409 message, stays, and focus moves to it when the answer was given there; on a desktop the locked buttons stay above it. Reason: one-handed, the answer and its effect are all there is to read; "Nothing ran" must not be said of an incident where something did (#95).

### Incident pages (#23)

The incident list (`/incidents`), one incident's page (`/incidents/[id]`) and the recoveries on the overview (`frontend/components/incident/`, `components/overview/recoveries.tsx`, `lib/use-incident-stream.ts`).

- **The live stream is a route handler, not the rewrite.** `app/api/stream/route.ts` pipes the backend's `/api/stream` with `Cache-Control: no-cache, no-transform`, forwarding only the cookie, `Last-Event-ID` and `Accept`. Through the rewrite, Next gzips `text/event-stream` and held every event until the stream ended, under `next start` and the standalone server alike. `next.config.ts` inlines `BACKEND_URL` for the handler at build time, the same build argument as the rewrite. Reason: a live view that shows nothing until the incident ends is not live ([evidence](../decisions/sse-through-next.md)) (#23).
- **`useIncidentStream(id)` reads the history, then streams after its last seq.** It loads `/events`, then opens `EventSource` with `after=<last seq>`. A dropped connection is retried by the browser with `Last-Event-ID`; a stream the browser gives up on (a 401, 404 or 5xx closes it) is reopened after 5 s by reading the history again from the last seq, through `apiFetch`, so a lost session goes to the login page. Every event is kept once by seq (`mergeEvents`), however the replays overlap. Reason: the backend's replay and the page's own history read can both send an event twice, and nothing may be shown twice or lost (#23).
- **The page reloads the incident when a step event arrives, not on tool events.** Diagnose publishes no event of its own and the findings live in the run's checkpoint, so every event except `tool_call` and `tool_result` (`node_finished`, `proposal`, `approval_requested`, `decision`, a notice) reads `GET /api/incidents/{id}` again; the newest read wins. It is also read every 10 s while the tab is visible, because the runner sets the status after the run's last event (Awaiting approval, Resolved) and publishes nothing for it. Reason: one read per step keeps the cards in step with the run, a long investigation does not cause a read per tool call, and the slow poll catches what has no event (#23).
- **"How I got there" (live reasoning) is the tool calls, each with its arguments and its result folded under it.** A result is matched to the oldest open call of the same tool. Only the result's size and first line are on the bus, so that is what the fold shows. Reason: what the model looked at is the part a human checks; the full output stays with the run and its guard (#23).
- **The timeline merges a node's start and finish into one line** ("Investigating", then "Investigated") and lists the question, the answer with its channel, and notices. Reason: a list of raw start and finish events doubles its length and says less (#23). Each step of a plan gets a line per status change (`docker.start shop-web-1: started`, then `done`, `failed` or `skipped`, red when failed) and each verification check one ("Check 1 failed", amber, "Check 2 passed"). Reason: what Bleep did to a host must be visible as it happens, not only in the report (#25).
- **An unsure diagnosis carries an "I am not sure" banner** above the cause, in amber with its own icon. Reason: a plan built on a guess must not look as solid as one built on evidence (#23).
- **The proposal card shows the plan the pending approval put to the human, and the decision bar sends that approval's id.** When the run holds a newer plan than a decided approval (after an instruction), the card shows the newer plan and one line for the earlier answer. Reason: the human approves what is on the screen, and the backend refuses a decision for a plan that was replaced (#21, #23).
- **A step's params keep their line breaks on the proposal card** (`whitespace-pre-wrap` on each `key=value`), so `node server.js` and `rm -rf /data` on two lines of a `set_env` value read as two commands, as Telegram's `⏎` shows them, not as arguments to `node`. Reason: the human must read a param as it runs; the plan check refuses what redaction would hide, but a line break is shown, not hidden. Since breaks are kept, the plan check refuses padding that would push the rest of a param out of sight (more than two line breaks in a row, 16 blanks in a row, over 30 lines), so the decision bar pinned on a phone cannot sit over a value whose end is far below ([guard](guard.md#plan-check), #294).
- **After any answer the buttons lock and the outcome stays on screen.** A 409 shows its message ("Already decided on Telegram") and locks too; any other error keeps the buttons, so the human can try again. A decision made on another channel shows as decided, with who and when. The bar is keyed by the approval id, so a new plan gets fresh buttons. Reason: a second click must not look like it might count, and the loser of a race must know who won (#23).
- **An incident that ended shows no decision bar for a plan nobody answered.** The card shows that plan with one line, "Closed before you answered. This plan did not run.", the panel is "My plan" without the accent border, and a phone pins nothing. It goes by the incident's status as well as the approval's (`awaitsAnswer` in `components/incident/proposal-card.tsx`), so an approval still `pending` under a resolved, closed or failed incident gets no buttons either. A plan answered before the end keeps its locked bar and its answer line. Reason: the backend refuses any decision on a finished incident, so live buttons there offered a choice that did not exist (#277).
- **Bleep's own advice in a plan gets its own block.** `human_instructions` is Bleep's text to the human, so the card shows it at normal weight under "What to do" (the fix to make for a no-action plan, such as the setting to change and the command that applies it) or "Why nothing will run" (Bleep's checks refused the plan twice). The human's own instructions stay on the timeline and in the "Earlier plan answered with an instruction" line. Reason: for a no-action incident that text is the one actionable output, and it must not read as an echo of something the human said (#72).
- **"Tell Bleep something" is the instruction.** It opens a text box (2,000 characters at most, empty is refused) and says that nothing runs until a plan is approved. Reason: an instruction leads to a new plan, never to an action (#23).
- **A plan Bleep's own checks refused has no "Yes, go ahead".** The decision bar shows "Tell Bleep something" (the instruction, which Bleep plans again with) and "Let it go" (a reject), and the card says why nothing will run. Reason: nothing can run from a refused plan, so offering a yes would only be refused (#113).
- **An incident's status uses the health colours:** red when it waits for a human or failed, amber while Bleep works, green when resolved, grey when closed; each with its word and icon. Reason: the same visual language as the overview, where red means "needs someone" (#23).
- **The report sits on top of the incident's page once the run has written it** (`components/incident/report-view.tsx`): the outcome line, the summary, the cause, the action ("Nothing ran."), the decision ("You were not asked."), the follow-ups and the report's own timeline. The outcome is green only for `resolved`, amber for `unverified` and `budget`, grey otherwise (`replan_limit` included, #25). Reason: how it ended is the first thing a human looks for, and an action nobody confirmed must not look like good news (#27).
- **Every diagnosis and plan asks "Was this right?" with Right and Wrong buttons** (`components/incident/feedback.tsx`) once the run has it. A vote is sent at once and shown pressed; "Add a note" opens a box whose text goes with the next vote; a failure says so and keeps the buttons. The service in the incident's header links to the service's page. Reason: one click is all a human gives in the middle of an outage, and the note is there when they have more to say (#30).
- **Recoveries go on the overview, the 10 newest, polled every 30 s,** with the container, host, time and the one-line explanation. Reason: a self-recovery is not an incident, but a container that keeps recovering is worth a glance (#14, #23).
- **The report is a document card** (`ReportView`): Bleep (72 px) in `reportMood(outcome)`, the outcome pill, the title, the subject, times and cost in mono (when the page passes the `incident`), then "In short", "Why it happened", "What I did", "Your decision", "Timeline" and "Follow-ups" under small-caps labels. The text is the backend's, unchanged; the dashboard adds only the labels, a check, cross or dash before the action (read from the action line's `: failed` ending, never rewriting it), and "Nothing ran." / "You were not asked." for the empty cases. The pill is green only for `resolved`, amber for `unverified` and `budget`, grey otherwise, each with its own icon. Reason: how it ended comes first, and an action nobody confirmed must not look like good news (#96).
- **The incident page shows the report card on its own, not inside a panel, and passes it the incident** for the subject, times and cost. Reason: the card is its own surface, and a card inside a card reads as two things (#98).
- **For a `no_action` report the follow-ups are shown as "What you can do" in a `soft` block.** The report has no separate field for Bleep's advice, and for a no-action run the follow-ups are that advice. Reason: it is the one actionable part of such a report (#96).
- **A report prints on white without the navigation.** The header carries `print:hidden`; the card pins its colour tokens to their light values for print and hides Bleep and the feedback bar. Reason: a report is pasted into a ticket or kept as PDF, and a dark page prints as light text on white (#96).
- **Right and Wrong are round buttons that take the tint of the vote when pressed** (green, red), keeping `aria-pressed` and the note box. Reason: colour is a second cue next to the pressed state and the written confirmation (#96).
- **The report's "What I did" has one row per step, split on the backend's `"; "`.** `action_taken` in `graph/nodes/report.py` joins every step as `<action> <target> on <host>: <status>`; the dashboard splits on that and shows each step verbatim with a check for `: done`, a cross for `: failed` and `: refused`, and a dash for `: skipped` or anything else, never a check unless it says done. Reason: a run that failed its first step and skipped the rest must not end in a check that makes the fix look done (#96).
- **An incident `waiting` for its host shows "Waiting for the host" (amber) and the headline "The host does not answer. I wait for it to come back."**; it counts as one Bleep is on, in the list's "I am on it" group and in the mood. Reason: it is open and watched, but there is nothing for the human to do and no plan is coming (#85).
- **"This is expected" sits beside "I'm on it" when the incident detail's `expectation` is set, with that sentence under it** (what it would record: a job's clean exit, or that a host may sleep). The sentence names containers and hosts, so it wraps anywhere inside a `min-w-0` column, as the headlines do (#237). A press posts `POST /api/incidents/{id}/expected`, then the page and the header read again; a 409 (a yes on another channel won, or it is no longer offered) is shown in the API's words. The timeline shows the `expected` event's sentence with a green dot. Reason: teaching Bleep that something is normal must be one press where the incident is, and the person must see what it records before pressing (#257).

### Service page (#30)

One service's page (`/services/[id]`, `components/service/`), reached from the service's name on the overview and from an incident's header.

- **The page shows the service's containers and URLs, its rules, its memory and its past incidents.** Rules come in two groups, the service's own and its host's, as they are in force (the hosts file's, with the dashboard's over them); past incidents are the 20 newest. Reason: before a human approves a plan, what Bleep already knows and has been told about the service is one click away (#30).
- **Memory is a list of facts, each with where it came from, and a box to add one.** A person's fact reads "Added by you"; a report's reads "Learned from an incident's report" and links that incident. Each has a delete button; a failed add or delete keeps the list and says why. Reason: a fact Bleep learned is trusted on every later incident, so the human must see where it came from and be able to remove it (#30).
- **A service Bleep does not see any more still shows its memory and incidents,** with one line saying it is gone from its host. Reason: the facts of a removed or renamed service should be readable and deletable, not stranded (#30).
- **The page's parts are small and take their data as props** (`FactList`, `RuleList`, the shared `Panel`), with the reads in `MemoryPanel`, `ServicePage` and `useServiceSettings` (`components/service/settings-cards.tsx`). Reason: a new look should not have to touch the data code (#30).
- **The service page speaks as Bleep and is ordered by what a human reads first (#97).** Headline is the service name with its health pill, then one line (source, host id, container count, and "healthy since" when it is healthy, #233); cards are "What I know about <name>", "Checked from outside" (each URL with status, code, latency and the strip of its recent checks), "Containers", "Rules I follow" and "Past incidents". Reason: the page answers "how has this service been doing" in the order a person asks it, in Bleep's voice.
- **"Healthy since" shows only when the service is `ok` and the API gives `health_since`,** as the time today ("9:05"), "yesterday 9:05", the weekday within a week, else the date (`formatSince` in `lib/format.ts`), with the full date and time on hover. A degraded or down service, or one the watcher has not judged yet, gets nothing new on the line. Reason: the line answers "how long has it been fine"; for an unhealthy service the incident says more, and a guessed time would be wrong (#233).
- **Each URL's recent checks are a strip of ticks under its last check, oldest left** (`CheckStrip`, `components/service/check-strip.tsx`): green (`ok`) for a passed check, red (`down`) and taller for a failed one, so a failure does not rely on colour alone. Only one tick is in the tab order (the newest at first); the arrow keys, Home and End move along the strip. The line under the strip says the hovered or focused tick's time, status code and latency, and the summary otherwise. Ticks shrink to 3 px with 3 px gaps, so 30 fit a phone's width. A URL with no checks yet has no strip. Reason: the strip answers "has it been flapping" at a glance; a line under it instead of a floating tooltip also works on a tap, and one tab stop per strip keeps 30 ticks from flooding the tab order (#233).
- **Past incidents show the human's right or wrong** for the diagnosis and the plan as small pills ("Diagnosis right", "Plan wrong", with a thumb), only for the votes there are, from `votes` on the incident list. Reason: whether Bleep was right before is part of how the service has been doing, and the note stays on the incident's page (#233).
- **"I never change anything without your yes." is always the last line of "Rules I follow",** also when the service has no rules of its own, and the card is hidden for a service gone from its host unless it still has settings. Reason: it is a fixed guarantee, not data from the hosts file (#97).
- **The service's URLs, rules and protected containers are edited on its page (#228).** "Checked from outside" lists the URLs in force, each with its last check (a URL just added shows "Not checked yet"); "Rules I follow" shows the service's own rules and its host's; "Containers" gains "Protected", with the hosts file's locked and the dashboard's as plain badges. Each card shows what is in force with an "Edit" button that opens the settings page's editor in its place (`UrlEditor`, `ListEditor`); Cancel or a save that goes through closes it, a refusal keeps it open with the reason. The host's rules are edited on the host's page. Reason: a service's settings belong where the service is, as a host's do (#227), and showing the checks and the editor at once would list every URL twice (#228).
- **The settings come from `GET /api/settings`, and a save goes through `PUT /api/settings` as the host's overrides with only that service's field replaced,** with the same `version` check, save lock (`SaveLockProvider` around the page) and stale notice as the host page (`useStaleSaving`). A service the hosts file names by its name (`shop`, not `compose:shop`) is found and saved under that name, as discovery matches it. When the settings cannot be read, the cards show what the service's own read gave and no Edit button. Reason: no new endpoint is needed, and a save under the other key would hide the hosts file's entry for the service (#228).
- **A service Bleep does not see any more but that has settings, under its key or the name in its id (`shop` for `m1/compose:shop`), shows its cards and can still be edited;** one without settings shows only its memory and incidents. The host page links a name-keyed one as `m1/shop`, where its settings are but not the memory and incidents kept under its full id, which Bleep cannot know once the service is gone. Reason: the settings of a stopped or renamed service must be reachable to change or clear them (#228).
- **The page draws its container and URL rows itself instead of reusing the overview's chips,** and its past incidents as rows with the shared status badge. Reason: the page needs one row per line, which the overview's inline chips do not give, and the overview is restyled in its own issue (#97).
- **"Expected to exit" lists the service's jobs under its containers, after the protected ones, and is edited as a list** (a container name, a Compose service name or `*`), saved as the service's `exits`, which replaces the hosts file's, with "Use the hosts file's" once changed. A finished job's health reads "Done" (double check, the `stopped` tone) wherever health shows, and a `done` service never tints its host. A toggle per container row was left out: the list covers a `compose run --rm` job whose rows never stay, which a toggle cannot. Reason: the jobs of a service are set where the service is (#257).

### Quiet services and hosts (#221)

- **A quiet service shows a grey pill in place of its health.** "Left alone", "Snoozed until 18:00" (with "tomorrow" or a weekday when it ends on another day) and "Host left alone" when the host's state is the reason. Reason: the real health stays in the API, and the dashboard decides how to show it, so a person can tell "quiet" from "fine" (#221).
- **The moon sits on service rows and host tiles.** On a service row it appears on hover and focus with a fine pointer and is always visible on touch; on a host tile it is always visible, because a tile's header has room for it. Reason: it is rare to want it, so a row keeps it out of the way on a desktop, but a touch screen has no hover to reveal it (#221).
- **The moon, the grey quiet pill and the service page's "Quiet" button are as tall as the health badge beside them (28 px, a 14 px icon), not 44 px buttons;** a touch screen gets a 44 px tap area around it. Reason: a full-size round button next to every row outweighed the badges it sits with (#225).
- **The menu is Base UI's menu from the shadcn base-nova set,** the same set as the dialog. Reason: it brings keyboard and focus handling that is not rebuilt by hand (#218, #221).
- **"Until tomorrow 8:00" means the next 08:00 in the browser's local time after the choice, and the menu says "Until 8:00" before 08:00.** Reason: at 02:00 "tomorrow" would skip the morning the person means (#221).
- **On the service page one control carries the quiet state.** Not quiet: the health badge and a badge-sized "Quiet" button beside the title. Quiet: the grey pill ("Left alone", "Snoozed until 18:00", "Host left alone") takes the badge's place and is itself the button; its menu holds "Watch again" (for the service's own quiet) and the other choices. One plain line under the title says why and since or until when ("Since Mon 14:02 Bleep opens no incidents for it.", "Bleep opens no incidents for it until 18:00.", "Its host is left alone, so Bleep opens no incidents for it."). Reason: a tag, a button and a banner with its own bigger button said the same thing three times at three sizes (#225).
- **An open incident's page has "I'm on it" as its own right-aligned row under the hero, with the same menu,** for incidents that are open, investigating, awaiting approval, paused or waiting for their host, and not while executing or verifying or once finished; it targets the service, or the host (named by its display name) for a host incident, and is not offered for a service incident that names no service. The menu's first line says what it silences: "Snooze shop". After a choice the page and the header read again and the page shows the closing notice. Reason: the decision bar exists only for a pending approval and is pinned on phones, while "I'm on it" applies to every unfinished incident, so it cannot live there; a run that is changing a host must not be cut short, and a finished incident has nothing left to silence (#221).
- **The mood and "Needs you" leave out the failed runs of quiet subjects.** Reason: a quiet service must not make Bleep look worried (#221).
- **A quiet host, or one whose only hurting services are quiet, is not tinted, the reach line counts it as fine, its unreachable error is not printed in red, and the hero does not headline an unreachable quiet host.** Reason: quiet must never make the overview look worried (#221).
- **An asleep host is treated the same way:** not tinted, counted as fine, its error not in red, never the hero's headline, and it does not turn Bleep's mood to working; its services' rows say "Asleep", not "Down". Reason: a host that may sleep was marked so that its sleep is no trouble (#85).

### Settings page (#41)

The settings page (`/settings`, `components/settings/`). What it may change and how a save is built is in [settings](settings.md).

- **A failed read of the services Bleep sees is shown as an alert in the host page's "Services" panel**, which then links only the services with settings of their own, without "Not seen now". Reason: a host with no services listed would otherwise look empty rather than unread (#41, moved to the host page in #227 and #228).
- **A "Hosts" panel lists each host as a link to its page (with whether it comes from `config/hosts.yaml` or the dashboard) and holds "Add an SSH host", then thresholds, plugins, secrets, Telegram and models.** A host's connection and rules are edited on its page, and its services' settings on each service's page, not here. Reason: one panel per host made the page long and unclear with a few hosts and services; Settings keeps what is Bleep-wide (#41, #227). The pages use the existing look (`Panel`, `Badge`, `Button`, `Input`, the health colours for "set" and "missing"). Reason: the dashboard is being restyled separately, so this page adds no style of its own (#41).
- **Every list is edited as a draft and saved as a whole, with Save and Cancel shown only once something changed** (on the service page, where an editor is opened with "Edit", Cancel is always shown and closes it). Each editor is keyed by the values it was built from, so a save that returns new values starts a fresh draft. Reason: one save per list matches one override per list, and a form that always shows Save invites saving nothing (#41).
- **A plugin's form is built from its `settings_schema`**: a text input for a string, a decimal input for a number, a checkbox for a boolean, a box with one entry per line for a list of strings; any other type is shown read-only. An empty field is left out, so the plugin's default holds and shows as the placeholder; a checkbox shows its default until the plugin has settings, and an untouched one sends that default, never `false`. A field typed as a secret gets no input at all. Switching on and saving the settings are separate requests, each showing the API's refusal ("needs COOLIFY_TOKEN set in the environment first"). Reason: a plugin author adds settings without touching the dashboard (#41).
- **Dashboard SSH hosts are added on the settings page and the overview, and edited and removed on their host page (#194, #213, #227).** The "Hosts" panel says only SSH hosts go there and that socket and loopback hosts go in `config/hosts.yaml`; a hosts-file host shows "From config/hosts.yaml" with no Edit or Remove. The key is a write-only textarea (autocomplete and spellcheck off) that is emptied once the save goes through and never filled from anything the API sends; a dashboard host shows "Key: set/missing" and "Host key: set/missing". "Check the host key" shows the offered fingerprint in mono with the `ssh-keygen -lf` line, and Save stays disabled until the human ticks that it matches; the confirmation is dropped when the address or port moves, and on a timer when the offer is ten minutes old. The fetch's single generic error and the busy 429 are shown as the API words them. An edit that moves address, port or user says it clears the key; saves and removals send the host's `version` in `If-Match`, and a 409 that carries a version reads the settings again and says "This host changed since this page read it; reload the page." Removal is an inline second click ("Remove", then "Yes, remove this host") that says the host's open incidents are closed with a notice, never a browser `confirm()`. Reason: the key and the fingerprint are the safety of this form, and an inline step is testable and does not depend on the browser's dialogs (#213).
- **Secrets, plugin addresses and tokens are set and cleared on the settings page from `GET /api/secrets` (#202).** One row per name (`SecretField`): its env name, set or missing, where it is kept, and an input with a Save/Replace and a Clear button. A plugin's card holds its own address and token; every other secret is in a Secrets panel. A secret's input is `type=password` with `autocomplete=off`, an address's is plain text; the input is empty on every render, even for a value that is set, and emptied once the save goes through, and the page keeps only the list the API answers, which holds no value. A failed save keeps what was typed and shows the API's reason under the field. A value the env sets shows "Set in .env, which wins" with no input or button (the API would answer 409). An address says it clears its token and switches the plugin off; a token has no input until its address is set on the dashboard, and is sent with the address's `version` (a 409 reads the list again, drops the typed token and says the address changed). An address the API now refuses (`invalid`, a hand-edited file) shows "Set, but not valid: enter it again" with the usual controls. After a save the plugins and the Telegram status are read again, so a plugin switched off by a new address shows as off. Reason: the page is the way in for people with no `.env` access, and a value that is shown, prefilled or kept in state would defeat a write-only store (#202).

### Incident list (#93)

- **The list is grouped "Needs you" (`awaiting_approval`, and a `failed` run for a day after it ended), "I am on it" (`open`, `investigating`, `paused`, `waiting`, `executing`, `verifying`) and "Earlier" (`resolved`, `closed`, an older `failed`).** The mapping is a `Record` over every status, so a new status fails the type check until it is placed, and a test puts each status in exactly one group. A failed run counts for the same day as in Bleep's mood (`failedRecently`, `FAILED_NEEDS_YOU_MS` in `lib/mood.ts`), so the list, the overview and the header never disagree about what needs the human; it also stays under the "Closed or failed" chip. Reason: the first group is what is blocked on the human, and a run Bleep could not finish is, until someone has looked (#93, #209).
- **Filter chips and the search box work on the incidents already loaded.** All, Needs you (the first group), Open (the second group), Resolved, and Closed or failed; the search matches the title and the subject text, ignoring case. Reason: the list holds at most 50 incidents, so a server query adds a request for nothing (#93).
- **A row shows the status pill, title, subject in mono, opened time and, once closed, the duration.** A running incident shows no duration rather than one that goes stale between polls. A row waiting for the human has a 2 px `down` border. There is no one-line outcome because `Incident` has no summary (#93).
- **A group of repeats is one row, with "Seen N times"** (`foldRepeats`; the list is newest first and each item carries `repeats`): its newest incident that needs the human when one does, so the group sits in "Needs you" and a yes is never folded away, else its newest. On an incident's page the group's first incident shows "Seen N times · last <time>" with its repeats listed (`GET /api/incidents?fold_of=<id>`, each with its status and time), and a repeat says how many times it happened in all and links the first time. The fold window is a threshold on the settings page ("A repeat within this time joins its group", in hours, 0 never). Reason: one subject that breaks every morning must read as one thing with a count (#259).
