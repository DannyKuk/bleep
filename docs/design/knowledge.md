# Knowledge search

How the agent looks things up (`backend/src/bleep/knowledge/`, `tools/knowledge.py`): agentic RAG over a curated snapshot of the Docker docs, the README and `docs/` of each service's linked GitHub repo, and past incident reports (spec §4.5, §7). Investigate calls `knowledge_search` when it decides to; nothing is put in the prompt up front.

| Piece | Path | What it does |
|---|---|---|
| **Snapshot** | `backend/knowledge/docker-docs/`, `scripts/fetch_docker_docs.py` | 27 Docker and Compose doc pages from docker/docs (Apache-2.0), each with `source_url`, `source_path`, `commit`, `fetched` and `license` in its front matter. The script refreshes them. |
| **Chunking** | `knowledge/chunking.py` | `chunk_markdown(text, max_tokens=300, overlap=50) -> list[Chunk(heading_path, text)]`. |
| **Index** | `knowledge/index.py`, migration `0014_knowledge.sql` | `KnowledgeIndex`: `ingest`, `sync`, `search(query, k=5, sources)`, in the `knowledge_documents` and `knowledge_chunks` tables; `last_refresh` and `mark_refresh` in `knowledge_refreshes`. |
| **Sources and refresh** | `knowledge/ingest.py` | `load_snapshot`, `incident_document` (from `MemoryStore.all_records`), `repo_documents` (from a `RepoDocs`), and `KnowledgeRefresher`, the loop the app runs. |
| **Repo docs** | `knowledge/repos.py` | `GithubRepoDocs`, the `RepoDocs` the app runs: linked repos from the hosts file, read with the GitHub client (`hosts/github.py`). |
| **Tool** | `tools/knowledge.py` | `knowledge_search(query, sources?)`, a read tool, offered whenever the app has the index. |
| **Retrieval check** | `backend/evals/knowledge.py`, `backend/evals/knowledge/questions.yaml` | 20 questions with their expected page, hit@k with the real embedder ([report](../evals/knowledge-2026-11-03.md)). |

## Choices

- **The Docker docs are a shipped snapshot, not fetched at run time.** About 25 pages chosen for what breaks on a Docker host: restart policies, memory limits and the OOM killer, exit codes, health checks, logging and the daemon's logs, live restore, networking and published ports, volumes, bind mounts and tmpfs, pruning and `docker system df`, Compose startup order, networking, environment variables and the `services` and `deploy` reference, `docker events` and `docker logs`. Reason: search works offline and the same on every install, and the pages Bleep reads are reviewed in the repo. Docker's docs are Apache-2.0, so the licence ships next to them (#39).
- **The fetch script reads one docker/docs commit and records it in every page.** It resolves Hugo includes, drops other shortcodes, keeps link text without targets, keeps only listed sections of the three long references, and builds the CLI pages from their YAML data. Reason: a refresh is reproducible and the diff shows what changed upstream; link targets and shortcodes are tokens that tell the model nothing (#39).
- **Chunks are cut at headings, then at 300 estimated tokens with 50 of overlap, and embedded with the page title and the headings above them.** Search returns the best chunk of each of the 5 closest pages. Reason: on the retrieval check, 300 put the right page first for 20 of 20 questions where 400 did for 18, and stays under the model's 512 tokens ([knowledge chunks](../decisions/knowledge-chunks.md)) (#39).
- **Tokens are estimated, not counted with the model's tokenizer:** a run of letters is one token, digits count in threes, and every mark (underscores too) is one. Reason: chunking then never loads the model; the estimate runs about 17% under the model's count on the snapshot, which the 300 limit leaves room for ([knowledge chunks](../decisions/knowledge-chunks.md)) (#39).
- **The vectors live in SQLite next to memory's, scored by brute force with numpy, and the embedder is memory's own.** One `Embedder` is built and shared, so the local model is loaded once. Each document stores the embedder's name, and search reads only the current one's. Reason: 444 chunks score in a few milliseconds, and two models' vectors cannot be compared ([embeddings](../decisions/embeddings.md)) (#39).
- **Re-ingest is skipped by content hash.** The hash covers the title, URL, text and chunk settings; a document is embedded again only when it or the embedder changed. `sync` makes a source (or one repo's prefix of it) hold exactly the documents given and removes the rest. Reason: the snapshot is synced on every start, and a start with nothing new must embed nothing (#39).
- **The refresher runs in the app's lifespan as a background task:** the snapshot once at start, past incidents every 10 minutes, repo docs once a day. A source that fails is logged and keeps what it had; a repo that is no longer linked loses its docs. Reason: the first start embeds the snapshot (31.9 s in the backend image on an M4 Pro, 0.02 s on a start with nothing new) without holding up the app, and knowledge search must never stop an incident or Bleep (#39).
- **The first start loads the local model.** Embedding the snapshot is its first use; on later starts nothing new is embedded and the model loads at the first search or recall, as before ([memory](memory.md)) (#39).
- **Past incidents come from memory, one page each:** the title, the day and the service, then the cause, the action, the outcome, the human's decision and feedback, at `/incidents/<id>`. Reason: memory already holds the cleaned record; `recall_incidents` finds incidents like this one, while knowledge search can find a past report by what it says alongside the docs (#39).
- **Repo docs are each linked repo's README and the markdown under the service's `docs_paths` (`docs` when it names none; a path ending in `.md` is read as one file), at most 40 files of at most 100,000 characters each.** They are read with the GitHub client from #37 (`GithubRepoDocs`, behind the small `RepoDocs` protocol). A missing README or folder is skipped, and so is a doc path whose last part has another extension (a compose file, say: no request is made for it) and a file GitHub cannot serve (gone, or over 1 MB); a rate limit, an outage or any other error is raised, so the repo keeps its docs. Reason: the README and docs are where a service's own runbook lives; the caps keep one large repo from filling the index (#39).
- **The linked repos are read from the hosts file, not from discovered services.** Reason: the refresher reads repo docs right at start, before the hosts are first polled; reading discovered services then would see no repo and drop every repo's docs until the next day (#39).
- **Repo docs are read at most once a day, restarts included, unless the linked repos changed.** The last repo refresh is kept in `knowledge_refreshes` with the repos it covered; a start within the day with the same repos waits out the rest of it, and a repo linked or unlinked since makes it due at once. A refresh that read no repo (GitHub unreachable) is not recorded, so the next start tries again. Reason: re-ingest skips embedding by content hash but not the GitHub requests, and without a token GitHub allows 60 an hour, shared with the commit tools; two restarts during setup would otherwise spend them (#39 review).
- **A GitHub rate limit stops the day's repo refresh; an outage or any other error skips that repo.** Either way a repo keeps the docs it had (#39 review). Reason: without a token GitHub allows 60 requests an hour, so every later repo would fail the same way (#37's client note on #39) (#39).
- **Every result reaches the model as untrusted data, guarded like host output.** The tool redacts, cleans and wraps its answer once (source `knowledge`), and Investigate's guard keeps it one wrapper. Each of the 5 hits is cleaned, redacted and escaped first and then cut to an equal share of the 8,000 characters, its title, headings and link included (each put on one line and capped at 200 characters), and the query is repeated in at most 120. Every part is redacted before it is cut, so a secret on a cut point cannot leave half of itself; the guard then has nothing left to grow, so the closest hit is never the one cut, however long a hostile page's heading. Reason: the guard keeps the tail of an over-long result, which would drop the best hits first (#39 review). A doc page whose text tries to close the wrapper is named "documents Bleep searched" in the report's warning (`docs` in `planted_in`). Reason: a linked repo's docs are written by whoever can push to it, and Docker's pages were not written for Bleep ([guard](guard.md)) (#39).
- **The tool says what each source holds and lets the model narrow it** (`sources`: `docker`, `repo`, `incident`). An unknown source is a readable error, not a search. Reason: the model picks the search; a filter it can name keeps a "what does exit code 137 mean" from returning a repo's README (#39).
