# Knowledge search

How the agent looks things up (`backend/src/bleep/knowledge/`, `tools/knowledge.py`): agentic RAG over a curated snapshot of the Docker docs, the README and `docs/` of each service's linked GitHub repo, and past incident reports. Investigate calls `knowledge_search` when it decides to; nothing is put in the prompt up front.

| Piece | Path | What it does |
|---|---|---|
| **Snapshot** | `backend/knowledge/docker-docs/`, `scripts/fetch_docker_docs.py` | 27 Docker and Compose doc pages from docker/docs (Apache-2.0), each with `source_url`, `source_path`, `commit`, `fetched` and `license` in its front matter. The script refreshes them. |
| **Chunking** | `knowledge/chunking.py` | `chunk_markdown(text, max_tokens=300, overlap=50) -> list[Chunk(heading_path, text)]`. |
| **Index** | `knowledge/index.py`, migration `0014_knowledge.sql` | `KnowledgeIndex`: `ingest`, `sync`, `search(query, k=5, sources)`, in the `knowledge_documents` and `knowledge_chunks` tables; `last_refresh` and `mark_refresh` in `knowledge_refreshes`. |
| **Sources and refresh** | `knowledge/ingest.py` | `load_snapshot`, `incident_document` (from `MemoryStore.all_records`), `repo_documents` (from a `RepoDocs`), and `KnowledgeRefresher`, the loop the app runs. |
| **Repo docs** | `knowledge/repos.py` | `GithubRepoDocs`, the `RepoDocs` the app runs: linked repos from the hosts file, read with the GitHub client (`hosts/github.py`). |
| **Tool** | `tools/knowledge.py` | `knowledge_search(query, sources?)`, a read tool, offered whenever the app has the index. |
| **Retrieval check** | `backend/evals/knowledge.py`, `backend/evals/knowledge/questions.yaml` | 20 questions with their expected page, hit@k with the real embedder ([report](../evals/knowledge-2026-11-03.md)). |

## Choices

- **The Docker docs are a shipped snapshot, not fetched at run time.** 27 pages chosen for what breaks on a Docker host: restart policies, memory limits and the OOM killer, exit codes, health checks, logging and the daemon's logs, live restore, networking and published ports, volumes, bind mounts and tmpfs, pruning and `docker system df`, Compose startup order, networking, environment variables and the `services` and `deploy` reference, `docker events` and `docker logs`. Reason: search works offline and the same on every install, and the pages Bleep reads are reviewed in the repo. Docker's docs are Apache-2.0, so the licence ships next to them (#39).
- **The fetch script reads one docker/docs commit and records it in every page.** It resolves Hugo includes, drops other shortcodes, keeps link text without targets, keeps only listed sections of the three long references, and builds the CLI pages from their YAML data. Reason: a refresh is reproducible and the diff shows what changed upstream; link targets and shortcodes are tokens that tell the model nothing (#39).
- **Chunks are cut at headings, then at 300 estimated tokens with 50 of overlap, and embedded with the page title and the headings above them.** Search returns the best chunk of each of the 5 closest pages. Reason: on the retrieval check, 300 put the right page first for 20 of 20 questions where 400 did for 18, and stays under the model's 512 tokens ([knowledge chunks](../decisions/knowledge-chunks.md)) (#39).
- **Tokens are estimated, not counted with the model's tokenizer:** a run of letters is one token, digits count in threes, and every mark (underscores too) is one. Reason: chunking then never loads the model; the estimate runs about 17% under the model's count on the snapshot, which the 300 limit leaves room for ([knowledge chunks](../decisions/knowledge-chunks.md)) (#39).
- **The vectors live in SQLite next to memory's, scored by brute force with numpy, and the embedder is memory's own.** One `Embedder` is built and shared, so the local model is loaded once. Each document stores the embedder's name, and search reads only the current one's. Reason: 444 chunks score in a few milliseconds, and two models' vectors cannot be compared ([embeddings](../decisions/embeddings.md)) (#39).
- **Re-ingest is skipped by content hash.** The hash covers the title, URL, text and chunk settings; a document is embedded again only when it or the embedder changed. `sync` makes a source (or one repo's prefix of it) hold exactly the documents given and removes the rest. Reason: the snapshot is synced on every start, and a start with nothing new must embed nothing (#39).
- **The refresher runs in the app's lifespan as a background task:** the snapshot at start, past incidents every 10 minutes, repo docs once a day. A source that fails is logged and keeps what it had; a repo that is no longer linked loses its docs. Reason: the first start embeds the snapshot (31.9 s in the backend image on an M4 Pro, 0.02 s on a start with nothing new) without holding up the app, and knowledge search must never stop an incident or Bleep (#39).
- **A snapshot sync that fails is tried again every 10 minutes, with past incidents, until it succeeds; after that it is not synced again until the next start.** Reason: the embedder (a model server still starting, say) being down at start otherwise left search without the Docker docs until a restart (#142).
- **The first start loads the local model.** Embedding the snapshot is its first use; on later starts nothing new is embedded and the model loads at the first search or recall, as before ([memory](memory.md)) (#39).
- **Past incidents come from memory, one page each:** the title, the day and the service, then the cause, the action, the outcome, the human's decision and feedback, at `/incidents/<id>`. Reason: memory already holds the cleaned record; `recall_incidents` finds incidents like this one, while knowledge search can find a past report by what it says alongside the docs (#39).
- **Repo docs are each linked repo's README and the markdown under the service's `docs_paths` (`docs` when it names none; a path ending in `.md` is read as one file), at most 40 files of at most 100,000 characters each.** They are read with the GitHub client from #37 (`GithubRepoDocs`, behind the small `RepoDocs` protocol). A missing README or folder is skipped, and so is a README over 1 MB, and so is a doc path whose last part has another extension (a compose file, say: no request is made for it) and a file GitHub no longer serves (gone, or over 1 MB), whose doc goes. A rate limit or an outage is raised, so the repo keeps its docs; a file that fails to read for any other reason (a 403, an answer of the wrong shape) keeps the doc it had while the rest of the repo is refreshed. Reason: the README and docs are where a service's own runbook lives; the caps keep one large repo from filling the index (#39). A read error used to drop the file's doc, and a README over 1 MB used to stop the whole repo (#142).
- **The 40-file cap counts markdown only.** `list_files` takes the suffixes to keep and filters before it counts. Reason: a docs folder with images or data files listed first filled the cap and left its markdown out (#142).
- **`readme: false` on a service leaves the repo's README out;** it is read when any service linking the repo leaves the default, `true`. Reason: a repo holding several services, such as Bleep's own with the demo shop, has a README about something else (#142).
- **`docs_paths` is checked when the hosts file loads.** `./docs`, `docs/` and `docs//ops` become `docs` and `docs/ops`, and a repeated path is kept once; an absolute path, a `..` part, an empty path (or `.`) and a backslash or control character are refused with the service and the reason. Reason: the GitHub client refuses such a path, so `docs/` used to skip the whole repo, README included, every day without saying why (#142).
- **A repo's README and docs are redacted before they are stored or embedded,** with the guard's `redact_text`, as memory redacts before it stores; the content hash is taken of the redacted text. Like the guard everywhere, redaction cuts the middle out of a line over 4,000 characters (after redacting around the cut), so such a line in a repo's docs is stored shortened. The Docker snapshot is not: it is reviewed in the repo, and its examples (`POSTGRES_PASSWORD: example`) are what a reader needs; incident pages come from memory, already redacted. Reason: whoever can push to the repo wrote its docs, `bleep.db` must not hold a secret, and the embedder may be a remote endpoint (#142).
- **The demo shop has its own docs,** two pages in `demo/shop/docs/` on its containers, ports, data, health checks and settings, and `config/hosts.demo.yaml` links the shop to `DannyKuk/bleep` with `docs_paths: [demo/shop/docs]` and `readme: false`. They describe how the shop is built, not its faults. Reason: with the default `docs`, the demo ingested Bleep's own README and pages, `docs/demo.md` (the faults' answers) among them, eval reports with attack payloads, and design pages whose literal wrapper tags made the report warn of planted orders. Served from this checkout on 2026-11-04 that was 37 files for 55 GitHub requests, where the shop's docs take 2 files and 3 requests. The repo link stays, since the GitHub tools read the shop's commits there. A test serves the checkout as the repo through a fake GitHub and checks that the demo hosts file reads only the two pages (#142).
- **The linked repos are read from the hosts file, not from discovered services.** Reason: the refresher reads repo docs right at start, before the hosts are first polled; reading discovered services then would see no repo and drop every repo's docs until the next day (#39).
- **Repo docs are read at most once a day, restarts included, unless the linked repos changed.** The last repo refresh is kept in `knowledge_refreshes` with the repos it read; a start within the day with the same repos waits out the rest of it, and a repo linked or unlinked since, or one the last refresh did not read, makes it due at once. A refresh that read no repo is not recorded, so the next start tries again; nor is one that raised after reading GitHub (the embedder or the database failing), so after that too every restart reads every linked repo again. Reason: re-ingest skips embedding by content hash but not the GitHub requests, and without a token GitHub allows 60 an hour, shared with the commit tools; two restarts during setup would otherwise spend them (#39). A refresh cut short by a rate limit used to be recorded as covering every repo (#142).
- **While Bleep runs, a repo refresh that read no repo is tried again after 10 minutes, then 20, 40 and so on, at most a day apart; one that failed after reading GitHub waits a day, or less when the snapshot syncs.** "Read no repo" is GitHub's side: unreachable, a refused token, a spent rate limit. A refresh that raises once GitHub answered is the embedder or the database failing; it is due again in a day, sooner when the snapshot sync first succeeds in between (a snapshot that keeps failing for its own reason does not hold the repos back past the day). A repo that keeps failing for the same reason is logged once, and again when the reason changes or it is read. Reason: one that read nothing used to wait a day, and a first fix retried every 10 minutes whatever failed: with a broken embedder that read every repo (about 40 requests each) 144 times a day, and a bad token logged a warning per repo each time; with the backoff a lasting outage costs 8 tries in the first day and about one a day after; a failing repo's log entry goes when the repo is unlinked and the backoff exponent is capped (#142, #148).
- **A GitHub rate limit stops the day's repo refresh; an outage or any other error skips that repo.** Either way a repo keeps the docs it had, and the repos not read are read at the next start (#39, #142). Reason: without a token GitHub allows 60 requests an hour, so every later repo would fail the same way (#37, #39).
- **Every result reaches the model as untrusted data, guarded like host output.** The tool redacts, cleans and wraps its answer once (source `knowledge`), and Investigate's guard keeps it one wrapper. Each of the 5 hits is cleaned, redacted and escaped first and then cut to an equal share of the 8,000 characters, its title, headings and link included (each put on one line and capped at 200 characters), and the query is repeated in at most 120. Every part is redacted before it is cut, so a secret on a cut point cannot leave half of itself; the guard then has nothing left to grow, so the closest hit is never the one cut, however long a hostile page's heading. Reason: the guard keeps the tail of an over-long result, which would drop the best hits first (#39). A doc page whose text tries to close the wrapper is named "documents Bleep searched" in the report's warning (`docs` in `planted_in`). Reason: a linked repo's docs are written by whoever can push to it, and Docker's pages were not written for Bleep ([guard](guard.md)) (#39).
- **The tool says what each source holds and lets the model narrow it** (`sources`: `docker`, `repo`, `incident`). An unknown source is a readable error, not a search. Reason: the model picks the search; a filter it can name keeps a "what does exit code 137 mean" from returning a repo's README (#39).
