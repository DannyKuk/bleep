# Memory

What Bleep remembers between incidents and how it uses it (`backend/src/bleep/memory/`, `tools/memory.py`, `api/memory.py`). Short-term memory is the incident's checkpointed graph state ([graph](graph.md)); this page is about long-term memory: every finished incident, the human's decision and feedback on it, and facts per service.

| Piece | Path | What it does |
|---|---|---|
| **Embedders** | `memory/embeddings.py` | `Embedder.embed(texts) -> np.ndarray`, unit-length float32 rows. `FastEmbedEmbedder` (local, the default), `OpenAICompatEmbedder` (any `/embeddings` endpoint), `FakeEmbedder` (hashed words, for tests). |
| **Store** | `memory/store.py`, migrations `0010_memory.sql`, `0011_feedback.sql` | `MemoryStore`: `add_report`, `similar`, `reembed`, `all_records` (for knowledge search); `feedback` and `set_feedback`; and `facts`, `add_fact`, `replace_report_facts`, `delete_fact`, in the `memory_incidents`, `incident_feedback` and `service_facts` tables. |
| **Text** | `memory/text.py` | Cleans memory text before it is stored and labels it when a prompt gets it. |
| **Recall tool** | `tools/memory.py` | `recall_incidents(query)`, a read tool Investigate can call. |
| **Facts learned** | `graph/nodes/report.py`, `prompts/graph/report_facts.md` | Report turns the human's lasting instructions into at most two service facts. |
| **Routes and views** | `api/memory.py`, `api/incidents.py`, `frontend/components/incident/feedback.tsx`, `frontend/components/service/` | Feedback on an incident's diagnosis and plan; a service's facts, listed, added and deleted on its page ([app](app.md)). |

## Choices

- **The local model is `BAAI/bge-small-en-v1.5` through `fastembed`, in the backend, on two CPU threads, baked into the image.** Reason: no paid service and no network at recall time; one embed costs 11 ms and 22 ms of CPU inside the image, and the image grows by 268 MB ([embeddings](../decisions/embeddings.md)) (#29).
- **bge-small stays the local model; a multilingual model such as bge-m3 is set through the endpoint option.** Reason: bge-m3 put the right page first for 8 of 11 German and mixed-language questions (bge-small 4) but for 16 of 20 English ones (bge-small 20), and in the image costs 320 ms of CPU per text, a 566 s first ingest and a 4.44 GB image ([embeddings](../decisions/embeddings.md)) (#146).
- **The model is loaded on the first embed, not when the embedder is built.** Reason: building the app, and every test, then loads and downloads nothing, and a Bleep that has seen no incident does not carry the model's 160 MB (#29). Knowledge search shares the embedder, so the very first start loads it to embed the Docker docs snapshot; later starts embed nothing new and load it at the first search or recall ([knowledge](knowledge.md)) (#39).
- **An OpenAI-compatible endpoint is the option: `EMBEDDINGS_PROVIDER=openai` with `EMBEDDINGS_BASE_URL`, `EMBEDDINGS_MODEL` and an optional `EMBEDDINGS_API_KEY`.** Each can be set from the dashboard too, the endpoint is read at each call, and with only half of it the local model embeds and the log says so; Bleep refused to start that way until the address could come from the dashboard ([settings](settings.md#models-embeddings-and-tracing-from-the-dashboard-372), #372). `EMBEDDINGS_MODEL` is read only for the endpoint; the local embedder always uses the model baked into the image (#87). An endpoint error is raised as `EmbedderError` with Bleep's own words (the status code or the error type), never the reply text. Reason: OpenAI, LM Studio and Ollama all serve that API, and a reply can echo the request (#29).
- **Every vector is stored with the embedder's name, and a different name re-embeds on boot.** `MemoryStore.reembed` runs in the app's lifespan right after the migrations, in batches of 64, committing each batch; until a record is re-embedded it is left out of recall. A re-embed that fails is logged and Bleep starts anyway. Reason: vectors of two models cannot be compared, and a model change must not lose the memory or stop Bleep (#29).
- **One record per incident, written by Report after the report is published and sent, and before the incident is closed.** `add_report` replaces the incident's record if there is one. A memory that fails is logged and the report goes on. Reason: a crash between remembering and closing runs Report again, and the second write must replace, not double; memory helps later runs and must never cost this one its report (#29).
- **A record keeps the date, title, cause, action taken, outcome text, the human's decision and feedback.** Its vector is made from `"<title>. Cause: <cause> Action: <action>."`. A report written in German keeps its cause in English as well (`Report.cause_en`), and the record stores and embeds that one; a German report without a usable English cause stores its German cause, logged as a warning, in the cases listed in [graph](graph.md#report) (#374). Reason: what failed, why and what was done is what makes two incidents alike; the decision is shown with the record, not searched on (#29); the default embedder is English-only (#146).
- **The human's decision is kept in words with the plan and the day: "rejected docker.restart shop-web-1 on 2026-11-10".** An approval reads "approved ... on ...", an instruction "instructed on 2026-11-10: <text>". The prompt shows it as "the human rejected ...". Reason: the next similar incident must hear that the human already said no to that plan (#29).
- **Feedback is a thumbs up or down on the diagnosis or the plan, with an optional note, one per target and incident; a later vote replaces it.** The votes live in `incident_feedback`, keyed by incident and target. Reason: a human changes their mind, and two opposite votes on one finding would tell the next run nothing (#30).
- **The votes reach the memory record in words: "the diagnosis was wrong (it was the disk, not the db) and the plan was right".** The diagnosis comes first; a note is cleaned like any memory text and cut to 200 characters. Recall shows it after the decision ("; feedback: ..."), so the next similar incident's Gather context and the investigate prompt carry it. Reason: the model reads a sentence more reliably than a vote code, and the note is often the real lesson (#30).
- **A vote is copied into the record whenever it comes.** `set_feedback` updates a record that is already there, and `add_report` reads the incident's votes itself, in the same `BEGIN IMMEDIATE` write as the record, so `add_report` lost its `feedback` argument. Reason: the human may vote while the run is still going or days after it closed, and a vote cast while Report writes the record must not be lost between a read and a replace (#30).
- **Recall scores every record of the current model by cosine with numpy, drops those under the embedder's `min_score` (0.5 for bge-small), and puts the same service's first, closest first within each group.** Reason: a few hosts' incidents fit in one matrix product well under a millisecond, and the same service's history is the most useful even when another service's incident scores higher. With bge-small, unrelated incidents score 0.49 to 0.80, so `k` and the order do most of the work ([embeddings](../decisions/embeddings.md)) (#29).
- **The recall threshold belongs to the embedder: `min_score` is the model's measured one, and `EMBEDDINGS_MIN_SCORE` sets it for any model.** `memory/embeddings.py` keeps 0.5 for bge-small and 0.35 for bge-m3 (`MIN_SCORES`, matched by the name with or without an owner or a tag, so Ollama's `bge-m3:latest` counts); any other model keeps 0.5. `MemoryStore.similar` reads it from the embedder, so Gather and `recall_incidents` use the same one. Reason: bge-m3 spreads its scores lower, and at 0.5 it dropped a right past incident that scored 0.39 for Gather's short query; at 0.35 it returned 18 of 18 right records over the 18 queries, one step below the highest that did ([min score](../evals/embeddings-min-score-2026-11-06.md)) (#306).
- **Gather asks for the top 3 similar incidents (the query is in [graph](graph.md)) and adds the service's facts.** A host incident gets no facts (facts are per service). A failure of either becomes a line in `gaps` ("similar incidents: RuntimeError", "service facts: RuntimeError"). Reason: Gather never fails on what it cannot read ([graph](graph.md)) (#16, #29).
- **Facts are text per service, from a person (`human`) or a report (`report`), listed oldest first and deleted by id.** Reason: "always redeploy rather than restart for X" is a preference no embedding search would surface reliably, so a service's facts are always shown whole (#29).
- **Report learns facts only from the human's instructions, in a second model call that sees nothing else but the plan's steps and the service's name.** It runs only for a service incident with at least one instruction (`state["instructions"]`, from Telegram or the dashboard), keeps at most two facts of at most 200 characters, and drops the ones that repeat. Reason: a fact is trusted on every later incident, so it must come from the human, never from a diagnosis or a log a host wrote; an instruction like "restart the db first this time" is only about this incident, and the model tells the two kinds apart (#30).
- **A report fact names its incident, and a re-run Report replaces that incident's facts.** `replace_report_facts` deletes the incident's earlier `report` facts and adds the new ones in one write. A model that fails or a spent budget keeps no facts, and the run still closes. Reason: a crash before the close runs Report again, and the facts must not double; a fact helps later runs and must never cost this one its close (#30).
- **A fact is deleted through its own service only.** `DELETE /api/services/{id}/facts/{fact_id}` removes the fact only when it belongs to that service, a person's or a report's alike, and Gather never sees it again. Reason: a wrong fact learned from a report must be as easy to undo as one typed by hand, and a stale page must not delete another service's fact (#30).
- **Memory text is cleaned before it is stored.** Every field goes through the guard's `strip_control`, `redact_text` and `escape_untrusted`, is joined to one line and cut to 500 characters. A service fact and a feedback note are cut to 200 (`FACT_CHARS` and `NOTE_CHARS` in `schemas/graph.py`), the same limits the API and the dashboard enforce, so what a person can type is what memory keeps (#87). Reason: a report's cause is written by a model that read logs; a stored record must not leak a secret or carry a tag that ends a wrapper (#29).
- **Memory reaches the model as Bleep's own records, trusted, except quoted text.** `describe_past` and `describe_fact` write one line each, and every stretch in double, typographic or back quotes is wrapped with the guard's `wrap_untrusted` (source `memory.quote`), whatever its length. `describe_past` labels each field on its own, and a quote with no closing mark (cut short by the 500-character limit, or never closed) is wrapped to the end of its field (#87). A field or a fact that holds an escaped wrapper tag copied text a prompt had wrapped, a service name above all, and is wrapped whole instead ([graph](graph.md), #305). Single quotes are left alone. The investigate prompt has a "Bleep's memory" section that says so and that a past cause is a lead, not proof; Diagnose labels each line as Bleep's own record; the propose prompt has a "What Bleep remembers" section with the same wording, so the human's past decisions and the service's facts reach the plan ([graph](graph.md), #87). Reason: the record is Bleep's, but a model may have quoted a log line into it, and that line is still host text; apostrophes are far more common than single-quoted text (#29).
- **A past incident's title is wrapped as untrusted when recalled** (`describe_past`, source `memory.title`). Reason: the stored title holds the service id, which comes from a container label, so a hostile Compose project or Coolify uuid would otherwise come back outside any wrapper on every later incident of that service (#295).
- **`recall_incidents(query)` is a read tool, offered whenever the app has a memory.** It returns at most 5 past incidents, without ranking by service (a tool has only the host), in the same one-line form. Its answer goes through Investigate's guard like every tool result and reaches the model wrapped as untrusted. Reason: the model can look further than Gather's three, in its own words; making one tool's output an exception to "every tool result is wrapped once" would weaken a rule that holds for all of them (#29).
- **Tests never load the real model.** A fixture in `tests/conftest.py` makes `FastEmbedEmbedder` refuse to load, and the app's parts in tests use `FakeEmbedder`; one test runs the real model when `BLEEP_REAL_EMBEDDINGS=1` is set. Reason: tests never touch the network (#29).

## Limits

- **A model's paraphrase of a log line is not caught.** Only quoted stretches are wrapped as untrusted, so a diagnosis that restates an injected log line in its own words, short enough to pass `check_report`, is stored as the cause and recalled later as Bleep's own record. The plan check and the human's approval still stand between it and any action. How often it happens is measured only in part: the local-model scenario run's diagnoses still repeated the planted story ([scenarios-local](../evals/scenarios-local-2026-11-03.md)), and a runbook page that lies about the cause did not steer the cloud model ([false cause](../evals/injection-false-cause-2026-11-04.md)) (#87).
