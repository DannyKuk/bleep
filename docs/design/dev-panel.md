# Dev panel

The developer settings, apart from the user UI (spec §4.6, §4.10): which models Bleep calls, its prompts, its budgets, what each incident and each day cost, and the guard log (`backend/src/bleep/api/dev.py`, `incidents/prompt_overrides.py`, `frontend/components/dev/`).

| Piece | Path | What it does |
|---|---|---|
| **Switch** | `config.py` (`BLEEP_DEV_PANEL`), `main.py` | Off by default; on, `create_app` includes the dev routes and the lifespan puts the stored prompt overrides in force. |
| **Prompt overrides** | `prompts/__init__.py`, `incidents/prompt_overrides.py`, the `prompt_overrides` table (`0016_prompt_overrides.sql`) | Text that stands in for a prompt file, checked like the loader's, stored, and handed to the loader. |
| **Cost** | `llm/usage.py` (`CostLedger.by_incident`, `by_day`) | The usage ledger summed per incident and per local day. |
| **Guard log** | `guard/log.py` (`GuardLog.recent`) | The newest records, optionally of one kind or one incident. |
| **Routes** | `api/dev.py`, `schemas/dev.py` | `GET /api/dev`, `GET /api/dev/prompts`, `PUT` and `DELETE /api/dev/prompts/{name}`, `GET /api/dev/costs`, `GET /api/dev/guard-log`. |
| **Page** | `frontend/app/(app)/dev/page.tsx`, `frontend/components/dev/` | Models, Budgets, Prompts, Cost and Guard log panels in the dashboard's current look. |

## Choices

- **Off unless `BLEEP_DEV_PANEL=true`.** Off, the dev router is not included at all, so every `/api/dev` path is a 404, signed in or not; on, the routes sit behind the same session check as the rest of `/api`, so a request without a session is a 401. Reason: a panel that is off should not show it exists, and one that is on must not open a second way in (#42).
- **The dashboard asks `GET /api/dev` whether the panel is on.** The nav shows Dev only when it answers, and the page says how to turn the panel on when it is a 404. Reason: the frontend container does not read the backend's `.env`, and one request tells it what the backend does (#42).
- **The model choice and the budgets are edited here, through `PUT /api/settings`'s `models` and `budgets` sections and the settings store (#36), not through a store or a route of the panel's own.** A save sends the overrides already stored plus the fields changed on the page, so a value left as it was is not pinned over the layer below; "Use the env's models" and "Use the defaults" send `{}`. That route belongs to #36 and stays open with the panel off: switching the panel off hides the editor, the admin session is what guards the values. Reason: one store keeps one precedence and one secret check for every setting (#42).
- **An override must pass exactly the loader's checks** (`prompts.check_override`): it parses with the loader's brace rules and uses exactly the file's placeholders, since the callers fill exactly those, so a missing, unknown or malformed placeholder and a stray brace are a 422 with the reason. Control characters are refused too, and an override is at most 20,000 characters (the longest prompt file is under 4,000). Reason: an override that the loader would refuse would fail the incident that loads it, not the save (#42).
- **`prompts.load` reads the override when there is one and the file otherwise, and fills both with the same checks; reset deletes the override.** The store hands the loader every override it holds at once (`prompts.use_overrides`), after each save and reset. Reason: every caller keeps calling `prompts.load(name, **vars)`, and the file stays the source of truth whenever no override exists (#42).
- **Overrides are not a secret store.** A body is checked with the settings' secret check (`check_body`) before it is validated, and the text again with `find_secrets` in the store; a refusal never quotes the text. Reason: prompts reach the model and the database must never hold a secret (#42).
- **A stored override is checked again when Bleep starts, and one that no longer fits is left out with a warning**: its file is gone, its file's placeholders changed with an upgrade, or it holds something secret-shaped. That prompt is read from its file. Reason: an upgrade that changes a prompt must not leave an incident loading an override its callers no longer fill (#42).
- **With the panel off, every prompt is read from its file**, even when overrides are stored: the lifespan loads them only with the panel on and puts the files back at shutdown. Reason: an override nobody can see or reset should not change what the model reads (#42).
- **Every prompt under `prompts/` can be overridden except `evals/`**, the Telegram templates (`notify/`) included. Reason: the eval runner is a process of its own that never reads the app's database, so an override there would show as in force and change nothing (#42).
- **Cost comes from the usage ledger only**: per incident (the 100 with the latest model call first) and per local day (the last 30, today first), each with its calls, tokens in and out, dollars and the number of calls without a known price. Dollars sum the priced calls, as `CostLedger.incident_total` does, and are "unknown" when none is priced; today's row is `spent_today`, the number the daily cap is checked against. Reason: the panel must show the numbers the budget checks use, not a second count (#42).
- **Each incident in the cost table links to its page and, when tracing stored one (#40), to its trace.** A link that is not http(s) is shown as text. Reason: the trace is where a costly run is read call by call (#42).
- **The guard log is listed newest first, at most 500 entries, filtered by kind and by the exact incident id**; clicking an entry's incident id filters by it. An unknown kind is a 422. Reason: the newest refusals are the ones being looked into, and the log also holds records that are not incidents (`telegram` for a foreign chat) (#42).
