# Observability

How an incident run becomes a trace (`backend/src/bleep/llm/tracing.py`, the runner in `backend/src/bleep/incidents/runner.py`, and the Compose file `docker-compose.observability.yaml`).

## Choices

- **`TRACING=off|langfuse|langsmith`, off by default; it and the tracers' addresses and projects can be chosen on the dashboard too, applied at once, and the env wins** ([settings](settings.md#models-embeddings-and-tracing-from-the-dashboard-372), #372). Off, the runner adds nothing to a run's config: no callbacks, no metadata, no link. An unknown value stops Bleep at startup, and so do, for `TRACING` in the env, Langfuse without `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY` or LangSmith without `LANGSMITH_API_KEY`, naming what is missing; a key set on the dashboard counts ([settings](settings.md#secrets-from-the-dashboard-135)). Reason: tracing sends every prompt and tool result to another service, so it is opted into, and a half-configured tracer should fail loudly instead of tracing nothing (#40).
- **The tracer's callbacks go into the config of each graph invocation, not onto the chat models.** `IncidentRunner` asks the tracer for its part of the config (`Tracer.run_config(incident)`) every time it drives the graph, and LangGraph hands the callbacks down to every node, tool and model call. Reason: a callback on the model would make each model call its own trace, without the nodes and tool calls between them (#40).
- **One trace per incident, with the incident id as its session.** A run that waits for a human ends its graph invocation at Approval, and the resume after the decision is a second invocation, possibly in a Bleep restarted in between. Langfuse's handler is given `trace_context={"trace_id": Langfuse.create_trace_id(seed=incident_id)}`, so every invocation lands in the same trace. The session is `langfuse_session_id` = incident id, the trace name `langfuse_trace_name` = `incident:<title>` (also the root run's `run_name`), and the tags `host:<host id>` and `service:<service id>` (the service tag only on a service incident) go in as the run's `tags`. Reason: one incident should read as one story, start to report, and the session groups it with nothing else (#40).
- **The trace link is stored on the incident before the run starts** (`incidents.trace_url`, migration 0015) and returned with the incident by `GET /api/incidents` and `GET /api/incidents/{id}`. It is `LANGFUSE_UI_URL/project/LANGFUSE_PROJECT_ID/traces/<trace id>`, computed from the incident id, so it needs no call to the API and is right even before the first span arrives. Without `LANGFUSE_PROJECT_ID` Bleep still traces but stores no link; the profile sets it to `bleep`, the project it creates. Langfuse's shorter `/trace/<id>` page, which needs no project, did not work: it looks the id up in the legacy `traces` table ([source](https://github.com/langfuse/langfuse/blob/main/web/src/features/traces/server/getTraceRedirectPageServerSideProps.ts)), which v4 in its default `events_only` mode leaves empty, and answered "not found" for the measured trace below. A link stays when tracing is switched off later, since the trace still exists. Reason: the dev panel (#42) links it, and a link computed from the incident id cannot point at the wrong trace (#40).
- **Two Langfuse addresses.** `LANGFUSE_BASE_URL` is where the backend sends spans (in Compose, `http://langfuse-web:3000`); `LANGFUSE_UI_URL` is what a browser opens (default `http://localhost:3001`). The profile takes `LANGFUSE_UI_URL` from `.env` with that default, for the trace links and for Langfuse's own `NEXTAUTH_URL`, so a Langfuse reached at another address needs one line (#141). Reason: the SDK's own `get_trace_url` builds links from the base URL, which inside Compose is a name no browser can resolve (#40).
- **Keys live in the environment or the dashboard's secret file, never the database.** The Langfuse and LangSmith keys are `SecretStr` settings handed to their clients; a key changed on the dashboard builds the tracer again (`ReloadingTracer`), except a running Langfuse tracer, whose change waits for the next start since Langfuse keeps one client per public key for the life of the process ([settings](settings.md#models-embeddings-and-tracing-from-the-dashboard-372), #372), and one `TRACING` needs cannot be cleared there (#135). They are never written to the database, put in a run's metadata or tags, or returned by the API. The incident carries only the link, a test checks the run's metadata and tags (which reach the checkpoints) for the keys, and the real check below found neither key in `bleep.db` or `checkpoints.sqlite`. A failure in the tracer is logged by its type only and the run goes on untraced (#40). Reason: the rule that secrets never live in the database (#40).
- **The tracer is flushed at shutdown, after the runs are cancelled.** The lifespan closes it after the runner, so the spans of a run stopped by the shutdown are still sent. Reason: Langfuse's SDK batches spans in a background thread (#40).
- **LangSmith is a switch, not a second stack.** `TRACING=langsmith` adds LangChain's own `LangChainTracer` for `LANGSMITH_PROJECT` (default `bleep`), with the same run name and tags and `session_id` = incident id in the metadata. LangSmith gives every invocation its own trace and groups them into a thread by that id, and its links need the workspace and project ids from its API, so no link is stored. Bleep's tracer is explicit: `LANGSMITH_TRACING=true` in the environment would make LangChain trace on its own as well, so leave it unset. Its free Developer plan is enough for Bleep; `LANGSMITH_ENDPOINT` is needed only for the EU region (`https://eu.api.smith.langchain.com`) (#40).
- **A node's model call adds its cost tracker to the callbacks it inherits** (`llm.usage.tracked`). Passing `config={"callbacks": [tracker]}` alone replaces the inherited callbacks, so the tracer never saw those calls: in the measured run below, the trace held Investigate's model calls but not those of Diagnose, Propose and Report. A runner test now fails if a node's model call misses the tracer (#40).
- **An unreachable Langfuse does not stall incidents.** The SDK exports spans from a background thread, so a run never waits on the server, whether Langfuse refuses the connection or drops its packets. Only shutdown waits: the tracer's `close()` runs the client's `shutdown` off the event loop, which gives the exporter its last attempt to send what is queued before Bleep stops. No timing is given here, since none was measured with a reproducible probe (#147). The exporter logs a warning for each batch it could not send, naming the URL only, never the keys. Reason: tracing is an aid, and a down Langfuse must cost a log line, not an incident (#141).
- **Incident runs and chat readings are traced, nothing else.** The cheap model's one-line explanation of a self-recovery runs outside any incident, outside the runner and outside a chat, so it is not traced. Reason: each trace belongs to a session a person looks up, an incident (#40) or a chat surface (#411), and a recovery line has neither.
- **Each chat reading is a trace of its own, in its surface's session.** `Talk` asks the tracer for `talk_config(surface)` at each message, merges it with its own callbacks (the usage ledger's and the log's cost counter), and runs the reading under one parent run (a `RunnableLambda` named `talk-<surface>`), so the tool-call attempt, the guard's retry and the JSON fallback with its retry nest in one trace instead of each starting its own. Only a tracer with `talk_config` traces chats (`talk.conversation.Tracing`; the graph's `Tracer` stays as it was). Langfuse gets a handler with no fixed trace id, the session `langfuse_session_id` = `talk-panel` or `talk-telegram`, the trace name and run name the same, and the tags `talk` and `surface:<surface>`; LangSmith gets `session_id` = the same name. A tracer that fails is logged by its type and the reading goes on untraced. The tracer is built before `talk` in `wiring.build_parts`, and a key changed on the dashboard reaches the next reading through `ReloadingTracer`. Not yet checked against a live Langfuse. Reason: the full prompt a chat answer came from (snapshot, turns, the wrapped text) is what a misread is fixed from (#411).

## The Langfuse profile

- **Langfuse v4, Python SDK v5.** On 2026-11-03 the current server was v4.74.0 ([releases](https://github.com/langfuse/langfuse/releases)) and the Python SDK 5.1.0 ([PyPI](https://pypi.org/project/langfuse/)); SDK v5 needs a server at v4.59.0 or later, and v3 only gets security patches until January 2027 ([upgrade guide](https://langfuse.com/self-hosting/upgrade/upgrade-guides/upgrade-v3-to-v4)). Both images are pinned to `4.74.0`. Reason: start on the version that is maintained (#40).
- **`docker-compose.observability.yaml` is Langfuse's own `docker-compose.yml` trimmed** ([source](https://github.com/langfuse/langfuse/blob/main/docker-compose.yml), [docs](https://langfuse.com/self-hosting/deployment/docker-compose)): web, worker, Postgres 17, ClickHouse 26.3, Redis 7.4 and MinIO (pinned by digest: its free image has only `latest`), every service under the profile `observability` and labelled `bleep.self=true`. The services are prefixed `langfuse-` so they cannot collide with Bleep's or a watched project's names. Dropped from upstream: the optional AI features, Azure and OCI storage, batch export, SMTP and the in-app agent. Telemetry to Langfuse is off. Reason: only what tracing needs, on Bleep's terms (#40).
- **Only the UI is published, on `127.0.0.1:3001`.** Upstream also publishes the worker, Postgres, ClickHouse, Redis and MinIO; here none of them is reachable from outside Docker. Port 3000 is Bleep's dashboard. MinIO not being published means media uploads from a browser do not work, and Bleep sends no media. Reason: the fewer open ports, the better, and 3000 is taken (#40).
- **No clicks to set it up: headless initialization.** The org `bleep`, the project `bleep`, its key pair and the login come from `LANGFUSE_INIT_*` in `.env` on first start ([docs](https://langfuse.com/self-hosting/administration/headless-initialization)), and the same two keys are handed to the backend as `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY`. Sign-up is off. The salt, encryption key, NextAuth secret, keys, login email and password must be set in `.env` (Compose refuses to start without them); the internal database passwords have defaults, since no database port is published. With this file, `TRACING` defaults to `langfuse`, so it is passed only with the profile; without it the spans have nowhere to go and are dropped. The backend reads all of `.env`, so it also holds the Langfuse server's salt, encryption key, NextAuth secret and login password, which it never uses; keeping them in a separate env file would take a second `--env-file` on every command, and the backend already holds the model and Telegram keys. Reason: the keys are chosen once, in one place, and never pasted from a UI (#40).
- **Measured on 2026-11-03.** With the profile up on Docker Desktop, the `db-down` demo fault opened one incident on gpt-6-luna; its run stopped at Approval, a rejection resumed it, and it closed. ClickHouse held exactly one trace for the project: its id matched the link on the incident, its session was the incident id, its name `incident:unhealthy on demo/compose:shop`, its tags `host:demo` and `service:demo/compose:shop`. It had 24 spans, among them both invocations (the run at 20:33:21 and the resume at 20:34:03, each named after the incident), every node, 7 tool calls and 4 model calls, all of them Investigate's: the model calls of Diagnose, Propose and Report were missing, fixed by `tracked` above and measured again on LangSmith below. The v4 public `GET /api/public/traces` no longer answers in the default `events_only` mode, so the count came from ClickHouse's `events_full` table. That run stored a `/trace/<id>` link, which answered "not found"; the project link that replaced it was checked against the same trace through the query the trace page makes (`traces.byId` for project `bleep`), which returned it with its name, tags and session. Reproduce: [below](#reproduce) (#40).

## LangSmith, measured

- **Measured on 2026-11-03** with `TRACING=langsmith` against LangSmith's EU region, on main at 5c17881, which includes `tracked`. A throwaway container on the demo engine that exits with code 1 and is restarted by its policy opened `container died on demo/container:crashloop-probe` by repeated deaths. An eval running at the same time also opened `unhealthy on demo/compose:shop` on the shared engine. Both runs ended without a plan to approve. The project `bleep` then held one root run per incident, named `incident:<title>`, with `session_id` and `thread_id` = the incident id and the tags `host:demo` and `service:demo/...`. Each held 10 model calls: Investigate 6, Diagnose 2, Propose 1, Report 1. Each node's model call is in the trace, which the Langfuse run before `tracked` lacked. No incident reached Approval, so a resume, which LangSmith shows as a second trace in the same thread, was not seen there. A third incident, opened when the container went on crashing after the first closed, was cut off in Investigate by the teardown (3 model calls, its own root run and session). The incidents' `trace_url` stayed empty, as designed. Counted with `langsmith.Client.list_runs(project_name="bleep")` (#40).

## Reproduce

```bash
# .env: the LANGFUSE_INIT_* values, LANGFUSE_SALT, LANGFUSE_ENCRYPTION_KEY, LANGFUSE_NEXTAUTH_SECRET (.env.example)
docker compose -f docker-compose.yaml -f docker-compose.observability.yaml --profile observability --profile demo up -d --build
docker compose -f demo/compose.yaml up -d --build
demo/fault.sh db-down on      # then approve or reject on the dashboard, and switch it off
docker compose -f docker-compose.yaml -f docker-compose.observability.yaml exec langfuse-clickhouse \
  clickhouse-client --user clickhouse --password clickhouse -q \
  "SELECT trace_id, count(), any(session_id), any(trace_name) FROM events_full FINAL GROUP BY trace_id"
```

The incident's link (`trace_url` in `GET /api/incidents/{id}`) opens the trace at http://localhost:3001 after logging in with `LANGFUSE_INIT_USER_EMAIL` and `LANGFUSE_INIT_USER_PASSWORD`.
