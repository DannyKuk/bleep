# Settings

What a person can change from the dashboard and how it takes effect (`backend/src/bleep/incidents/settings_store.py`, `api/settings.py`, `guard/secret_fields.py`, `store/secrets.py`, `api/secrets.py`). Non-secret settings are stored in SQLite. Secrets never are: they come from the environment, from files the hosts file names, or from the secret file the dashboard writes, apart from the database ([below](#secrets-from-the-dashboard-135)).

| Piece | Path | What it does |
|---|---|---|
| **Settings store** | `incidents/settings_store.py`, the `settings` table (`0001_init.sql`) | The overrides, one JSON row per section; the values in force, computed from the layers below; the graph's `SettingsSource`. |
| **Schemas** | `schemas/settings.py` | `SettingsUpdate` and its sections with their bounds, and `SettingsView`. |
| **Secret check** | `guard/secret_fields.py` | Finds a secret-shaped key or value anywhere in a body. |
| **Routes** | `api/settings.py` | `GET /api/settings` (values in force, the overrides and their `version`, each host's connection and whether the model key is set) and `PUT /api/settings`, which needs that version in `If-Match`. Each plugin's view (`GET /api/plugins`) carries its own `version`, which `PUT /api/plugins/{name}` needs the same way. |
| **Secret file** | `store/secrets.py`, `data/secrets.json` on the data volume | The secrets and plugin addresses set from the dashboard, mode 0600, apart from the database; the values in force (the env's, else the file's); who is told when one changes. |
| **Secret routes** | `api/secrets.py` | `GET /api/secrets` (each value's name, kind, whether it is set and where from, never a secret's value), `PUT /api/secrets/{name}` (`{"value": "..."}`) and `DELETE /api/secrets/{name}`. |
| **Settings page** | `frontend/components/settings/` | The dashboard's `/settings`: the Bleep-wide forms (time zone, language, thresholds, models, embeddings, tracing, plugins, secrets) and the read-only state of what stays in the env and the hosts file. A host's rules are edited on the host's page (`/hosts/[id]`, `frontend/components/host/`, #227) and a service's URLs, rules and protected containers on the service's page (`/services/[id]`, `frontend/components/service/`, #228), with the same forms. |

## Choices

- **Precedence is database override > hosts file > defaults; for the model choice, the embeddings and tracing it is env > database override > defaults** ([below](#models-embeddings-and-tracing-from-the-dashboard-372)). The store keeps only what a person changed and computes the values in force on every read. Reason: clearing an override brings the hosts file's value back, and a hosts file edit still shows where nothing overrides it (#36).
- **A person can change the model choice (`provider`, `model`, `cheap_model`, `local_model`), the embeddings and tracing settings (#372), the budgets, the thresholds, each host's rules and each service's URLs, rules and protected containers, and switch plugins.** Every connection field of a hosts file host (address, key file, endpoint, socket) stays in the hosts file, and an ssh host can be added, changed and removed from the dashboard, its key going to the secret file ([hosts](hosts.md#hosts-from-the-dashboard-194), #194); the API keys, the plugins' addresses and the model servers' addresses can be set from the dashboard too, but only into the secret file ([below](#secrets-from-the-dashboard-135)). Reason: these are the settings the settings page and the dev panel edit; a connection field decides where Bleep logs in (#36).
- **The `settings` table already existed from the first migration, so this needed none.** Each section is a row: `models`, `budgets`, `thresholds`, `general`, `embeddings`, `tracing`, `host:<id>`, `plugin:<name>` (#36, `general` #400, `embeddings` and `tracing` #372).
- **Bleep's time zone is the `general` section's `timezone`, an IANA name the backend's zone data knows (`UTC` needs none); any other name is a 422 at `general.timezone`.** `GET /api/settings` shows the zone in force as `timezone`: the dashboard's choice, else `BLEEP_TIMEZONE`, else null. `SettingsStore.zone()` is read by Telegram at each message, so a change applies to the next one without a restart, and it is not behind the dev panel. Reason: `BLEEP_TIMEZONE` stays as the starting value, so an existing `.env` keeps working, and the person changes it where every other setting is (#400).
- **Bleep's language is the `general` section's `language`, `en` or `de` (`Language` in `schemas/settings.py`); anything else is a 422 at `general.language`.** `GET /api/settings` shows the language in force as `language`: the dashboard's choice, else `en`. `SettingsStore.language()` is read each time a prompt is built (it is part of the graph's `SettingsSource`, and the watcher reads it for the recovery line), so a change applies to the next text the model writes without a restart; it is not behind the dev panel and has no env variable. The settings page's Language panel sends the time zone along, and the Time zone panel the language, since a `PUT` replaces the `general` section whole (`withGeneral` in `components/settings/settings-page.tsx`). What the language changes in the prompts is in [graph](graph.md); Telegram, the chat and their buttons read it at each message too, and what they say in it is in [notify](notify.md) (#375). Reason: Telegram and the reports are shared by everyone on the install, so it is one setting for the install, not one per browser (#374).
- **A `PUT` replaces each section it names and leaves the others; under `hosts` it replaces each host it names; `{}` clears.** Reason: the settings page and the dev panel write different sections, and one page open on old values must not undo the other's change (#36).
- **Every `PUT /api/settings` sends the `version` of the overrides it was built from in `If-Match`; without it the answer is 428, and when the overrides have changed since it is 409 with the current version, and nothing is applied.** `GET` and `PUT` return the version in the body and as the `ETag`. It is a hash of the overrides as they are stored (`SettingsStore.version`), so it holds across a restart, needs no column or migration, and the same content always has the same version; the check runs under the store's lock, so of two writers from one version only the first goes through. Reason: every form builds its section's whole body from the overrides it read, so without the check a stale tab, or the dev panel and the settings page saving at once, would silently put back what the other changed, such as unprotecting a container protected meanwhile (#41).
- **Each plugin has a version of its own on the same rules: a hash of its stored row (on or off, settings), in each `PluginView`, required in `If-Match` on `PUT /api/plugins/{name}`, 428 without it, 409 with the current one when stale.** `SettingsStore.plugin_view` waits for a save in progress and then reads the version and the settings with nothing in between, so the settings it shows are stored ones (`set_plugin` puts a change in force before it writes it, and restores the plugin when the write fails); a change made while the health check runs makes the version older than the view, never newer. One version for everything was the other choice; it was not taken because the page reads the plugins and the settings in separate requests, so a save of a threshold would make every plugin form stale, and a plugin read just before a change could carry a version that is already current. Reason: a plugin's `PUT` replaces all its settings, built from what the form read, and a plugin's settings can name the read tools it may run without approval, so a stale tab must not put a removed one back (#41, #132).
- **A plugin's secret that is optional (`required: false`, the MCP token) is shown neutrally as "Not set, optional" when unset; only a required one is "Missing".** Reason: an unset optional secret is not a broken setup (#132).
- **A Coolify application can be protected by its name or uuid, not only by a container name** (why: [guard](guard.md#plan-check), #38).
- **A service's URLs and rules replace the hosts file's, but its protected containers are added to them: the dashboard can protect a container and never unprotect one the hosts file protects.** Reason: protection is a guard that blocks act tools even after an approval; lifting it should take an edit of the file on the server, not a click in a browser session (#36).
- **This holds when the hosts file and the dashboard name the service differently**, one by its display name (`shop`) and the other by its key (`compose:shop`): the store keeps both entries, and discovery applies both to the service, unioning their protected containers ([hosts](hosts.md#service-discovery-and-the-registry), #230). `ServiceSettingsView.hosts_file_protected_containers` for either key lists the hosts file's protected containers under the service's key and its name, read from the services Bleep sees on the host; for a service not seen yet it is the entry's own key only. Reason: the service page edits the key it finds first, and showing that entry's hosts file protection alone would leave a container protected under the other key unlocked on the page (#230).
- **The layer under a host's overrides is the hosts file's host or the dashboard's.** `SettingsStore.host_changed` adds or replaces a dashboard host there when it is added or changed, and drops it and deletes its overrides when it is removed. Reason: the same rules, URLs and protected containers apply to both, and a host added again under a removed one's id must not inherit them (#194).
- **The merged host goes into the registry at once (`Registry.override`), which regroups the services from the last listing.** Reason: the URL checks, the plan check, Verify and Gather all read the host's config from the registry, so every one of them sees the same value from the next read on (#36).
- **Three budgets belong to model outages and stuck incidents:** `model_timeout_s` (default 120, 10 to 600), `paused_retry_min` (default 5, 1 to 240) and `stuck_after_min` (default 30, 5 to 1440). All are whole numbers, editable in the dev panel like the other budgets and read at the moment they are used ([incidents](incidents.md#model-outages-and-stuck-incidents), #86).
- **Every value takes effect without a restart.** The graph reads budgets, models and enabled actions from the store as each node runs; the detector reads the thresholds on every signal. Reason: a budget or a threshold is changed when it is wrong now (#36).
- **Budgets and thresholds have bounds**: for example 1 to 50 tool calls per round, a daily cap of $0 to $100, at most 5 verify loops, a disk threshold of 50 to 99 %, at least 1 % memory available, a load per CPU of 0.5 to 20, a low-confidence line of 0.1 to 0.95. A rule is at most 500 characters, a service at most 20 URLs. Reason: a typo must not switch a guard off or let one incident spend without end (#36).
- **A body is checked for secrets before it is validated, and refused with 422 naming where, never what.** Any key at any depth that looks like a secret's name is refused: the name is lower-cased with `_`, `-` and `.` removed and matched for `token`, `secret`, `passw`, `apikey`, `privatekey`, `credential` and similar, or ends in the word `key`, so `TOKEN`, `apiKey`, `x-api-key` and `Db_Password` all are. The settings models' own field names are trusted (`incident_tokens` is a budget). Any string, key or value, that redaction would change is refused too: a token in a rule, a password in a URL, a URL with a secret-named query parameter (`?key=`). Names and strings are also checked folded (NFKC, no invisible characters, look-alike letters mapped to Latin; a string over 4,000 characters read in overlapping 4,000-character windows instead of whole, so redaction never cuts it, #130), so `ｔｏｋｅｎ`, `pаssword` with a Cyrillic а and `pass​word` with a zero-width space are caught. The body is walked with a stack, so a deeply nested one is refused, not a crash, and a body over 100,000 characters as JSON is a 413 before the check reads it (`MAX_BODY_CHARS` in `api/settings.py`, also for plugin and prompt-override bodies), so its cost stays small (#130). Validation errors are returned with where and why but without the values sent, and a URL error says what a URL must be rather than quoting it. Reason: rules and URLs reach the model, the database must never hold a secret, and a 422 that echoes the body would put the secret in a response and in logs (#36).
- **A write body is capped by size before it is read: `BodyLimitMiddleware` (`api/body_limit.py`) refuses `PUT /api/settings`, `PUT /api/plugins/{name}` and `PUT /api/dev/prompts/{name}` with 413 when `Content-Length` is over 400,000 bytes, and for a chunked body stops reading at that cap.** The cap is `MAX_BODY_CHARS` (100,000) times 4, the most bytes a character takes in UTF-8, so a compact JSON body within the character limit is never refused (the dashboard sends `JSON.stringify` output; whitespace or `\uXXXX` escapes can make a raw body larger and it is refused); `check_size` still applies the exact character limit to the parsed JSON, and answers 422 for a body nested deeper than 32 levels (`MAX_BODY_DEPTH`; the dashboard's deepest body is about six), checked with a stack before anything else reads it, so the answer is the same on every platform: relying on `json.dumps` raising `RecursionError` gave 422 on macOS and 413 on Linux, where a thread's larger stack lets it finish (#251). A middleware, not a dependency, because FastAPI parses the body before any dependency of a route with a `Body()` parameter runs, so only code in front of the routing can stop the read; it is scoped to these paths so other routes are untouched. Reason: a logged-in client could otherwise make the backend buffer a body of any size before the 413 (#167).
- **The check is stricter than redaction's own.** `token_file`, `key_file` and a service named `x-api-key` are refused here, though redaction would leave them. Reason: a settings key that only might be a secret costs a person a rename; a missed one costs a leak (#36).
- **A stored row is checked again on load, and one that no longer fits is left out with a warning**: a host gone from the hosts file, a field renamed, a value out of bounds or anything secret-shaped. Reason: Bleep must start on the layers below rather than refuse to start, and a row written behind the API's back gets no further than one written through it (#36).
- **What the check does not catch**: a password written as prose ("the db password is hunter2") and token formats redaction does not know. Reason: the check is defence in depth behind the rule that secrets go in the environment; a pattern for every format is redaction's work, not the settings page's (#117).
- **A person with a session can point URL checks at any http(s) host and switch the provider from local to OpenRouter.** Reason: both are what the settings page is for and need the admin login; the plan check's rule that only configured URLs may be verified is about what the model names, not what the admin configures (#36).

### The settings page (#41)

- **The settings page edits the time zone (#400), the language (#374), thresholds, the model choice, the embeddings and tracing (#433) and the plugins, each host's page edits that host's rules (#227), and each service's page edits that service's URLs, rules and protected containers (#228); the budgets are edited only in the dev panel.** With the panel off, `PUT /api/settings` refuses `budgets` with 403 ([dev panel](dev-panel.md), #130); since #372 it takes `models`, `embeddings` and `tracing` with the panel on or off, since they belong to the settings page, and the dev panel's models form is gone (#433). Reason: the dev panel holds the prompts and the budgets, and one place per setting means two pages can never fight over a section (#41).
- **A hosts file host's connection (`source: "file"`) is shown read-only, as the hosts file has it; a dashboard host's (`source: "dashboard"`) carries its key and host key as set or not and its `version` ([hosts](hosts.md#hosts-from-the-dashboard-194), #194).** For a hosts file host: kind, `user@address:port`, the Docker socket or the endpoint, the known hosts file, and the SSH key as its file and whether Bleep can read it. `GET /api/settings` gives it as each host's `connection`; the key file is a `SecretStatus` (`{env, file, set}`), `set` when it is a file Bleep's user may read (`is_file()` and `os.access(R_OK)`), and it is never opened. Userinfo in an endpoint or address is replaced, up to its last `@` (`tcp://<redacted>@proxy:2375`). Reason: where Bleep logs in is the hosts file's to say (#36), but a person debugging an unreachable host needs to see it, a key file that is not mounted or not readable is the first thing to rule out, and a password in an endpoint URL must not reach a browser (#41).
- **Every secret shows as set or missing with where it is kept, and the settings page sets and clears it** (#41, #202). The model key is `model_key` in `GET /api/settings` (the variable of the provider in force, `OPENROUTER_API_KEY` or, for `anthropic`, `ANTHROPIC_API_KEY`, set or not; #504), a plugin's secrets come from `GET /api/plugins`, the Telegram token from `GET /api/telegram/status`; where each is kept ("Set in .env", "Set on the dashboard") comes from `GET /api/secrets`, so a dashboard-set value is never said to come from the env. The field is named `model_key`, not `api_key`, so the existing test that no `api_key` reaches the response still holds. Reason: a person must be able to tell why something is off without the value ever leaving the server (#41).
- **A protected container from the hosts file is shown with a lock and no remove button; only the ones added on the dashboard can be removed.** `ServiceSettingsView.hosts_file_protected_containers` says which are the file's, since `protected_containers` is the merged list. Reason: the dashboard can never unprotect what the hosts file protects (#36), and a remove button that does nothing would look like it did (#41).
- **A host's page lists every service Bleep sees on the host (`GET /api/services`) and links every one the hosts file or the database has settings for; each service's page edits its settings, and a service with none starts from empty lists (#228).** Reason: a person adds the first URL or rule to a service from the dashboard, not only to the ones the hosts file already names (#41).
- **Each save sends the whole section it changes, built from the overrides: a service's change goes as that host's overrides with only that service's field replaced, and thresholds as the overrides already there plus the changed values.** "Use the hosts file's" drops the one field; "Back to the defaults" sends `thresholds: {}`. Reason: `PUT /api/settings` replaces each section and each host it names (#36), so a body built from the values in force would turn every hosts file value into an override (#41).
- **The forms do not repeat the bounds, not even a `maxLength` on an input; the API's 422 is shown under the form that sent it, named as the form names the field** ("Disk used at or above: Input should be less than or equal to 99", "Rule 1: String should have at most 500 characters", "URL 2: …"), and Bleep's own refusals (a secret in a rule, an unknown host) as the API words them. A value that is not a number is sent as typed for the API to refuse. The draft stays after a refusal. A URL row left empty is the one thing checked on the page: it is marked invalid and nothing is sent, rather than the row being dropped. Reason: the bounds live in `schemas/settings.py` only, so the page cannot drift from them, and an input that cuts text off as it is typed hides that anything was lost (#41).
- **After a 409 the page reads the settings (or the plugins) again and says the save was not applied because they changed elsewhere; it never retries.** When that read fails too it says so and asks for a reload, instead of claiming the page is current. Each save sends the version of the view its body was built from, and only one save on the page is in flight at a time (`components/save-lock.tsx`: every Save waits while one runs), so the next is built from the last one's result. Reason: a retry would send the same stale body with a fresh version and put back what the other writer changed; and two saves from one view would make the second a 409 for no reason (#41).
- **A plugin switched on that does not run shows "On, waiting for" its unset required secrets (or "On, not running" when its code failed to build), with a Switch off button.** `PluginView.switched_on` is the stored toggle, apart from `enabled` (on and running); at boot a stored "on" whose secret is unset keeps its row (#36), and the boot log says it "stays switched on but does not run", not that it was left out. Switching it off stores off, so it stays off when the secret comes back. Reason: the view said only `enabled: false`, so the page would offer "Switch on" and the plugin came back on by itself after the next restart with the secret set (#141).
- **A plugin's invalid settings are a 422 naming each field with pydantic's reason** ("plugin coolify: invalid settings (deploy_timeout_s: Input should be greater than or equal to 60)"), without the value sent. Reason: the same "where and why" as the settings' own errors above; a field name alone did not say what to fix (#141).
- **`GET /api/plugins` runs the plugins' health checks together** (`asyncio.gather`), each still bounded to 5 s. Reason: the page reads the list on load and again after every 409, and one after another it waited up to 5 s per plugin (#141).
- **A protected entry may hold spaces and `:`** (`Shop API`, `name:main`), up to 255 characters and trimmed, but no control character (`schemas/settings.py` `ContainerName`); a secret-shaped one is still refused by the secret check. Reason: a Coolify application is protected by its name as written in Coolify ([guard](guard.md#plan-check), #134), which a container-name pattern would refuse (#141).
- **A protected name whose Coolify slug is empty (only symbols or emoji, such as `🚀`) is refused with a 422 that says to protect the application by its uuid, instead of being stored.** `put_settings` checks each protected name with `coolify_slug` (`api/settings.py` `refuse_names_without_a_slug`); the hosts file only warns at startup for the same name ([guard](guard.md#plan-check)). Reason: such a name matches no application by slug, so a saved entry would show as protected and protect nothing, and a refusal is shown by the dashboard as it is for any 422; a Docker container name starts with a letter or digit, so no real container is refused (#176).
- **The page's types are in `frontend/lib/settings-types.ts`, apart from `api-types.ts` ([app](app.md)).** Reason: a separate file keeps the settings contract out of the way of the other pages' types (#41).
- **The Models, Embeddings and Tracing panels are one form each, built from one component (`components/settings/section-form.tsx`), with each setting's secrets as rows under the form.** Models: `provider` (OpenRouter, Anthropic, local), `model`, `cheap_model`, `local_model`, then `OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY` and `LOCAL_BASE_URL` (#504). Embeddings: `provider` (the built-in model, a local server, an endpoint), `model`, `min_score`, then `EMBEDDINGS_BASE_URL` and, only while the embedder in force (`embeddings.provider` in `GET /api/settings`) is an endpoint, `EMBEDDINGS_API_KEY`; the built-in model and a local server need no key (#442). Tracing: `tracing`, the Langfuse base URL, UI URL and project id, the LangSmith endpoint and project, then the three keys. The Secrets panel no longer lists the names a panel shows. A stored `EMBEDDINGS_API_KEY` is hidden while the embeddings provider in force is the built-in model (`local`) or a local server (`server`), so it is not listed anywhere then; it stays stored, is used again when the provider becomes an endpoint (`openai`), is never sent to a local server, and is cleared with its address (a new or cleared `EMBEDDINGS_BASE_URL` clears it, [above](#secrets-from-the-dashboard-135)). A save sends the section's stored overrides with the changed fields on top, as the thresholds form does, and a field emptied is left out, so the layer below shows; a number is compared as a number (`0.30` is `0.3`) and emptying a field no override sets is no change, so neither enables Save or asks; "Back to the defaults" sends `{}`. Reason: one place per setting, a key next to what it is for, and one set of save and error rules for the three (#433).
- **The Models panel shows only what the provider in the select uses, and its model fields follow the select before a save.** OpenRouter and Anthropic show `model` and `cheap_model` with `OPENROUTER_API_KEY` or `ANTHROPIC_API_KEY`; local shows `local_model` with `LOCAL_BASE_URL`; the rest are hidden (`visibleWhen` on a field). A hidden field's stored override is neither sent nor cleared by a save. Picking another provider switches `model` and `cheap_model` to its defaults at once, decided by value as `ModelSettings.resolved()` does: a field whose value is the default of the provider in force counts as unset (whether or not an override stores it), shows the new provider's default, and a save drops its override; any other value, typed before or after the switch, stays and is saved. The form never shows an id the save will not use. The defaults are `PROVIDER_DEFAULT_MODELS` in `schemas/settings.py`, the one source `ModelSettings.resolved()` uses too, and `GET /api/settings` carries them as `model_defaults` (`follow` on `SectionForm`). Reason: the form must not look like it will send OpenAI ids to Anthropic, and a person should see only the key of the provider they chose (#517).
- **A field named in `from_env` has no input: it shows "Set in the environment (.env or Compose)", the variable's name and the value in force, and is left out of what the form changes.** The stored overrides are still sent as they are, which the API accepts for an override that is not in force. Reason: the API refuses a change to such a field with a 422, so an input would only lead to a refusal; the page says which place decides, as it does for a secret (#433).
- **A save of the embeddings asks first, inline, and sends only on the second click.** The text says it applies at the next start; a provider change, or a model change while an endpoint or a local server is the embedder, adds that the memory and the knowledge index are embedded again then and past incidents are left out of recall until that is done; a change of the minimum score alone says it embeds nothing again. "Back to the defaults" gets the re-embed text, as it may change the provider. The question takes focus on its first button, is described by its text and returns focus to Save on Cancel. Editing a field again, or Cancel, drops the question, so the body sent is always the one the question was about. No `alert()` or `confirm()`. Reason: a restart that re-embeds is not something to find out afterwards, and the wording follows what `restart_needed` and `MemoryStore.reembed` do ([below](#models-embeddings-and-tracing-from-the-dashboard-372), #433).
- **The Embeddings panel says "A restart is needed" while `restart_needed` lists `embeddings`, and the Tracing panel while it lists `tracing`; no other field says anything, since it applies at once.** The page's heading says the same in one sentence. A secret saved or cleared makes the page read the settings again along with the plugins and Telegram, since a tracer's key or the embeddings' address decides `restart_needed`. Reason: the page tells a person only what differs from "saved means in force" (#433).
- **The API's refusals are shown under the form that sent them, as the other forms do** (an env field, "set EMBEDDINGS_BASE_URL first", "clear LANGSMITH_API_KEY first", "TRACING=langsmith needs LANGSMITH_API_KEY"), named as the form names the field when the API names one; a refusal to clear `EMBEDDINGS_BASE_URL` while the endpoint embeds (409) is shown under that row. Reason: the rules are the backend's alone ([below](#models-embeddings-and-tracing-from-the-dashboard-372)); the page repeats none of them (#433).

## Secrets from the dashboard (#135)

Every secret Bleep reads from `.env` can also be set from the dashboard, and so can the plugins' addresses and the model servers' (#372): the model keys (`OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`), the Telegram token and chat id, `GITHUB_TOKEN`, `LOCAL_BASE_URL`, `EMBEDDINGS_BASE_URL`/`EMBEDDINGS_API_KEY`, the Langfuse and LangSmith keys, and `COOLIFY_URL`/`COOLIFY_TOKEN` and `MCP_URL`/`MCP_TOKEN`. `wiring.secret_names` is the list; a name not on it is a 404, a dashboard host's key (`SSH_KEY:<id>`, `KNOWN_HOSTS:<id>`) included: it is set only with its host ([hosts](hosts.md#hosts-from-the-dashboard-194), #194).

- **They live in one file apart from the database: `secrets.json` in the data directory (`/data` in the backend container, the `bleep-data` volume), next to `bleep.db`.** It is JSON, mode 0600, owned by the backend's user (uid 10001 in the image). Every write goes to a temporary file in the same directory, created 0600 (`mkstemp`, then `fchmod` to say so), flushed and synced, then renamed over the old one, so the file is never readable by another user, not even halfway through a write, and a failed write leaves the old file whole. The directory is synced after the rename, so the rename survives a power loss. At boot the file is opened without following a link (`O_NOFOLLOW`): a link or anything but a regular file at the path stops Bleep, and nothing is read or chmodded through it. A file found readable by others is set to 0600 with a warning; one that is not valid JSON in Bleep's format stops Bleep with its path and "fix or delete it", never its content. Temporary files left by a write the process did not live to finish (`.secrets-*.tmp`, which hold secrets too) are deleted. A name in the file that Bleep no longer knows is left out with a warning. Reason: Bleep's rule that secrets never live in the database holds as written: nothing of the file reaches SQLite, the checkpoints, the bus or the guard log (`tests/api/test_secrets.py` reads `bleep.db` for the value) (#135).
- **Who can read it: the backend's user, and anyone who can read the data volume as root**, which on the Docker host means root and anyone in the `docker` group (any container that mounts the volume reads it). The file is not encrypted. Reason: a key to decrypt it would have to live on the same host, in the env or another file the same people can read; encrypting it with a key held elsewhere is a later step if the threat model needs it (#135).
- **A backup of the data volume holds the secrets in clear.** Treat a copy of `bleep-data` (or of `/data`) like the `.env` file: keep it where only the people who may read the tokens can, and revoke the tokens when a copy is lost. `docker compose down -v` deletes the file with the database. Restoring a backup brings back the secrets as they were when it was taken. Reason: the file sits on the volume so that a restart, an upgrade and a backup keep it together with the database it belongs to (#135).
- **The API is write-only.** `GET /api/secrets` names each value with its kind (`secret`, `address`, `id`), whether it is set, where it comes from (`env` or `dashboard`), whether the env decides it (`env_owned`) and, for an address, the token it carries; never a secret's value. Of an address set on the dashboard it gives only the origin (`https://host[:port]`) and an opaque `version`; of an address the env sets, nothing beyond set and source; a dashboard address in the file that Bleep would not accept now (the file edited by hand) is `invalid: true` with no part of it shown, and its plugin is refused at switch-on; the chat id is masked to its last two characters. `PUT` and `DELETE` answer the same list. A value is checked before it is stored: not empty, at most 16,384 characters, no control character (C0, DEL, C1), no invisible format character and no line or paragraph separator, and an address as below. Reason: a path can hold a credential (a hosted MCP server's endpoint often does), and the env's address was never the API's to show (#135). A refusal says why in Bleep's words, a body that does not fit is a 422 without the input (FastAPI's own 422 would echo it), and `BodyLimitMiddleware` caps the body before it is read. The log says only "NAME set from the dashboard" or "cleared". Reason: the value must never come back to a browser, a log or an error, and the settings check refuses secret-shaped values, so this route reads its own small body and skips that check (#135).
- **The env wins.** A name the env sets (non-empty) is used from the env, shown as `source: env`, `env_owned: true`, and the dashboard can neither set nor clear it: 409, "change it there". Reason: Compose and CI setups keep `.env`, and a value that silently shadows or is shadowed by the other would leave a person guessing which one Bleep uses (#135).
- **A plugin's address is bound to its token.** Setting a new address from the dashboard, or clearing it, clears the token stored for it in the same write, and the plugin is switched off and stored off first (`SettingsStore.secrets_changing`, a listener that runs before the file is written; when it fails, nothing is written and the answer is 500), so neither a failed write nor a crash in between can leave a plugin stored on that would start at the new address by itself; it runs again only when a token is entered and a person switches it on. The same address again changes nothing, also spelled differently (host case, a default port, an empty path against `/`). A token cannot be set before its address ("set COOLIFY_URL first"), and is stored only with the `version` of the address it was typed for (`address_version` in the body: 428 without it, 409 when the address changed since), so a token typed in a tab that read address A is never stored with address B another tab set meanwhile. The version is an HMAC of the address under a key made at each start, so it says nothing about the address, and a page read before a restart reads again. An address and its token come whole from one place: when the env sets either, both are read from the env, and the dashboard can change neither; a token the env sets is never sent to an address the dashboard set, nor a dashboard token to an env address. `Plugin.connection` names the pair (Coolify's, the MCP plugin's). Reason: a dashboard session must never be able to send an existing token to an address it chose; that is why the addresses were env-only before (#38, #43), and this rule replaces that one (#135).
- **An address set from the dashboard must be https and reach public addresses only; plain http, and anything on a private network, can be set in `.env` only.** The two model servers' addresses are the exception ([below](#models-embeddings-and-tracing-from-the-dashboard-372)). At `PUT` the address must pass `check_url` and be https, and its name must resolve, every answer public: not private, loopback, link-local (cloud metadata), CGNAT (100.64/10), unique-local IPv6, unspecified, reserved or multicast, nor an IPv4-mapped, 6to4, Teredo or NAT64 form of one; an IPv6 address must be global unicast (2000::/3), so IPv4-compatible, SIIT and site-local forms are refused too (`plugins/urls.is_public`). An address literal is judged without a lookup. The check runs again at every connection the plugin makes (`PublicOnlyTransport`, given to the plugin as `PluginContext.public_only`): the name is resolved, every answer checked, and the request sent to the first checked address, with the name kept in the Host header and in TLS (SNI and the certificate check), so a name that resolves elsewhere later (DNS rebinding) or a redirect to another host is checked again. A failing check fails the call as an outage, `AddressRefused` (a `ConnectError`), logged and shown by its type only. Each request through it has its own connection. An address the env sets keeps the rule as it was. Reason: a dashboard session must not be able to aim Bleep's plugin client at the Docker API (the demo's socket proxy, a host's TCP endpoint) or another service on Bleep's own networks: the MCP plugin's token is optional, so the address alone made Bleep POST wherever it named, outside the approval gate (#135).
- **A change takes effect without a restart of Bleep: at the next use, or by restarting only the part that holds it.** The store tells its listeners which names changed (`SecretStore.subscribe`), never the values. The model key is read at every model call (`SettingsStore.models`), the GitHub token at every request (`GithubClient`), the embeddings key at every call (`OpenAICompatEmbedder`). A plugin that uses a changed value and is switched on is built again with the values in force; one whose required value is now unset stops and waits for it ("On, waiting for"), never running on with the old one. A changed Telegram token or chat id stops the poller, closes the old client, builds the bot again and starts polling with it, from the last update the old bot confirmed when the token is the same (so a new chat id gets nothing delivered twice; an update being handled when the poller stops is cut off, as on a restart); the notifier object stays, so the graph, the runner and the reminders send with the new bot, and a message being sent during the swap fails as in an outage. A changed tracing key builds the tracer again (`ReloadingTracer`) and closes the old one; a tracer that fails to build turns tracing off, never left on the old key; a run already going keeps the callbacks it was given. A listener that fails is logged by its error's type and the value stays stored. Reason: one mechanism, listeners by name, and the parts that read at each use need none (#135).
- **A tracing key that `TRACING` in the env needs cannot be cleared from the dashboard** (it can be replaced). Bleep still refuses to start with `TRACING` set in the env and its keys missing from both places ([observability](observability.md)). Reason: clearing it would leave a Bleep that refuses its next start, which the dashboard could not fix (#135). A `TRACING` chosen on the dashboard (#372) is held to less, [below](#models-embeddings-and-tracing-from-the-dashboard-372).
- **`BLEEP_ADMIN_PASSWORD` and `BLEEP_SECRET` stay in the env only, and are not on the list.** Reason: the dashboard is behind them: the login checks the one, and sessions and approval grants are signed with the other (#135).
- **Addresses other than a plugin's stayed in the env until #372**, which made each one settable and bound to its key ([below](#models-embeddings-and-tracing-from-the-dashboard-372)). Reason: an address that could be changed from the dashboard while its key stays would send that key wherever a session chose (#135).
- **The GitHub token from the dashboard is used when the hosts file names `{env: GITHUB_TOKEN}` or has no `github` section.** A hosts file that names a file or another variable keeps it, read at start as before ([hosts](hosts.md)). Reason: a token pointed at by the hosts file is the operator's choice (#135).
- **Limits.** The file is not encrypted (above). The settings page sets and clears them (#202). The env is read live for a name the env decides, but a variable added to the env reaches Bleep only through a restart of its container, as before.

## Models, embeddings and tracing from the dashboard (#372)

Bleep runs without editing `.env` beyond the first start: the model, the embeddings and tracing can be set from the dashboard too. Only `BLEEP_SECRET`, `BLEEP_ADMIN_PASSWORD`, `BLEEP_HOSTS_FILE` and `BLEEP_COOKIE_SECURE` stay env-only, since Bleep needs them before anyone can log in. The backend is `PUT /api/settings`'s `models`, `embeddings` and `tracing` sections and the secret file's model server addresses (the first part); the settings page's forms for them are the second ([the page](#the-settings-page-41), #433).

- **The non-secret settings live in the database, next to the time zone and the language; the keys and the model servers' addresses in the secret file.** `models` holds `provider`, `model`, `cheap_model` and `local_model`; `embeddings` holds `provider` (`local`, the built-in model; `server`, a local server; `openai`, an endpoint with a key; #442), `model` and `min_score`; `tracing` holds `tracing` (`off`, `langfuse`, `langsmith`), `langfuse_base_url`, `langfuse_ui_url`, `langfuse_project_id`, `langsmith_endpoint` and `langsmith_project` (`schemas/settings.py`). `LOCAL_BASE_URL` and `EMBEDDINGS_BASE_URL` are addresses in the secret file, as a plugin's are, since `EMBEDDINGS_BASE_URL` carries `EMBEDDINGS_API_KEY`. Reason: the secret file holds what is secret or bound to a secret, the settings table everything else, and each keeps its own checks: the settings' secret check refuses a URL with a password or a key in it (#372).
- **A field the env sets wins, and the dashboard cannot change it.** The store reads which fields the env set (the model choice from `ModelSettings`, the embeddings from `Settings`, tracing from `TracingSettings`); `GET /api/settings` names them in `from_env` as `section.field` (`models.provider`), and a `PUT` that changes one is a 422 naming the variable ("LLM_MODEL is set in the environment (.env or Compose), which wins; change it there"). The environment is `.env` and what a Compose file sets: `docker-compose.observability.yaml` sets `TRACING` and every Langfuse value. An override stored before the env set the field is kept but not in force, and the start's log names it ("the dashboard's LLM_MODEL is not in force"); it may be sent again as it is, or left out to clear it, so a form built from the overrides still saves its other fields. This turned the model choice's precedence round: before #372 a dev panel override won over `LLM_MODEL`. `.env.example` leaves `LLM_PROVIDER` and `LANGSMITH_PROJECT` empty (their defaults are the same), so a copied `.env` decides nothing it does not mean to. Reason: the rule secrets have since #135, so a Compose or CI setup that keeps `.env` is never silently overridden, and the page can say "Set in .env" instead of leaving a person guessing which value Bleep uses (#372).
- **What applies at once and what at the next start.** The model choice and `LOCAL_BASE_URL` apply at the next model call: the graph and the chat build their models from `SettingsStore.models()` as each node runs. LangSmith tracing applies at once, and so does switching tracing off from LangSmith or on to either tracer: a change of the `tracing` section or of a tracing key builds the tracer again (`ReloadingTracer.reload`, the store's listener in `wiring.subscribe_reloads`), and a run already going keeps the callbacks it was given. A running Langfuse tracer is never built again: a change to its keys, address or project applies at the next start, and `restart_needed` lists `tracing` until then (`ReloadingTracer.restart_needed`, given to the store with `restart_when`). Switching it off or to LangSmith, or clearing one of its keys, applies at once: the tracer becomes the one now in force and the Langfuse one is closed, so incident text never goes out with a key that was cleared. Switching Langfuse on again with a public key a client was already made for in this process waits for the next start too (tracing stays off until then), since that client would come back with its old address; with a key not used before, it applies at once. `EMBEDDINGS_BASE_URL` and `EMBEDDINGS_API_KEY` apply at the next embedding: `OpenAICompatEmbedder` reads both at each call. The embeddings `provider`, `model` and `min_score` apply at the next start: the embedder is built once, at its first use after the stored settings are loaded (`memory.embeddings.DeferredEmbedder`, the re-embed at boot), and `GET /api/settings` lists `embeddings` in `restart_needed` while the embedder the saved choice would build differs from the one running (`SettingsStore.embedder_choice`: an endpoint without its model or address is the local model, and the local model ignores `model`, so neither shows a restart that would change nothing). Only a provider or model change re-embeds: vectors are stored under the embedder's name, and `min_score` only moves recall's cut-off. Reason: a model and a LangSmith tracer are cheap to build again. Langfuse keeps one client per public key for the life of the process (`LangfuseResourceManager._instances`): a second `Langfuse` with the same public key gets the first one's address and secret key back, and shutting the first down shuts what the second shares, so building it again would send the keys to the old address while the API showed the new one. A new embedder means re-embedding the memory and the knowledge index (`MemoryStore.reembed` at boot, the knowledge refresher's next pass), and swapping it under a running search would mix vectors of two models in one table, so the restart Bleep already does that work at is the honest point (#372).
- **A model server's address set from the dashboard may be private: `LOCAL_BASE_URL` and `EMBEDDINGS_BASE_URL`, and only these.** They are held to the rule of an address in `.env` (`plugins/urls.check_url`): http(s) with a host, no password, query or fragment, and plain http only to a private or loopback address, a Docker service name, or a name under `.internal` (`host.docker.internal`); the name is not resolved and no public-only check runs at connection. `GET /api/secrets` marks them `private: true`, and their row in the Secrets panel says a private address may be set instead of the plugins' https rule. Every other address the dashboard sets, a plugin's and a tracer's, stays https to public addresses only. Reason: a local model and a local embeddings server usually listen on this machine or the LAN (`host.docker.internal:1234`, `192.168.x`, `10.x`), so the public-only rule would make them `.env`-only and defeat the point of the issue. The risk the rule guards against is a session aiming Bleep at the Docker API or another service on its networks: the local model's client sends no key (`api_key="local"`), only incident text, which the person running a local model wants sent there; the embeddings client sends memory text and the key typed for that address. `.internal` is the top-level domain reserved for private use, so no public name is under it. A cloud metadata service is refused by name (`metadata`, `metadata.google.internal`, `instance-data`, `instance-data.ec2.internal`), at any link-local address (169.254.169.254) and at AWS's IPv6 `fd00:ec2::254` and Alibaba Cloud's `100.100.100.200`, over http or https (`plugins/urls.METADATA_NAMES`, `METADATA_ADDRESSES`); the list is best effort, the services known when it was written. The rest of the risk is low: what the clients send is a blind POST to `/chat/completions` or `/embeddings` whose answer is never shown to anyone as is, so it reads nothing from the service it lands on; and a metadata service serves its data to a GET, which the clients never send, Google's only with a `Metadata-Flavor: Google` header and AWS's IMDSv2 only with a token from a PUT, neither of which Bleep sends (#372).
- **A model server's address is still bound to its key, as a plugin's is.** `EMBEDDINGS_BASE_URL` carries `EMBEDDINGS_API_KEY`: a new or cleared address clears the key in the same write, a key cannot be set before its address, and it is stored only with the `version` of the address it was typed for ([above](#secrets-from-the-dashboard-135)). They come whole from one place: when the env sets either, both are read from the env, so an `EMBEDDINGS_API_KEY` set on the dashboard is no longer used while `EMBEDDINGS_BASE_URL` is in `.env`, and the start's log says so ("EMBEDDINGS_API_KEY in the secret file is not used", `SecretStore._warn_shadowed`, for any value the env decides); put both in one place. `LOCAL_BASE_URL` carries no key. The address cannot be cleared while the endpoint is the running embedder (409, `SettingsStore.clear_refused`): every embed would fail until a restart, and recall with it; choosing the local model and restarting first ends that. A new address is accepted, since the embedder reads it at the next call. Reason: the binding is what lets an address be changed from the dashboard at all (#135, #372).
- **A tracer's address is a setting, held to its keys by the store: it changes only while the keys sent to it are unset, and from the env when the env sets one of them.** `LANGFUSE_BASE_URL` carries `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY`, `LANGSMITH_ENDPOINT` carries `LANGSMITH_API_KEY` (`TRACING_ENDPOINTS`). A `PUT` that changes one while a key for it is set is a 422 ("clear LANGSMITH_API_KEY first ..."), so the order is: clear the key, set the address, enter the key again. When the env sets a key, the address is read from the env (or its default), the dashboard's override is not in force and a change is a 422 ("LANGSMITH_API_KEY is set in the environment (.env or Compose), so LANGSMITH_ENDPOINT is read from there too"). An address changed from the dashboard must be https and resolve to public addresses only, checked at the `PUT` (`api/settings.check_tracing_addresses`). `LANGFUSE_UI_URL` is only a link a browser opens and carries nothing. An address the env decides is shown by `GET /api/settings` as its origin only (`scheme://host[:port]`, `api/settings.shown_tracing`), as `GET /api/secrets` shows one, and one in the env with a user or password in it stops Bleep at start without quoting it (`wiring.tracing_env`). A project field (`langsmith_project`, `langfuse_project_id`) that looks like a key is a 422: one starting `lsv2_`, `pk-lf-` or `sk-lf-`, an OpenAI-style `sk-` with 20 or more characters after it, or one holding a run of 32 or more letters and digits mixed that is not a UUID's 32 hex digits (`schemas/settings.ProjectName`); a Langfuse project id (a 25-character cuid), a UUID and a name such as `sk-team` are kept. The secret check does not know the LangSmith key's shape, and a project name reaches the database and the tracer's metadata. Reason: these addresses have defaults (LangSmith's US cloud, the Compose profile's `langfuse-web`), so a key may be set with no address set, which the secret file's address rule ("set the address first") would refuse; refusing the change while a key is set gives the same guarantee, that no key goes to an address it was not entered for, without that order (#372).
- **`TRACING` chosen on the dashboard needs its keys set first, and turns tracing off rather than stopping Bleep when they go.** Switching a tracer on is a 422 naming the missing keys. A key cleared later, or missing at the next start, turns tracing off with a warning ("tracing is off until they are set"); only `TRACING` in the env stops Bleep at start without its keys, as before. `ReloadingTracer` is made before the stored settings are loaded, so then it only checks the env's keys (`check_tracer`); the tracer and its client are built at their first use, which is after the load, so the first client already has the settings page's address. Reason: a Bleep that refuses to start over a setting only the dashboard can change could not be fixed from the dashboard (#135, #372).
- **An embeddings endpoint or local server needs its address and model.** Saving `provider: openai` or `provider: server` is a 422 until `EMBEDDINGS_BASE_URL` is set and a `model` is in force. One that is incomplete at start (its address cleared since, or `EMBEDDINGS_PROVIDER=openai` in `.env` without the rest) no longer stops Bleep: the built-in model embeds, the log says so, and `restart_needed` lists `embeddings` until the endpoint is complete and Bleep restarted. Reason: the address may now come from the dashboard, which is read only after `check_settings` runs (#372).
- **The Embeddings panel offers three embedders: the built-in model, a local server and an endpoint, and says in each option's label what it needs (#442).** `EMBEDDINGS_PROVIDER` is `local`, `server` or `openai`; `server` and `openai` share `EMBEDDINGS_BASE_URL` and `EMBEDDINGS_MODEL`, and only `openai` shows and sends `EMBEDDINGS_API_KEY`. `.env` still wins for the provider, model and min score, with no input. Which to pick: the built-in bge-small for English text or no setup; a local server (LM Studio, Ollama) running `bge-m3` for German or mixed-language logs and docs when a machine can keep it running (free, no key, 22 of 22 first on the German set, the first ingest in 15 s); an endpoint such as OpenRouter's `google/gemini-embedding-2` when no machine can ([embeddings](../decisions/embeddings.md), [local server](../evals/embeddings-local-server-2026-11-11.md)). Reason: a local server was an `openai` endpoint with a private address, which made the page ask for a key it never needs; naming it makes the key row, the stored vector name (`server:<model>`) and the log say what is running.
- **Limits.** A tracer's address is checked for public addresses at the `PUT` only: the Langfuse and LangSmith clients make their own connections, so a name that resolves elsewhere later is not checked again, unlike a plugin's (`PublicOnlyTransport`). Such an address is https and the clients verify its certificate, so a connection rebound to another address fails the TLS handshake before any key is sent, unless that address holds a certificate valid for the name. A key typed for a tracer's address in a tab that read the address before another tab changed it is stored for the new one: the secret file's address version covers its own addresses only, and a tracer's address cannot change while its key is set, so this needs the key to have been unset in between. The page's forms, the "Set in the environment" and restart notes, the question before an embeddings change and hiding `EMBEDDINGS_API_KEY` unless the provider is an endpoint are done, in [the settings page](#the-settings-page-41) (#433). The page's notes follow the API's `from_env` and `restart_needed` as the page last read them, not live, so a page left open keeps showing a restart as needed until it is reloaded or saves again.
