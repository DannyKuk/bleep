# Settings

What a person can change from the dashboard and how it takes effect (`backend/src/bleep/incidents/settings_store.py`, `api/settings.py`, `guard/secret_fields.py`, `store/secrets.py`, `api/secrets.py`). Non-secret settings are stored in SQLite. Secrets never are: they come from the environment, from files the hosts file names, or from the secret file the dashboard writes, apart from the database ([below](#secrets-from-the-dashboard-135), spec §4.10).

| Piece | Path | What it does |
|---|---|---|
| **Settings store** | `incidents/settings_store.py`, the `settings` table (`0001_init.sql`) | The overrides, one JSON row per section; the values in force, computed from the layers below; the graph's `SettingsSource`. |
| **Schemas** | `schemas/settings.py` | `SettingsUpdate` and its sections with their bounds, and `SettingsView`. |
| **Secret check** | `guard/secret_fields.py` | Finds a secret-shaped key or value anywhere in a body. |
| **Routes** | `api/settings.py` | `GET /api/settings` (values in force, the overrides and their `version`, each host's connection and whether the model key is set) and `PUT /api/settings`, which needs that version in `If-Match`. Each plugin's view (`GET /api/plugins`) carries its own `version`, which `PUT /api/plugins/{name}` needs the same way. |
| **Secret file** | `store/secrets.py`, `data/secrets.json` on the data volume | The secrets and plugin addresses set from the dashboard, mode 0600, apart from the database; the values in force (the env's, else the file's); who is told when one changes. |
| **Secret routes** | `api/secrets.py` | `GET /api/secrets` (each value's name, kind, whether it is set and where from, never a secret's value), `PUT /api/secrets/{name}` (`{"value": "..."}`) and `DELETE /api/secrets/{name}`. |
| **Settings page** | `frontend/components/settings/` | The dashboard's `/settings`: the forms for these settings and the read-only state of what stays in the env and the hosts file. |

## Choices

- **Precedence is database override > hosts file > defaults; the model choice's defaults come from the env.** The store keeps only what a person changed and computes the values in force on every read. Reason: clearing an override brings the hosts file's value back, and a hosts file edit still shows where nothing overrides it (#36).
- **A person can change the model choice (`provider`, `model`, `cheap_model`, `local_model`), the budgets, the thresholds, each host's rules and each service's URLs, rules and protected containers, and switch plugins.** The local model's base URL and every connection field of a hosts file host (address, key file, endpoint, socket) stay in the env and the hosts file, and an ssh host can be added, changed and removed from the dashboard, its key going to the secret file ([hosts](hosts.md#hosts-from-the-dashboard-194), #194); the API keys and the plugins' addresses can be set from the dashboard too, but only into the secret file ([below](#secrets-from-the-dashboard-135)). Reason: these are the settings the settings page and the dev panel edit; a base URL decides where incident text is sent, and a connection field where Bleep logs in (#36).
- **The `settings` table already existed from the first migration, so this needed none.** Each section is a row: `models`, `budgets`, `thresholds`, `host:<id>`, `plugin:<name>` (#36).
- **A `PUT` replaces each section it names and leaves the others; under `hosts` it replaces each host it names; `{}` clears.** Reason: the settings page and the dev panel write different sections, and one page open on old values must not undo the other's change (#36).
- **Every `PUT /api/settings` sends the `version` of the overrides it was built from in `If-Match`; without it the answer is 428, and when the overrides have changed since it is 409 with the current version, and nothing is applied.** `GET` and `PUT` return the version in the body and as the `ETag`. It is a hash of the overrides as they are stored (`SettingsStore.version`), so it holds across a restart, needs no column or migration, and the same content always has the same version; the check runs under the store's lock, so of two writers from one version only the first goes through. Reason: every form builds its section's whole body from the overrides it read, so without the check a stale tab, or the dev panel and the settings page saving at once, would silently put back what the other changed, such as unprotecting a container protected meanwhile (#41).
- **Each plugin has a version of its own on the same rules: a hash of its stored row (on or off, settings), in each `PluginView`, required in `If-Match` on `PUT /api/plugins/{name}`, 428 without it, 409 with the current one when stale.** `SettingsStore.plugin_view` waits for a save in progress and then reads the version and the settings with nothing in between, so the settings it shows are stored ones (`set_plugin` puts a change in force before it writes it, and restores the plugin when the write fails); a change made while the health check runs makes the version older than the view, never newer. One version for everything was the other choice; it was not taken because the page reads the plugins and the settings in separate requests, so a save of a threshold would make every plugin form stale, and a plugin read just before a change could carry a version that is already current. Reason: a plugin's `PUT` replaces all its settings, built from what the form read, and a plugin's settings can name the read tools it may run without approval, so a stale tab must not put a removed one back (#41, #132).
- **A plugin's secret that is optional (`required: false`, the MCP token) is shown neutrally as "Not set, optional" when unset; only a required one is "Missing".** Reason: an unset optional secret is not a broken setup (#132).
- **A Coolify application is protected by its name (as written in Coolify, or as its label slugs it) or its uuid**, not only by a container name: Coolify names an application's containers anew at each deploy, so a protected container name stops matching after the next one ([guard](guard.md#plan-check)) (#38).
- **A service's URLs and rules replace the hosts file's, but its protected containers are added to them: the dashboard can protect a container and never unprotect one the hosts file protects.** Reason: protection is a guard that blocks act tools even after an approval; lifting it should take an edit of the file on the server, not a click in a browser session (#36).
- **The layer under a host's overrides is the hosts file's host or the dashboard's.** `SettingsStore.host_changed` adds or replaces a dashboard host there when it is added or changed, and drops it and deletes its overrides when it is removed. Reason: the same rules, URLs and protected containers apply to both, and a host added again under a removed one's id must not inherit them (#194).
- **The merged host goes into the registry at once (`Registry.override`), which regroups the services from the last listing.** Reason: the URL checks, the plan check, Verify and Gather all read the host's config from the registry, so every one of them sees the same value from the next read on (#36).
- **Three budgets belong to model outages and stuck incidents:** `model_timeout_s` (default 120, 10 to 600), `paused_retry_min` (default 5, 1 to 240) and `stuck_after_min` (default 30, 5 to 1440). All are whole numbers, editable in the dev panel like the other budgets and read at the moment they are used ([incidents](incidents.md#model-outages-and-stuck-incidents), #86).
- **Every value takes effect without a restart.** The graph reads budgets, models and enabled actions from the store as each node runs; the detector reads the thresholds on every signal. Reason: a budget or a threshold is changed when it is wrong now (#36).
- **Budgets and thresholds have bounds**: for example 1 to 50 tool calls per round, a daily cap of $0 to $100, at most 5 verify loops, a disk threshold of 50 to 99 %, at least 1 % memory available, a load per CPU of 0.5 to 20, a low-confidence line of 0.1 to 0.95. A rule is at most 500 characters, a service at most 20 URLs. Reason: a typo must not switch a guard off or let one incident spend without end (#36).
- **A body is checked for secrets before it is validated, and refused with 422 naming where, never what.** Any key at any depth that looks like a secret's name is refused: the name is lower-cased with `_`, `-` and `.` removed and matched for `token`, `secret`, `passw`, `apikey`, `privatekey`, `credential` and similar, or ends in the word `key`, so `TOKEN`, `apiKey`, `x-api-key` and `Db_Password` all are. The settings models' own field names are trusted (`incident_tokens` is a budget). Any string, key or value, that redaction would change is refused too: a token in a rule, a password in a URL, a URL with a secret-named query parameter (`?key=`). Names and strings are also checked folded (NFKC, no invisible characters, look-alike letters mapped to Latin; a string over 4,000 characters read in overlapping 4,000-character windows instead of whole, so redaction never cuts it, #130), so `ｔｏｋｅｎ`, `pаssword` with a Cyrillic а and `pass​word` with a zero-width space are caught. The body is walked with a stack, so a deeply nested one is refused, not a crash, and a body over 100,000 characters as JSON is a 413 before the check reads it (`MAX_BODY_CHARS` in `api/settings.py`, also for plugin and prompt-override bodies), so its cost stays small (#130). Validation errors are returned with where and why but without the values sent, and a URL error says what a URL must be rather than quoting it. Reason: rules and URLs reach the model, the database must never hold a secret, and a 422 that echoes the body would put the secret in a response and in logs (#36).
- **A write body is capped by size before it is read: `BodyLimitMiddleware` (`api/body_limit.py`) refuses `PUT /api/settings`, `PUT /api/plugins/{name}` and `PUT /api/dev/prompts/{name}` with 413 when `Content-Length` is over 400,000 bytes, and for a chunked body stops reading at that cap.** The cap is `MAX_BODY_CHARS` (100,000) times 4, the most bytes a character takes in UTF-8, so a compact JSON body within the character limit is never refused (the dashboard sends `JSON.stringify` output; whitespace or `\uXXXX` escapes can make a raw body larger and it is refused); `check_size` still applies the exact character limit to the parsed JSON, and answers 422 instead of crashing for a body nested too deeply to measure. A middleware, not a dependency, because FastAPI parses the body before any dependency of a route with a `Body()` parameter runs, so only code in front of the routing can stop the read; it is scoped to these paths so other routes are untouched. Reason: a logged-in client could otherwise make the backend buffer a body of any size before the 413 (#167).
- **The check is stricter than redaction's own.** `token_file`, `key_file` and a service named `x-api-key` are refused here, though redaction would leave them. Reason: a settings key that only might be a secret costs a person a rename; a missed one costs a leak (#36).
- **A stored row is checked again on load, and one that no longer fits is left out with a warning**: a host gone from the hosts file, a field renamed, a value out of bounds or anything secret-shaped. Reason: Bleep must start on the layers below rather than refuse to start, and a row written behind the API's back gets no further than one written through it (#36).
- **What the check does not catch**: a password written as prose ("the db password is hunter2") and token formats redaction does not know. Reason: the check is defence in depth behind the rule that secrets go in the environment; a pattern for every format is redaction's work, not the settings page's (#117).
- **A person with a session can point URL checks at any http(s) host and switch the provider from local to OpenRouter.** Reason: both are what the settings page is for and need the admin login; the plan check's rule that only configured URLs may be verified is about what the model names, not what the admin configures (#36).

### The settings page (#41)

- **The settings page edits thresholds, each host's rules, each service's URLs, rules and protected containers, and the plugins; the model choice and the budgets are edited only in the dev panel.** The page shows the provider and the models in force read-only, with a link there; with the panel off, `PUT /api/settings` refuses `models` and `budgets` with 403 ([dev panel](dev-panel.md), #130). Reason: the dev panel holds the model, the prompts and the budgets (§4.6), and one place per setting means two pages can never fight over a section (#41).
- **A hosts file host's connection (`source: "file"`) is shown read-only, as the hosts file has it; a dashboard host's (`source: "dashboard"`) carries its key and host key as set or not and its `version` ([hosts](hosts.md#hosts-from-the-dashboard-194), #194).** For a hosts file host: kind, `user@address:port`, the Docker socket or the endpoint, the known hosts file, and the SSH key as its file and whether Bleep can read it. `GET /api/settings` gives it as each host's `connection`; the key file is a `SecretStatus` (`{env, file, set}`), `set` when it is a file Bleep's user may read (`is_file()` and `os.access(R_OK)`), and it is never opened. Userinfo in an endpoint or address is replaced, up to its last `@` (`tcp://<redacted>@proxy:2375`). Reason: where Bleep logs in is the hosts file's to say (#36), but a person debugging an unreachable host needs to see it, a key file that is not mounted or not readable is the first thing to rule out, and a password in an endpoint URL must not reach a browser (#41).
- **Every secret shows as set or missing with where it is kept, and the settings page sets and clears it** (#41, #202). The model key is `model_key` in `GET /api/settings` (the variable `OPENROUTER_API_KEY`, set or not, whatever the provider), a plugin's secrets come from `GET /api/plugins`, the Telegram token from `GET /api/telegram/status`; where each is kept ("Set in .env", "Set on the dashboard") comes from `GET /api/secrets`, so a dashboard-set value is never said to come from the env. The field is named `model_key`, not `api_key`, so the existing test that no `api_key` reaches the response still holds. Reason: §4.10; a person must be able to tell why something is off without the value ever leaving the server (#41).
- **A protected container from the hosts file is shown with a lock and no remove button; only the ones added on the dashboard can be removed.** `ServiceSettingsView.hosts_file_protected_containers` says which are the file's, since `protected_containers` is the merged list. Reason: the dashboard can never unprotect what the hosts file protects (#36), and a remove button that does nothing would look like it did (#41).
- **The page lists every service Bleep sees on a host (`GET /api/services`) and every one the hosts file or the database has settings for.** A service with neither shows empty lists. Reason: a person adds the first URL or rule to a service from the dashboard, not only to the ones the hosts file already names (#41).
- **Each save sends the whole section it changes, built from the overrides: a service's change goes as that host's overrides with only that service's field replaced, and thresholds as the overrides already there plus the changed values.** "Use the hosts file's" drops the one field; "Back to the defaults" sends `thresholds: {}`. Reason: `PUT /api/settings` replaces each section and each host it names (#36), so a body built from the values in force would turn every hosts file value into an override (#41).
- **The forms do not repeat the bounds, not even a `maxLength` on an input; the API's 422 is shown under the form that sent it, named as the form names the field** ("Disk used at or above: Input should be less than or equal to 99", "Rule 1: String should have at most 500 characters", "URL 2: …"), and Bleep's own refusals (a secret in a rule, an unknown host) as the API words them. A value that is not a number is sent as typed for the API to refuse. The draft stays after a refusal. A URL row left empty is the one thing checked on the page: it is marked invalid and nothing is sent, rather than the row being dropped. Reason: the bounds live in `schemas/settings.py` only, so the page cannot drift from them, and an input that cuts text off as it is typed hides that anything was lost (#41).
- **After a 409 the page reads the settings (or the plugins) again and says the save was not applied because they changed elsewhere; it never retries.** When that read fails too it says so and asks for a reload, instead of claiming the page is current. Each save sends the version of the view its body was built from, and only one save on the page is in flight at a time (`components/save-lock.tsx`: every Save waits while one runs), so the next is built from the last one's result. Reason: a retry would send the same stale body with a fresh version and put back what the other writer changed; and two saves from one view would make the second a 409 for no reason (#41).
- **A plugin switched on that does not run shows "On, waiting for" its unset required secrets (or "On, not running" when its code failed to build), with a Switch off button.** `PluginView.switched_on` is the stored toggle, apart from `enabled` (on and running); at boot a stored "on" whose secret is unset keeps its row (#36), and the boot log says it "stays switched on but does not run", not that it was left out. Switching it off stores off, so it stays off when the secret comes back. Reason: before, the view said only `enabled: false`, so the page offered "Switch on" and the plugin came back on by itself after the next restart with the secret set (#141).
- **A plugin's invalid settings are a 422 naming each field with pydantic's reason** ("plugin coolify: invalid settings (deploy_timeout_s: Input should be greater than or equal to 60)"), without the value sent. Reason: the same "where and why" as the settings' own errors above; a field name alone did not say what to fix (#141).
- **`GET /api/plugins` runs the plugins' health checks together** (`asyncio.gather`), each still bounded to 5 s. Reason: the page reads the list on load and again after every 409, and one after another it waited up to 5 s per plugin (#141).
- **A protected entry may hold spaces and `:`** (`Shop API`, `name:main`), up to 255 characters and trimmed, but no control character (`schemas/settings.py` `ContainerName`); a secret-shaped one is still refused by the secret check. Reason: a Coolify application is protected by its name as written in Coolify, which the plan check slugs (#134), and the old container-name pattern refused it (#141).
- **A protected name whose Coolify slug is empty (only symbols or emoji, such as `🚀`) is refused with a 422 that says to protect the application by its uuid, instead of being stored.** `put_settings` checks each protected name with `coolify_slug` (`api/settings.py` `refuse_names_without_a_slug`); the hosts file only warns at startup for the same name ([guard](guard.md#plan-check)). Reason: such a name matches no application by slug, so a saved entry would show as protected and protect nothing, and a refusal is shown by the dashboard as it is for any 422; a Docker container name starts with a letter or digit, so no real container is refused (#176).
- **The page's types are in `frontend/lib/settings-types.ts`, written by hand next to `api-types.ts`.** Reason: until `npm run gen:api` replaces both, a separate file keeps the settings contract out of the way of the other pages' types (#41).

## Secrets from the dashboard (#135)

Every secret Bleep reads from `.env` can also be set from the dashboard, and so can the plugins' addresses: the model key (`OPENROUTER_API_KEY`), the Telegram token and chat id, `GITHUB_TOKEN`, `EMBEDDINGS_API_KEY`, the Langfuse and LangSmith keys, and `COOLIFY_URL`/`COOLIFY_TOKEN` and `MCP_URL`/`MCP_TOKEN`. `wiring.secret_names` is the list; a name not on it is a 404.

- **They live in one file apart from the database: `secrets.json` in the data directory (`/data` in the backend container, the `bleep-data` volume), next to `bleep.db`.** It is JSON, mode 0600, owned by the backend's user (uid 10001 in the image). Every write goes to a temporary file in the same directory, created 0600 (`mkstemp`, then `fchmod` to say so), flushed and synced, then renamed over the old one, so the file is never readable by another user, not even halfway through a write, and a failed write leaves the old file whole. The directory is synced after the rename, so the rename survives a power loss. At boot the file is opened without following a link (`O_NOFOLLOW`): a link or anything but a regular file at the path stops Bleep, and nothing is read or chmodded through it. A file found readable by others is set to 0600 with a warning; one that is not valid JSON in Bleep's format stops Bleep with its path and "fix or delete it", never its content. Temporary files left by a write the process did not live to finish (`.secrets-*.tmp`, which hold secrets too) are deleted. A name in the file that Bleep no longer knows is left out with a warning. Reason: CLAUDE.md's rule that secrets never live in the database holds as written: nothing of the file reaches SQLite, the checkpoints, the bus or the guard log (`tests/api/test_secrets.py` reads `bleep.db` for the value) (#135).
- **Who can read it: the backend's user, and anyone who can read the data volume as root**, which on the Docker host means root and anyone in the `docker` group (any container that mounts the volume reads it). The file is not encrypted. Reason: a key to decrypt it would have to live on the same host, in the env or another file the same people can read; encrypting it with a key held elsewhere is a later step if the threat model needs it (#135).
- **A backup of the data volume holds the secrets in clear.** Treat a copy of `bleep-data` (or of `/data`) like the `.env` file: keep it where only the people who may read the tokens can, and revoke the tokens when a copy is lost. `docker compose down -v` deletes the file with the database. Restoring a backup brings back the secrets as they were when it was taken. Reason: the file sits on the volume so that a restart, an upgrade and a backup keep it together with the database it belongs to (#135).
- **The API is write-only.** `GET /api/secrets` names each value with its kind (`secret`, `address`, `id`), whether it is set, where it comes from (`env` or `dashboard`), whether the env decides it (`env_owned`) and, for an address, the token it carries; never a secret's value. Of an address set on the dashboard it gives only the origin (`https://host[:port]`) and an opaque `version`; of an address the env sets, nothing beyond set and source; a dashboard address in the file that Bleep would not accept now (the file edited by hand) is `invalid: true` with no part of it shown, and its plugin is refused at switch-on; the chat id is masked to its last two characters. `PUT` and `DELETE` answer the same list. A value is checked before it is stored: not empty, at most 16,384 characters, no control character (C0, DEL, C1), no invisible format character and no line or paragraph separator, and an address as below. Reason: a path can hold a credential (a hosted MCP server's endpoint often does), and the env's address was never the API's to show (#135). A refusal says why in Bleep's words, a body that does not fit is a 422 without the input (FastAPI's own 422 would echo it), and `BodyLimitMiddleware` caps the body before it is read. The log says only "NAME set from the dashboard" or "cleared". Reason: the value must never come back to a browser, a log or an error, and the settings check refuses secret-shaped values, so this route reads its own small body and skips that check (#135).
- **The env wins.** A name the env sets (non-empty) is used from the env, shown as `source: env`, `env_owned: true`, and the dashboard can neither set nor clear it: 409, "change it there". Reason: Compose and CI setups keep `.env`, and a value that silently shadows or is shadowed by the other would leave a person guessing which one Bleep uses (#135).
- **A plugin's address is bound to its token.** Setting a new address from the dashboard, or clearing it, clears the token stored for it in the same write, and the plugin is switched off and stored off first (`SettingsStore.secrets_changing`, a listener that runs before the file is written; when it fails, nothing is written and the answer is 500), so neither a failed write nor a crash in between can leave a plugin stored on that would start at the new address by itself; it runs again only when a token is entered and a person switches it on. The same address again changes nothing, also spelled differently (host case, a default port, an empty path against `/`). A token cannot be set before its address ("set COOLIFY_URL first"), and is stored only with the `version` of the address it was typed for (`address_version` in the body: 428 without it, 409 when the address changed since), so a token typed in a tab that read address A is never stored with address B another tab set meanwhile. The version is an HMAC of the address under a key made at each start, so it says nothing about the address, and a page read before a restart reads again. An address and its token come whole from one place: when the env sets either, both are read from the env, and the dashboard can change neither; a token the env sets is never sent to an address the dashboard set, nor a dashboard token to an env address. `Plugin.connection` names the pair (Coolify's, the MCP plugin's). Reason: a dashboard session must never be able to send an existing token to an address it chose; that is why the addresses were env-only before (#38, #43), and this rule replaces that one (#135).
- **An address set from the dashboard must be https and reach public addresses only; plain http, and anything on a private network, can be set in `.env` only.** At `PUT` the address must pass `check_url` and be https, and its name must resolve, every answer public: not private, loopback, link-local (cloud metadata), CGNAT (100.64/10), unique-local IPv6, unspecified, reserved or multicast, nor an IPv4-mapped, 6to4, Teredo or NAT64 form of one; an IPv6 address must be global unicast (2000::/3), so IPv4-compatible, SIIT and site-local forms are refused too (`plugins/urls.is_public`). An address literal is judged without a lookup. The check runs again at every connection the plugin makes (`PublicOnlyTransport`, given to the plugin as `PluginContext.public_only`): the name is resolved, every answer checked, and the request sent to the first checked address, with the name kept in the Host header and in TLS (SNI and the certificate check), so a name that resolves elsewhere later (DNS rebinding) or a redirect to another host is checked again. A failing check fails the call as an outage, `AddressRefused` (a `ConnectError`), logged and shown by its type only. Each request through it has its own connection. An address the env sets keeps the rule as it was. Reason: a dashboard session must not be able to aim Bleep's plugin client at the Docker API (the demo's socket proxy, a host's TCP endpoint) or another service on Bleep's own networks: the MCP plugin's token is optional, so the address alone made Bleep POST wherever it named, outside the approval gate (#135).
- **A change takes effect without a restart of Bleep: at the next use, or by restarting only the part that holds it.** The store tells its listeners which names changed (`SecretStore.subscribe`), never the values. The model key is read at every model call (`SettingsStore.models`), the GitHub token at every request (`GithubClient`), the embeddings key at every call (`OpenAICompatEmbedder`). A plugin that uses a changed value and is switched on is built again with the values in force; one whose required value is now unset stops and waits for it ("On, waiting for"), never running on with the old one. A changed Telegram token or chat id stops the poller, closes the old client, builds the bot again and starts polling with it, from the last update the old bot confirmed when the token is the same (so a new chat id gets nothing delivered twice; an update being handled when the poller stops is cut off, as on a restart); the notifier object stays, so the graph, the runner and the reminders send with the new bot, and a message being sent during the swap fails as in an outage. A changed tracing key builds the tracer again (`ReloadingTracer`) and closes the old one; a tracer that fails to build turns tracing off, never left on the old key; a run already going keeps the callbacks it was given. A listener that fails is logged by its error's type and the value stays stored. Reason: one mechanism, listeners by name, and the parts that read at each use need none (#135).
- **A tracing key that `TRACING` needs cannot be cleared from the dashboard** (it can be replaced), and `TRACING` itself stays in the env. Bleep still refuses to start with `TRACING` set and its keys missing from both places ([observability](observability.md)). Reason: clearing it would leave a Bleep that refuses its next start, which the dashboard could not fix (#135).
- **`BLEEP_ADMIN_PASSWORD` and `BLEEP_SECRET` stay in the env only, and are not on the list.** Reason: the dashboard is behind them: the login checks the one, and sessions and approval grants are signed with the other (#135).
- **Addresses other than a plugin's stay in the env**: `LOCAL_BASE_URL`, `EMBEDDINGS_BASE_URL`, `LANGFUSE_BASE_URL`, `LANGSMITH_ENDPOINT`. A key set from the dashboard for one of them is sent to the address the env names. Reason: only a plugin's address is bound to its token; an address that could be changed from the dashboard while its key stays would send that key wherever a session chose (#135).
- **The GitHub token from the dashboard is used when the hosts file names `{env: GITHUB_TOKEN}` or has no `github` section.** A hosts file that names a file or another variable keeps it, read at start as before ([hosts](hosts.md)). Reason: a token pointed at by the hosts file is the operator's choice (#135).
- **Limits.** The file is not encrypted (above). The settings page has no inputs for these yet; the API is in place. The env is read live for a name the env decides, but a variable added to the env reaches Bleep only through a restart of its container, as before.
