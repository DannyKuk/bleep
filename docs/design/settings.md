# Settings

What a person can change from the dashboard and how it takes effect (`backend/src/bleep/incidents/settings_store.py`, `api/settings.py`, `guard/secret_fields.py`). Secrets stay in the environment or in files the hosts file names; only non-secret settings are stored, in SQLite (spec §4.10).

| Piece | Path | What it does |
|---|---|---|
| **Settings store** | `incidents/settings_store.py`, the `settings` table (`0001_init.sql`) | The overrides, one JSON row per section; the values in force, computed from the layers below; the graph's `SettingsSource`. |
| **Schemas** | `schemas/settings.py` | `SettingsUpdate` and its sections with their bounds, and `SettingsView`. |
| **Secret check** | `guard/secret_fields.py` | Finds a secret-shaped key or value anywhere in a body. |
| **Routes** | `api/settings.py` | `GET /api/settings` (values in force, the overrides, each host's connection and whether the model key is set) and `PUT /api/settings`. |
| **Settings page** | `frontend/components/settings/` | The dashboard's `/settings`: the forms for these settings and the read-only state of what stays in the env and the hosts file. |

## Choices

- **Precedence is database override > hosts file > defaults; the model choice's defaults come from the env.** The store keeps only what a person changed and computes the values in force on every read. Reason: clearing an override brings the hosts file's value back, and a hosts file edit still shows where nothing overrides it (#36).
- **A person can change the model choice (`provider`, `model`, `cheap_model`, `local_model`), the budgets, the thresholds, each host's rules and each service's URLs, rules and protected containers, and switch plugins.** The local model's base URL, every API key and every connection field (address, key file, endpoint, socket) stay in the env and the hosts file. Reason: these are the settings the settings page and the dev panel edit; a base URL decides where incident text is sent, and a connection field where Bleep logs in (#36).
- **The `settings` table already existed from the first migration, so this needed none.** Each section is a row: `models`, `budgets`, `thresholds`, `host:<id>`, `plugin:<name>` (#36).
- **A `PUT` replaces each section it names and leaves the others; under `hosts` it replaces each host it names; `{}` clears.** Reason: the settings page and the dev panel write different sections, and one page open on old values must not undo the other's change (#36).
- **A service's URLs and rules replace the hosts file's, but its protected containers are added to them: the dashboard can protect a container and never unprotect one the hosts file protects.** Reason: protection is a guard that blocks act tools even after an approval; lifting it should take an edit of the file on the server, not a click in a browser session (#36).
- **The merged host goes into the registry at once (`Registry.override`), which regroups the services from the last listing.** Reason: the URL checks, the plan check, Verify and Gather all read the host's config from the registry, so every one of them sees the same value from the next read on (#36).
- **Every value takes effect without a restart.** The graph reads budgets, models and enabled actions from the store as each node runs; the detector reads the thresholds on every signal. Reason: a budget or a threshold is changed when it is wrong now (#36).
- **Budgets and thresholds have bounds**: for example 1 to 50 tool calls per round, a daily cap of $0 to $100, at most 5 verify loops, a disk threshold of 50 to 99 %, at least 1 % memory available, a load per CPU of 0.5 to 20, a low-confidence line of 0.1 to 0.95. A rule is at most 500 characters, a service at most 20 URLs. Reason: a typo must not switch a guard off or let one incident spend without end (#36).
- **A body is checked for secrets before it is validated, and refused with 422 naming where, never what.** Any key at any depth that looks like a secret's name is refused: the name is lower-cased with `_`, `-` and `.` removed and matched for `token`, `secret`, `passw`, `apikey`, `privatekey`, `credential` and similar, or ends in the word `key`, so `TOKEN`, `apiKey`, `x-api-key` and `Db_Password` all are. The settings models' own field names are trusted (`incident_tokens` is a budget). Any string, key or value, that redaction would change is refused too: a token in a rule, a password in a URL, a URL with a secret-named query parameter (`?key=`). Names and strings are also checked folded (NFKC, no invisible characters, look-alike letters mapped to Latin), so `ｔｏｋｅｎ`, `pаssword` with a Cyrillic а and `pass​word` with a zero-width space are caught. The body is walked with a stack, so a deeply nested one is refused, not a crash. Validation errors are returned with where and why but without the values sent, and a URL error says what a URL must be rather than quoting it. Reason: rules and URLs reach the model, the database must never hold a secret, and a 422 that echoes the body would put the secret in a response and in logs (#36).
- **The check is stricter than redaction's own.** `token_file`, `key_file` and a service named `x-api-key` are refused here, though redaction would leave them. Reason: a settings key that only might be a secret costs a person a rename; a missed one costs a leak (#36).
- **A stored row is checked again on load, and one that no longer fits is left out with a warning**: a host gone from the hosts file, a field renamed, a value out of bounds or anything secret-shaped. Reason: Bleep must start on the layers below rather than refuse to start, and a row written behind the API's back gets no further than one written through it (#36).
- **What the check does not catch**: a password written as prose ("the db password is hunter2") and token formats redaction does not know. Reason: the check is defence in depth behind the rule that secrets go in the environment; a pattern for every format is redaction's work, not the settings page's (#117).
- **A person with a session can point URL checks at any http(s) host and switch the provider from local to OpenRouter.** Reason: both are what the settings page is for and need the admin login; the plan check's rule that only configured URLs may be verified is about what the model names, not what the admin configures (#36).

### The settings page (#41)

- **The settings page edits thresholds, each host's rules, each service's URLs, rules and protected containers, and the plugins; the model choice and the budgets are edited only in the dev panel.** The page shows the provider and the models in force read-only, with a link there. Reason: the dev panel holds the model, the prompts and the budgets (§4.6), and one place per setting means two pages can never fight over a section (#41).
- **A host's connection is shown read-only, as the hosts file has it: kind, `user@address:port`, the Docker socket or the endpoint, the known hosts file, and the SSH key as its file and whether that file is there.** `GET /api/settings` gives it as each host's `connection`; the key file is a `SecretStatus` (`{env, file, set}`), checked with `Path.is_file()` and never read. Reason: where Bleep logs in is the hosts file's to say (#36), but a person debugging an unreachable host needs to see it, and a key file that is not mounted is the first thing to rule out (#41).
- **Every secret shows as "Set via env NAME" or "Missing: env NAME", and there is no input for any.** The model key is `model_key` in `GET /api/settings` (the variable `OPENROUTER_API_KEY`, set or not, whatever the provider), a plugin's secrets come from `GET /api/plugins`, the Telegram token from `GET /api/telegram/status`. The field is named `model_key`, not `api_key`, so the existing test that no `api_key` reaches the response still holds. Reason: §4.10; a person must be able to tell why something is off without the value ever leaving the server (#41).
- **A protected container from the hosts file is shown with a lock and no remove button; only the ones added on the dashboard can be removed.** `ServiceSettingsView.hosts_file_protected_containers` says which are the file's, since `protected_containers` is the merged list. Reason: the dashboard can never unprotect what the hosts file protects (#36), and a remove button that does nothing would look like it did (#41).
- **The page lists every service Bleep sees on a host (`GET /api/services`) and every one the hosts file or the database has settings for.** A service with neither shows empty lists. Reason: a person adds the first URL or rule to a service from the dashboard, not only to the ones the hosts file already names (#41).
- **Each save sends the whole section it changes, built from the overrides: a service's change goes as that host's overrides with only that service's field replaced, and thresholds as the overrides already there plus the changed values.** "Use the hosts file's" drops the one field; "Back to the defaults" sends `thresholds: {}`. Reason: `PUT /api/settings` replaces each section and each host it names (#36), so a body built from the values in force would turn every hosts file value into an override (#41).
- **The forms do not repeat the bounds; the API's 422 is shown under the form that sent it, named as the form names the field** ("Disk used at or above: Input should be less than or equal to 99", "URL 2: …"), and Bleep's own refusals (a secret in a rule, an unknown host) as the API words them. A value that is not a number is sent as typed for the API to refuse. The draft stays after a refusal. Reason: the bounds live in `schemas/settings.py` only, so the page cannot drift from them (#41).
- **The page's types are in `frontend/lib/settings-types.ts`, written by hand next to `api-types.ts`.** Reason: until `npm run gen:api` replaces both, a separate file keeps the settings contract out of the way of the other pages' types (#41).
