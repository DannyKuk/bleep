# Watcher: detection

How raw signals become incidents, self-recoveries or nothing. The decision logic is `bleep/watcher/detector.py`: pure, with an injected clock, so it is tested without Docker.

## Pull model: `watcher/poller.py`, `events.py`

One `HostWatcher` per host ticks every 15 s (`BLEEP_WATCH_INTERVAL_S`). A tick is: reconnect if the host is down, `events(since=cursor, until=now)`, then `Registry.refresh` (which lists containers). It is pure code; no model is called.

- **Pull, not a live event stream.** Reason: Bleep reaches a few hosts over agentless SSH, and some sleep. A dropped link or a sleeping host is a non-event: the tick fails, and the next one reads from the same cursor and catches up. There is no stream state to repair and no reconnect-and-replay race. The limit is up to 15 s of detection delay and one listing per host per tick; at hundreds of hosts an agent on each host would be the right design (#13, decided by Danny 2026-11-02).
- **The cursor advances only after a successful tick,** and a failed tick emits nothing but its probe result. Reason: so a gap is replayed once in full, and a host that was asleep is never marked dead by silence (#13).
- **Events and the listing are fetched before anything is emitted,** and the watcher's state changes only then. Reason: a tick that fails halfway must be exactly repeatable (#13).
- **Event identity is (container id, action, time).** A remembered set, kept 120 s past the cursor, drops events that an overlapping or retried window returns again; the window bounds are inclusive, so the boundary event is returned twice by design. Reason: a retried tick must never emit a signal twice (#13).
- **Mapping.** `die` is `container_died` with exit code and the container's restart policy; `oom` is `oom`; `health_status: unhealthy` is `unhealthy`; a `restart` event with no `die` in the same batch is a `container_died` with no exit code. `restart_loop` stays the detector's. Reason: a restart policy firing is evidence of a death, but a single restart is not by itself a loop (#13).
- **Stopped on purpose is not a death.** A `stop` or `destroy` event for the container in the same batch removes its `die` and `restart`. A container that exited with 0 or 143 between two snapshots makes no signal either; the service shows `stopped`. Reason: `docker stop` and `compose stop` are choices, and a restart policy does not fire for them (#13).
- **`bleep.self` containers emit nothing,** by the event's own labels or the snapshot's (#13).
- **The snapshot diff catches what events missed, once.** A container that was running and is now gone, exited with a crash code, or has a higher restart count is reported as `container_died` on the tick where the change first shows. A death the diff reported is remembered, so a late event for the same death is skipped, even one stamped after the tick's window but before the listing was taken. A diff death carries the container's own time (its finish, or its new start after a restart), not the tick's, so a restart the diff caught still counts as a recovery in the detector. Reason: events can be lost (the engine backlog, a window cut short), and listing and events are read a moment apart (#13).
- **Every tick sends `host_unreachable` with `ok` to the detector,** true when the tick reached the host and false when not, so its 5-minute timer starts and resets (#13).
- **The detector is ticked with the containers of the same tick** (the watcher's `on_snapshot` hook, `WatcherManager.snapshot`, grouped by service id). Reason: the detector judges a recovery from `started_at` and state, which must come from the snapshot taken with the signal, not from an older one (#13).
- **A start before the death is never a recovery.** `Detector.tick` treats a container whose `started_at` is earlier than the death as the old run seen in a stale snapshot: not recovered, so it opens past grace if it never restarts. Reason: otherwise a snapshot taken just before the death would clear it (#14 review, #13).
- **The manager feeds the detector:** every signal goes through one shared `Detector`, and its snapshot hook ticks the detector with that host's fresh listing (#13, #15).
- **A host's pending deaths are judged only by that host's own listing.** `Detector.tick(now, states, host_id)` skips deaths on other hosts. A host that stops answering takes no listing, so a death seen just before it went quiet stays pending until it answers again, then is judged (recovered, or down past grace) by what it shows. Reason: judging it against the last listing while another host ticks would open a service incident for a host Bleep cannot see, a run that gathers nothing, and then the `host_unreachable` incident as a second page for one cause (#72).
- **Container deaths are keyed by host id and container name.** The detector's pending deaths, death history (the restart-loop count) and recoveries use `(host_id, name)`, never the name alone. Reason: hosts run same-named containers (every Coolify server has `coolify-db` and `coolify-proxy`), so a name-only key dropped one host's death while the other's was pending, let a recovery on one host clear the other's, and added deaths on two hosts into a false restart loop (#74).
- **A tick is bounded to 60 s and never raises;** a sink that fails is logged and the rest of the tick goes on. Reason: one hung call or one bad consumer must not stop a host's watching (#13).
- **Host basics (disk, memory, load) are not fed here.** They have their own cadence (60 s); the detector counts polls, so the 15 s tick must not feed them (#13).

## Manager, URL checks and host probes: `watcher/manager.py`, `http_checks.py`, `host_probe.py` (#15)

`WatcherManager` runs three loops per host: the pull watcher (15 s), the host probe (60 s) and the URL checks (30 s). Each loop is its own supervised task: if it dies of an error it is logged and started again, backing off 1, 2, 5, 15 then 60 s. Reason: one bug or one bad host must stop nothing else, and a watcher that quietly stops is worse than one that restarts.

- **Outcomes become actions in one place.** `OpenIncident` and `AttachSignals` both go to `IncidentRepo.open_or_attach`; the incident runner starts only when that call reports the incident as newly opened. Reason: the detector may ask to open again for a persistent breach (disk at 95 %), and two tasks may race on one subject; the repository decides, so a run starts exactly once per incident. An attach that finds no open incident (it closed in between) opens one and starts its run.
- **`start()` restarts unfinished runs first** (`IncidentRunner.recover_on_boot`), then starts watching. Reason: after a crash, runs that were mid-investigation go on from their checkpoints before new signals arrive.
- **A recovery is logged off the tick.** `Recovered` starts a background task that reads the last 50 log lines, asks the cheap model for one sentence and writes the `recovery_events` row. If the logs or the model fail, the row is still written, with a plain "no explanation" line. The call is in the usage ledger under `recoveries` and is skipped once the day's cost cap is spent ([dev panel](dev-panel.md), #130). Reason: a slow model call inside the tick would delay the next pull (the tick has a 60 s bound), and a recovery must never be lost for want of a sentence.
- **The recovery line's model call is bounded by the model guard.** `explain_recovery` runs under the same `ModelGuard` as the graph's calls (the `model_timeout_s` budget, retries on transient errors). If the model is still unreachable after the retries, the line is the plain fact "The container died and its restart policy brought it back.", the outage is logged by error type only, and the recovery row is written as usual. Reason: a hanging or down model must not hold the recovery task, and the row must say what happened rather than nothing (#193).
- **URL checks** (`check_url`): one GET, redirects followed, 10 s timeout for the whole reply. It fails on a wrong status, a timeout or connection error, a reply slower than 5000 ms, or (when `body_contains` is set) a body without the text. Only the first 64 KB of the body is read, and only when text is asked for and the status is the expected one; otherwise no body is read and compression is not looked at. The request asks for `Accept-Encoding: identity` and the body is read raw (`aiter_raw`), so the cap counts bytes before any decompression; a reply that still carries a `Content-Encoding` other than identity fails the check with "the reply is compressed although plain text was asked for" and its body is never read (#136). Reason: a gzip or zstd body of a few KB can inflate to hundreds of MB inside the 10 s window, and a server that ignores `identity` is misbehaving, so a plain failure is honest and cheaper than decoding a capped prefix; same rule as the Coolify client and the MCP transport. Redirects are followed by a bounded loop in `http_checks.py` (20, httpx's default) with `follow_redirects=False` on each hop, and every 3xx reply is closed unread, because httpx reads and decompresses the body of each redirect it follows by itself, before any check code runs. Reason: that closes the hole without a transport wrapper, and `watcher` must not import from `plugins`. Any other per-URL error (a malformed URL, a bad header) is a failed check too, never an exception, and `UrlWatcher` handles a crashing check as a failed one. The hosts file is validated on load: a service URL that is not an http(s) URL with a host is a config error naming the host and the URL (#26). The error text never quotes the body. Reason: a URL answers for the service, so a check must say "the page is up and is the right page" cheaply, and a hostile or huge body must cost nothing.
- **Every result is fed, good or bad,** as `url_failed` with `ok`, `latency_ms`, `url`, `status` and `error`, and the latest result per URL is kept in `url_checks` (migration 0005) for the dashboard. Reason: the detector's streak must reset on a good check, and the dashboard needs to show what the last check saw.
- **The services API shows the stored result** (`api/hosts.py`): each configured URL gets its latest `url_checks` row as `ok` or `failing` with the time, status code and latency; a URL with no row is `unknown` with no time. A row older than three check intervals (90 s) is shown as `unknown` but keeps its time, status code and latency, and the dashboard says "No recent check" with that time. Rows for URLs no longer configured are ignored. A failing URL makes its service `down`, as before (#103). Reason: when a host's watcher stops or the host is down, an old "OK" would claim a health nobody measured; the kept time tells the reader how old the last answer is.
- **URL failures wait while their host is unreachable.** A failing URL check on a host the registry marks unreachable is held (the last 5 per service), not fed to the detector. When that host's `host_unreachable` incident is open, the held failures attach to it through `open_or_attach` (which routes a service signal to the host incident) and a notice lists the URLs on its timeline, once per URL: later failures of a URL already named attach without another notice (#72). If the host comes back first, they are dropped. Reason: when a host is down all of its services' URLs fail, and three service incidents for one dead machine is three pages for one problem. A host incident opened for another reason (a full disk) does not collect them: the manager checks for a `host_unreachable` signal first. Limit: a failure fed in the one tick before the registry notices the host is down stays in the detector's streak, so one more failure after the host returns can open a service incident one check early.
- **Host probe reads what the registry already holds.** The registry reads host basics about once a minute for the API; the probe feeds `disk` (the fullest filesystem, with its mount), `memory` (available percent) and `load` (load15 per CPU) from each new reading, and skips a reading it already fed or a host that is unreachable. Reason: running `df`, `free` and `uptime` a second time per minute only to feed the same numbers would double the ssh work, and counting one reading twice would make "3 polls" mean fewer. A socket host's engine reports no disk, load or available memory, so it yields no signals.
- **`host_unreachable` comes from the pull watcher, not the probe.** The watcher sends it on every tick, so the detector's 5-minute timer already runs; sending it again would count the same outage twice. Reason: one source for one fact.
- **The watcher resumes on its own.** After a host returns, the next tick reconnects, replays the cursor's gap once and carries on; nothing in the manager is "reconnecting". A death during the outage that is still down past its grace window opens its own incident (#15).
- **Registry lock.** The poller's tick holds no lock of its own; it takes the host's entry lock through the registry calls it makes, `Registry.reconnect` and `Registry.refresh` (the listing). A refresh from Gather (`registry.refresh(host_id)`) takes the same lock, so it waits for the tick's listing to finish or the other way round, and neither sees a half-updated snapshot. Reading Docker events and building signals happen outside the lock. The cost is that a slow listing delays the other caller, never that two listings run at once (#15).
- **A host added, changed or removed on the dashboard is put in force by `WatcherManager.host_changed`, without a restart.** Added: its three loops start. A new connection: they stop and start again with fresh state (no cursor, no previous listing), so a listing of another machine is never diffed against the old one's. Removed: they stop, its open incidents are closed with a notice (`IncidentRunner.end`), the detector forgets the host's pending deaths, streaks and timers (`Detector.forget_host`), and the registry closes it ([hosts](hosts.md#hosts-from-the-dashboard-194), #194).
- **A cancelled database connect closes itself.** `Database.connect` shields the open and closes the connection if the caller is cancelled midway. Reason: shutdown cancels the watcher loops while they write, and a connection left open keeps its thread running past the event loop (seen as a flaky thread warning in the API tests) (#15).

- **Grace window of 60 s.** A container that dies and is running and healthy (or running with no healthcheck) within `container_grace_s` is a `Recovered` event with a one-line explanation, not an incident. Reason: restart policies fix most deaths in seconds, and paging a human for those teaches them to ignore pages (#14).
- **A healthcheck still "starting" is not recovered.** It counts as down past grace once the window ends. Reason: running but not yet healthy proves nothing about the fix (#14).
- **Repeated deaths: 3 in 600 s open an incident, even if each recovered.** Counted per container in a sliding window. Reason: a crash loop that restarts quickly is still broken (#14).
- **One-shot containers are ignored.** Exit code 0 with restart policy `no` or empty is `Ignored("one-shot exit 0")`; exit 0 under a restart policy is a normal death. Reason: migrations and batch jobs are meant to exit, while a service that keeps exiting 0 under `always` is not healthy (#14).
- **Host subjects.** Disk (at or above 90 %), memory (available under 5 % for 3 polls), load (per CPU over 2.0 for 3 polls) and host unreachable (5 min) open on a host subject, not a service. Poll-count thresholds count consecutive breaches per host and reset on a good poll; the watcher feeds every poll, good or bad (`ok`, `percent`, `available_percent`, `load_per_cpu` in the signal detail). Reason: a single spike is noise, and the cause of a host problem is rarely one service (#14).
- **URL checks.** Two consecutive failures open; a reply slower than 5000 ms counts as failed; a good check resets the count (#14).
- **Debounce: open immediately, attach later.** The first qualifying signal for a subject emits `OpenIncident` at once; further qualifying signals for the same subject within 30 s emit `AttachSignals`, so there is never a second open inside the window. Reason: waiting out the window would delay a real outage by 30 s, and the manager only has to handle "create" and "append to the incident I just created" (#14).
- **Pass-through kinds.** `unhealthy`, `restart_loop` and `down_past_grace` already mean a threshold was crossed at the source, so they open directly. `oom` is treated like a death and gets the grace window (#14).
- **Defaults** (`Thresholds` in `schemas/settings.py`): grace 60 s, repeated deaths 3 in 600 s, URL failures 2, slow 5000 ms, disk 90 %, memory under 5 % for 3 polls, load per CPU 2.0 for 3 polls, host unreachable 300 s, debounce 30 s (#14).
- **Recovery explanations.** `explain_recovery` sends the last 4,000 characters of logs, wrapped as untrusted data with any `<untrusted` tags inside escaped, to the cheap model and keeps one sentence of at most 200 characters. Reason: logs are attacker-influenced text and the line goes on the dashboard (#14).
- **Persistent breach re-opens.** Disk at 95 % polled every minute yields an `OpenIncident` each time the 30 s window has passed. The manager dedupes against the subject's open incident (`IncidentRepo.open_or_attach` attaches), so repeats are expected and safe (#14).
- **Late ticks.** A container running healthy (or with no healthcheck) whose `started_at` is within the grace window of its death is recovered whenever `tick` first sees it. One still `starting` cannot be judged that way, so the manager must tick about every 10 s (#14).
- **An `unhealthy` signal for a container with a pending death** folds that death into its incident and clears it, so grace expiry does not open a second one. A second death while one is pending keeps the first death's grace window (#14).
- **Bounded state.** `tick` drops death history older than the repeat window and debounce windows older than `debounce_s` (#14).

## Signal contract for the watcher and manager

| Signal kind | Detail keys | Notes |
| --- | --- | --- |
| `container_died` | `exit_code`, `restart_policy` | `signal.container` must equal `ContainerSummary.name` |
| `oom` | none | treated as a death |
| `unhealthy`, `restart_loop`, `down_past_grace` | none | open directly |
| `url_failed` | `ok`, `latency_ms`, `url` | fed on every check, good or bad; the name means "URL check result" and `ok` says whether it passed (the kind is shared with the schema, so it is not renamed) |
| `disk` | `percent` | fed every poll |
| `memory` | `available_percent` | fed every poll |
| `load` | `load_per_cpu` | fed every poll |
| `host_unreachable` | `ok` | fed on every probe, `ok=True` resets |

`tick(now, states)` takes `states` keyed by service id. The manager must handle `AttachSignals` (append to the incident just opened) as well as `OpenIncident`.
