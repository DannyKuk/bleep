# Watcher: detection

How raw signals become incidents, self-recoveries or nothing. The decision logic is `bleep/watcher/detector.py`: pure, with an injected clock, so it is tested without Docker.

## Pull model: `watcher/poller.py`, `events.py`

One `HostWatcher` per host ticks every 15 s (`BLEEP_WATCH_INTERVAL_S`). A tick is: reconnect if the host is down, `events(since=cursor, until=now)`, then `Registry.refresh` (which lists containers). It is pure code; no model is called.

- **Pull, not a live event stream.** Reason: Bleep reaches a few hosts over agentless SSH, and some sleep. A dropped link or a sleeping host is a non-event: the tick fails, and the next one reads from the same cursor and catches up. There is no stream state to repair and no reconnect-and-replay race. The limit is up to 15 s of detection delay and one listing per host per tick; at hundreds of hosts an agent on each host would be the right design (#13).
- **The cursor advances only after a successful tick,** and a failed tick emits nothing but its probe result. Reason: so a gap is replayed once in full, and a host that was asleep is never marked dead by silence (#13).
- **Events and the listing are fetched before anything is emitted,** and the watcher's state changes only then. Reason: a tick that fails halfway must be exactly repeatable (#13).
- **Event identity is (container id, action, time).** A remembered set, kept 120 s past the cursor, drops events that an overlapping or retried window returns again; the window bounds are inclusive, so the boundary event is returned twice by design. Reason: a retried tick must never emit a signal twice (#13).
- **Mapping.** `die` is `container_died` with exit code and the container's restart policy; `oom` is `oom`; `health_status: unhealthy` is `unhealthy`; a `restart` event with no `die` in the same batch is a `container_died` with no exit code. `restart_loop` stays the detector's. Reason: a restart policy firing is evidence of a death, but a single restart is not by itself a loop (#13).
- **Stopped on purpose is not a death.** A `stop` or `destroy` event for the container in the same batch removes its `die` and `restart`. A container that exited with 0 or 143 between two snapshots makes no signal either; the service shows `stopped`. Reason: `docker stop` and `compose stop` are choices, and a restart policy does not fire for them (#13).
- **`bleep.self` containers emit nothing,** by the event's own labels or the snapshot's (#13).
- **The snapshot diff catches what events missed, once.** A container that was running and is now gone, exited with a crash code, or has a higher restart count is reported as `container_died` on the tick where the change first shows. A death the diff reported is remembered, so a late event for the same death is skipped, even one stamped after the tick's window but before the listing was taken. A diff death carries the container's own time (its finish, or its new start after a restart), not the tick's, so a restart the diff caught still counts as a recovery in the detector. Reason: events can be lost (the engine backlog, a window cut short), and listing and events are read a moment apart (#13).
- **Every tick sends `host_unreachable` with `ok` to the detector,** true when the tick reached the host and false when not, so its 5-minute timer starts and resets (#13).
- **The detector is ticked with the containers of the same tick** (the watcher's `on_snapshot` hook, `WatcherManager.snapshot`, grouped by service id). Reason: the detector judges a recovery from `started_at` and state, which must come from the snapshot taken with the signal, not from an older one (#13).
- **A start before the death is never a recovery.** `Detector.tick` treats a container whose `started_at` is earlier than the death as the old run seen in a stale snapshot: not recovered, so it opens past grace if it never restarts. Reason: otherwise a snapshot taken just before the death would clear it (#13, #14).
- **The manager feeds the detector:** every signal goes through one shared `Detector`, and its snapshot hook ticks the detector with that host's fresh listing (#13, #15).
- **A host's pending deaths are judged only by that host's own listing.** `Detector.tick(now, states, host_id)` skips deaths on other hosts. A host that stops answering takes no listing, so a death seen just before it went quiet stays pending until it answers again, then is judged (recovered, or down past grace) by what it shows. Reason: judging it against the last listing while another host ticks would open a service incident for a host Bleep cannot see, a run that gathers nothing, and then the `host_unreachable` incident as a second page for one cause (#72).
- **Container deaths are keyed by host id and container name.** The detector's pending deaths, death history (the restart-loop count) and recoveries use `(host_id, name)`, never the name alone. Reason: hosts run same-named containers (every Coolify server has `coolify-db` and `coolify-proxy`), so a name-only key dropped one host's death while the other's was pending, let a recovery on one host clear the other's, and added deaths on two hosts into a false restart loop (#74).
- **A tick is bounded to 60 s and never raises;** a sink that fails is logged and the rest of the tick goes on. Reason: one hung call or one bad consumer must not stop a host's watching (#13).
- **Host basics (disk, memory, load) are not fed here.** They have their own cadence (60 s); the detector counts polls, so the 15 s tick must not feed them (#13).

## Manager, URL checks and host probes: `watcher/manager.py`, `http_checks.py`, `host_probe.py` (#15)

`WatcherManager` runs three loops per host: the pull watcher (15 s), the host probe (60 s) and the URL checks (30 s). Each loop is its own supervised task: if it dies of an error it is logged and started again, backing off 1, 2, 5, 15 then 60 s. Reason: one bug or one bad host must stop nothing else, and a watcher that quietly stops is worse than one that restarts.

- **Outcomes become actions in one place.** `OpenIncident` and `AttachSignals` both go to `IncidentRepo.open_or_attach`; the incident runner starts only when that call reports the incident as newly opened. Reason: the detector may ask to open again for a persistent breach (disk at 95 %), and two tasks may race on one subject; the repository decides, so a run starts exactly once per incident. An attach that finds no open incident (it closed in between) opens one and starts its run.
- **`start()` restarts unfinished runs first** (`IncidentRunner.recover_on_boot`), then starts watching. Reason: after a crash, runs that were mid-investigation go on from their checkpoints before new signals arrive.
- **A recovery is logged off the tick.** `Recovered` starts a background task that reads the last 50 log lines, asks the cheap model for one sentence and writes the `recovery_events` row. If the logs or the model fail, the row is still written, with a plain "no explanation" line. The call is in the usage ledger under `recoveries` and is skipped once the day's cost cap is spent ([dev panel](dev-panel.md), #130). Reason: a slow model call inside the tick would delay the next pull (the tick has a 60 s bound), and a recovery must never be lost for want of a sentence.
- **The recovery line's model call is bounded by the model guard.** `explain_recovery` runs under the same `ModelGuard` as the graph's calls (the `model_timeout_s` budget, retries on transient errors). If the model is still unreachable after the retries, the line is the plain fact "The container died and its restart policy brought it back.", the outage is logged by error type only, and the recovery row is written as usual. Reason: a hanging or down model must not hold the recovery task, and the row must say what happened rather than nothing (#193).
- **URL checks** (`check_url`): one GET, redirects followed, 10 s timeout for the whole reply. It fails on a wrong status, a timeout or connection error, a reply slower than 5000 ms, or (when `body_contains` is set) a body without the text. Only the first 64 KB of the body is read, and only when text is asked for and the status is the expected one; otherwise no body is read and compression is not looked at. The request asks for `Accept-Encoding: identity` and the body is read raw (`aiter_raw`), so the cap counts bytes before any decompression; a reply that still carries a `Content-Encoding` other than identity fails the check with "the reply is compressed although plain text was asked for" and its body is never read (#136). Reason: a gzip or zstd body of a few KB can inflate to hundreds of MB inside the 10 s window, and a server that ignores `identity` is misbehaving, so a plain failure is honest and cheaper than decoding a capped prefix; same rule as the Coolify client and the MCP transport. Redirects are followed by a bounded loop in `http_checks.py` (20, httpx's default) with `follow_redirects=False` on each hop, and every 3xx reply is closed unread, because httpx reads and decompresses the body of each redirect it follows by itself, before any check code runs. Reason: that closes the hole without a transport wrapper, and `watcher` must not import from `plugins`. Any other per-URL error (a malformed URL, a bad header) is a failed check too, never an exception, and `UrlWatcher` handles a crashing check as a failed one. The hosts file is validated on load: a service URL that is not an http(s) URL with a host is a config error naming the host and the URL (#26). The error text never quotes the body. Reason: a URL answers for the service, so a check must say "the page is up and is the right page" cheaply, and a hostile or huge body must cost nothing.
- **Every result is fed, good or bad,** as `url_failed` with `ok`, `latency_ms`, `url`, `status` and `error`, and the latest result per URL is kept in `url_checks` (migration 0005) for the dashboard. Reason: the detector's streak must reset on a good check, and the dashboard needs to show what the last check saw.
- **The services API shows the stored result** (`url_status` in `watcher/health.py`, used by `api/hosts.py`): each configured URL gets its latest `url_checks` row as `ok` or `failing` with the time, status code and latency; a URL with no row is `unknown` with no time. A row older than three check intervals (90 s) is shown as `unknown` but keeps its time, status code and latency, and the dashboard says "No recent check" with that time. Rows for URLs no longer configured are ignored. A failing URL makes its service `down`, as before (#103). Reason: when a host's watcher stops or the host is down, an old "OK" would claim a health nobody measured; the kept time tells the reader how old the last answer is.
- **URL failures wait while their host is unreachable.** A failing URL check on a host the registry marks unreachable is held (the last 5 per service), not fed to the detector. When that host's `host_unreachable` incident is open, the held failures attach to it through `open_or_attach` (which routes a service signal to the host incident) and a notice lists the URLs on its timeline, once per URL: later failures of a URL already named attach without another notice (#72). If the host comes back first, they are dropped. Reason: when a host is down all of its services' URLs fail, and three service incidents for one dead machine is three pages for one problem. A host incident opened for another reason (a full disk) does not collect them: the manager checks for a `host_unreachable` signal first. Limit: a failure fed in the one tick before the registry notices the host is down stays in the detector's streak, so one more failure after the host returns can open a service incident one check early.
- **Host probe reads what the registry already holds.** The registry reads host basics about once a minute for the API; the probe feeds `disk` (the fullest filesystem, with its mount), `memory` (available percent) and `load` (load15 per CPU) from each new reading, and skips a reading it already fed or a host that is unreachable. Reason: running `df`, `free` and `uptime` a second time per minute only to feed the same numbers would double the ssh work, and counting one reading twice would make "3 polls" mean fewer. A socket host's engine reports no disk, load or available memory, so it yields no signals.
- **`host_unreachable` comes from the pull watcher, not the probe.** The watcher sends it on every tick, so the detector's 5-minute timer already runs; sending it again would count the same outage twice. Reason: one source for one fact.
- **The watcher resumes on its own.** After a host returns, the next tick reconnects, replays the cursor's gap once and carries on; nothing in the manager is "reconnecting". A death during the outage that is still down past its grace window opens its own incident (#15).
- **Registry lock.** The poller's tick holds no lock of its own; it takes the host's entry lock through the registry calls it makes, `Registry.reconnect` and `Registry.refresh` (the listing). A refresh from Gather (`registry.refresh(host_id)`) takes the same lock, so it waits for the tick's listing to finish or the other way round, and neither sees a half-updated snapshot. Reading Docker events and building signals happen outside the lock. The cost is that a slow listing delays the other caller, never that two listings run at once (#15).
- **A host added, changed or removed on the dashboard is put in force by `WatcherManager.host_changed`, without a restart.** Added: its three loops start. A new connection: they stop and start again with fresh state (no cursor, no previous listing), so a listing of another machine is never diffed against the old one's; a new address, port or user also makes the detector forget the host (`Detector.forget_host`) and drops its held URL failures, so a death pending on the old machine never opens an incident on the new one. Removed: they stop, its open incidents are closed with a notice (`IncidentRunner.end`), the detector forgets the host's pending deaths, streaks and timers (`Detector.forget_host`), and the registry closes it ([hosts](hosts.md#hosts-from-the-dashboard-194), #194).
- **A cancelled database connect closes itself.** `Database.connect` shields the open and closes the connection if the caller is cancelled midway. Reason: shutdown cancels the watcher loops while they write, and a connection left open keeps its thread running past the event loop (#15).

## Detector: `watcher/detector.py` (#14)

- **Grace window of 60 s.** A container that dies and is running and healthy (or running with no healthcheck) within `container_grace_s` is a `Recovered` event with a one-line explanation, not an incident. Reason: restart policies fix most deaths in seconds, and paging a human for those teaches them to ignore pages (#14).
- **A healthcheck still "starting" is not recovered.** It counts as down past grace once the window ends. Reason: running but not yet healthy proves nothing about the fix (#14).
- **Repeated deaths: 3 in 600 s open an incident, even if each recovered.** Counted per container in a sliding window. Reason: a crash loop that restarts quickly is still broken (#14).
- **One-shot containers are ignored.** Exit code 0 with restart policy `no` or empty is `Ignored("one-shot exit 0")`; exit 0 under a restart policy is a normal death. Reason: migrations and batch jobs are meant to exit, while a service that keeps exiting 0 under `always` is not healthy (#14).
- **Host subjects.** Disk (at or above 90 %), memory (available under 5 % for 3 polls), load (per CPU over 2.0 for 3 polls) and host unreachable (5 min) open on a host subject, not a service. Poll-count thresholds count consecutive breaches per host and reset on a good poll; the watcher feeds every poll, good or bad (`ok`, `percent`, `available_percent`, `load_per_cpu` in the signal detail). Reason: a single spike is noise, and the cause of a host problem is rarely one service (#14).
- **URL checks.** Two consecutive failures open; a reply slower than 5000 ms counts as failed; a good check resets the count (#14).
- **Debounce: open immediately, attach later.** The first qualifying signal for a subject emits `OpenIncident` at once; further qualifying signals for the same subject within 30 s emit `AttachSignals`, so there is never a second open inside the window. Reason: waiting out the window would delay a real outage by 30 s, and the manager only has to handle "create" and "append to the incident I just created" (#14).
- **Pass-through kinds.** `unhealthy`, `restart_loop` and `down_past_grace` already mean a threshold was crossed at the source, so they open directly. `oom` is treated like a death and gets the grace window (#14).
- **Defaults** (`Thresholds` in `schemas/settings.py`): grace 60 s, repeated deaths 3 in 600 s, URL failures 2, slow 5000 ms, disk 90 %, memory under 5 % for 3 polls, load per CPU 2.0 for 3 polls, host unreachable 300 s, debounce 30 s (#14).
- **Recovery explanations.** `explain_recovery` sends the last 4,000 characters of logs, wrapped as untrusted data with any `<untrusted` tags inside escaped, to the cheap model and keeps one sentence of at most 200 characters. Reason: logs are attacker-influenced text and the line goes on the dashboard (#14).
- **Persistent breach re-opens.** Disk at 95 % polled every minute yields an `OpenIncident` each time the 30 s window has passed. The manager dedupes against the subject's open incident (`IncidentRepo.open_or_attach` attaches), so repeats are expected and safe (#14).
- **Late ticks.** A container running healthy (or with no healthcheck) whose `started_at` is within the grace window of its death is recovered whenever `tick` first sees it. One still `starting` on the first tick after the window opens as down past grace, so a slow healthcheck gets the window plus up to one tick (15 s) (#14).
- **An `unhealthy` signal for a container with a pending death** folds that death into its incident and clears it, so grace expiry does not open a second one. A second death while one is pending keeps the first death's grace window (#14).
- **Bounded state.** `tick` drops death history older than the repeat window and debounce windows older than `debounce_s` (#14).

## Health since and recent checks (#232)

- **The watcher keeps each service's health with the time it last changed** (`service_health`, migration 0021, `watcher/health_store.py`). `WatcherManager.record_health` judges each of the host's services with `watcher/health.service_health` from the same inputs the services API uses (the registry's containers and the stored URL results through `url_status`), after every successful poll tick (from `snapshot`) and after every round of URL checks (`UrlWatcher`'s `on_round`, once the round's results are stored). One upsert moves `since` only when the health differs from the stored one. Reason: the service page says "healthy since" from it, and judging it where the inputs change keeps it as fresh as the views; the API stays a reader (#232).
- **`unknown` is never stored.** It means no data (no listing yet after a restart, a URL check gone stale), so the last known health and its time stay. Reason: a backend restart or a host's watcher pausing must not reset "healthy since" to the moment Bleep looked again (#232).
- **Quiet services and hosts get their health stored too.** Reason: quiet only stops incidents; the page must still say how the service has been (#232).
- **A removed host's rows are dropped, and so are a moved host's** (a new address, port or user). Reason: the old machine's history says nothing about the new one, and a host re-added under the same id starts fresh (#232).
- **Every URL check is also written to `url_check_history`** (migration 0022) in the same transaction as the latest row, and the URL's rows past the last 30 per (host, service, URL) are deleted in that insert (`HISTORY_PER_URL`, 15 minutes at one check every 30 s). The history keeps `ok`, the status code, the latency and the time, not the error text. Reason: the service page's strip of recent checks needs a short, bounded history, and pruning on insert keeps the table bounded without a sweeper (#232).
- **Limit:** a row in either table for a service that is gone from a host that is still watched stays until the host is removed or moved. It is a few small rows and is read only for a service the registry knows (#232).

## Quiet services and hosts (#220)

- **A quiet service or host is still read, not acted on.** The detector, URL checks and host probe keep running, so health stays true. `WatcherManager` drops an `OpenIncident` or `AttachSignals` for a quiet subject with a debug log line, and a service's URL failures that would be held for a host incident are dropped too. Reason: the person decided to be left alone, but Bleep must know the real state the moment the quiet ends (#220).
- **The host's state wins.** A service is quiet when it is quiet itself or its host is, and a quiet host also silences its own host incidents (unreachable, disk, memory). Reason: "my laptop is asleep" must not page about the laptop either (#220).
- **A quiet starting closes the subject's unfinished incidents through `IncidentRunner.end`**, except one that is `executing` or `verifying`. Setting a quiet again replaces the first and adds no second round of notices. Reason: half-cancelling an approved plan can leave the service worse than either state, and the run stops at its own next step instead (#220).
- **A quiet ending looks at the target again.** Expiry runs in a loop every 30 s (`QUIET_TICK_S`) and once at start, so a snooze that passed while the backend was down ends at once. Only a `down` service opens an incident; `degraded`, `stopped`, `ok` and `unknown` open nothing. Reason: whatever happened during the quiet must not arrive as a burst, only the state at the end counts (#220).
- **A recheck that cannot run now waits for the host's next listing.** When a host's quiet ends while it is unreachable, its host incident opens at once and the recheck of every one of its services waits; a service whose quiet ends while its host is unreachable, or has no listing yet (its first connect at boot failed), waits the same way. `WatcherManager.snapshot` runs what waited on the host's next successful listing, once, through `recheck`, so a service quiet again by then is skipped. Such a recheck judges the containers only: the stored URL results were taken while the host was unreachable, and the live URL checks judge the URLs from there. A removed or moved host drops what waited. Reason: a container that died during the quiet sent its one death event then, and the quiet dropped it; the recheck is the only way back to it, and the last listing of an unreachable host is stale (#220).
- **A service still quiet on its own when its host's quiet ends stays quiet and is not judged again** (#220).

## Bleep's own sleep, hosts that may sleep, and recovery (#85)

- **Bleep notices its own suspension from the wall clock running ahead of the monotonic clock.** While the process is suspended (its machine sleeps, its container is paused) the wall clock runs on and the monotonic clock does not, on macOS, on Linux and in the Linux VM Docker Desktop runs Bleep in. One `SleepWatch` (`watcher/wake.py`), shared by every host's loops, keeps the last (wall, monotonic) pair any loop looked at; a wall-clock advance beyond the monotonic one of more than two watch intervals (30 s) since that look is a sleep, and it calls `WatcherManager.woke`. `HostWatcher` looks before it pulls and again before its probe result goes out, and `UrlWatcher` looks after each check returns and before it feeds the result, so a result taken across a sleep (a tick inside an SSH connect when the lid closed) is fed only after the wake is known and falls in the grace window. A slow tick or a stalled event loop moves both clocks and is no sleep; a wall clock set back (NTP) gives a negative difference and is no sleep either. Reason: on 2026-11-03 the machine running Bleep slept all night with short dark wakes; at each wake the network was not up yet, the outage timer started before the sleep had run for hours, and two "host unreachable" incidents opened for a host that had been up for three days. A pause between ticks alone misses a sleep that begins inside a tick, which a connect to a host that does not answer makes likely (#85).
- **After a wake, an outage counts from zero, and failed contact is not counted for a grace window.** `woke` makes the detector forget every host's outage timer and every unreachable and URL streak (`Detector.woke`), and for `BLEEP_WAKE_GRACE_TICKS` watch intervals (4 by default, one minute at 15 s; the one default is `Settings.wake_grace_ticks`) after the wake the manager drops a failed `host_unreachable` probe and a failed URL check before the detector sees them. The window's end is held on the monotonic clock, so a wall clock set back cannot stretch it. A host still unreachable after that opens its incident `host_unreachable_s` (5 minutes) later, as any outage. Service health is not stored inside the window either. Reason: the time Bleep could not see is no evidence that a host was down, and after a wake Wi-Fi and the `.local` name lookup take a few seconds to come back. Four ticks covers the reconnect seen on the dark wakes and keeps a real outage's page within about six minutes of the wake (#85).
- **`may_sleep: true` marks a host that sleeps by design** (a laptop). It is set in the hosts file, or for any host on its page ("This host may sleep", saved as `HostSettings.may_sleep` through `PUT /api/settings`, the dashboard's choice over the file's, like a host's rules). Such a host not answering opens no incident: `WatcherManager._open` drops an outcome whose only signals are `host_unreachable` for it. Its URL failures are held as for any unreachable host and dropped when it answers again, and its pending container deaths wait for its next listing, so nothing pages for its sleep. Any other host incident (a full disk) still opens. `GET /api/hosts` shows its health as `asleep`, not `down` or `unknown`, while it does not answer, and carries `may_sleep`. Reason: a laptop closing its lid is not an outage, but the overview must still say where it is (#85).
- **An asleep host's services are asleep too.** The services API shows every service of an asleep host as `asleep`, not judged from its last listing or its failing URL checks, and `record_health` stores nothing for it (as for `unknown`, the health from before the sleep and its time stay), also on the first failed tick before the registry marks it unreachable. Its URL failures are held as for any unreachable host and open nothing. Reason: a laptop with its lid closed has no service that is down (#85).
- **A host-unreachable incident waits for its host and makes no model call.** An incident on a host subject whose signals are only `host_unreachable` and the URL failures held for it does not run the graph: `IncidentRunner` sets it `waiting`, puts one notice on its timeline and tells the channels once, with a message that promises no plan (`notify/incident_waiting.md`). Reason: every tool would fail against a host that does not answer, so Investigate and Diagnose would spend model calls to learn nothing (#85).
- **Every tick that reaches the host closes its waiting incident as recovered on its own.** On every probe that reaches a host (not only the first after an outage) the manager calls `IncidentRunner.host_back`, one indexed read when nothing waits. A waiting incident whose signals are still only the outage and its URL failures is closed with "Closed: the host answers again. It recovered on its own; nothing was changed.", on its timeline and once to the channels, with no approval since nothing is done. The close happens in one transaction only while the incident is still `waiting`, so an incident of another kind, or one whose run has started, is never closed by it. A waiting incident that took another signal meanwhile (a disk reading as the host came back) starts its run instead, without being announced a second time. The URL checks judge the service URLs again from here, so a URL still failing opens its own service incident. Reason: when the host answers, the outage is over; and a run that parks just after the host's first good tick is caught by the next one instead of waiting for ever (#85).
- **A waiting incident is not announced when the host already came back.** `recover_on_boot` skips a `waiting` incident; the first tick that reaches its host closes it. When a host-unreachable incident's run starts (just opened, or opened just before a stop), it is closed at once with one notice on its timeline ("the host answered again before I got to it") and no channel message only when the manager's last probe of the host reached it after the incident's newest signal (`WatcherManager.answered`, the probe's own time); otherwise it waits and is announced. The registry's reachable flag is not used for this: it stays true when the engine hangs or its events fail behind a working session, while the probe fails. At boot no probe has run when the runs start, so an incident from before the stop waits and is announced, and the first good tick closes it with the usual "recovered on its own" (#85).
- **Limits.** A host that never answers again keeps its waiting incident open until a person removes the host or makes it quiet, and a `may_sleep` host that never comes back stays asleep with no incident at all. Wakes that keep coming (a machine in a sleep and dark-wake cycle) restart every outage timer each time, so a host down meanwhile opens no incident until Bleep stays awake for the grace window and five minutes. A host that flaps (down five minutes or more, back, down again) sends two messages per cycle, the waiting one and the recovered one; folding repeats (#84) is where that is addressed. `may_sleep` set while a host's incident is already waiting leaves that incident to close on the host's return.

## Expected exits and "This is expected" (#84, #256)

A container can be named as a job that is meant to finish, and a person can teach Bleep that from an incident in one tap. A service or host stopped on purpose is covered by quiet services and hosts (#220, #221): snooze it or leave it alone. A job that should have run and did not is a follow-up (#260).

- **`exits` names the jobs of a service.** `ServiceOverrides.exits` in the hosts file is a list of entries, each a container name, a Compose service name (the container's `com.docker.compose.service` label, so `fetch` matches `molecula-fetch-1` and every `molecula-fetch-run-3f2a…` of `compose run --rm`), or `"*"` for every container of the service (a Coolify scheduled app, whose container names are generated). Discovery gives a service the entries of its override, by key else by name, like its URLs (`Service.exits`), and `hosts/discovery.expects_exit` matches a container against them. Reason: an exit 0 with no restart policy was already ignored, but a job under `on-failure` (its exit 0 then went down past grace), one under `always` (its clean exits added up to a restart loop) and a `compose run --rm` job (gone before the next listing) all opened incidents (#256).
- **The dashboard's list replaces the hosts file's**, as for `urls` and `rules` (`ServiceSettings.exits` in the `settings` rows; no migration). Reason: it only changes alerting; protected containers are the only list that only adds, because they are a safety rule (#256).
- **The poller marks a job's death, and the detector ignores its exit 0 before counting it.** `translate` and `diff` add `expected_exit: true` (and `compose_service` when the label is there) to a `container_died` of a container its service names; `Detector._death` answers an exit 0 with it `Ignored("expected exit 0")` before the death is counted toward a restart loop. A non-zero exit, an OOM, `unhealthy` or a crash code is a death as before. For such a job only `stop` makes its `die` deliberate, not `destroy`, so a failed `--rm` run is still reported; and one that vanished between two listings is its `--rm` end, not a death. A container never listed (a `--rm` run between two listings) is placed in its service by its event labels (`discovery.service_key`), not as `container:<name>`. Reason: the person said this container finishes; a crash of it is still a crash (#256).
- **Health `done`.** A container that exited 0 and is a one-shot (no restart policy) or named in `exits` is `done`. A service whose containers are all `done` is `done`; `done` beside running containers changes nothing; a host counts a `done` service as `ok`. It is stored in `service_health` like any other health, so the service page can say "done since". Reason: `stopped` reads as something somebody did, while a finished job is the normal end of its day (#256).
- **"This is expected" records only what a later identical event is judged by** (`incidents/expectations.py`): for an incident whose deaths all exited 0 (with their `down_past_grace` or `restart_loop`), each container's Compose service name (else its name) is added to its service's dashboard `exits`; for a host-unreachable incident, the host's `may_sleep` is set (#85). Anything else (a crash, a failing URL, a full disk, `unhealthy`) has no expectation, and the action is not offered; the quiet menu is the way to silence those. It is not offered while a plan is approved, executing or verifying, or once the incident is finished. `GET /api/incidents/{id}` says what it would record in `expectation` (null when not offered). Reason: one tap must make the next identical event quiet, and nothing else (#256).
- **One path for both channels.** `POST /api/incidents/{id}/expected` and Telegram's "It's expected" button call `Expectations.expected(incident_id, via)`. A pending approval is first rejected through `ApprovalStore.resolve`, so the action races a yes like any other decision: when the yes won, nothing is recorded and the answer says where it was decided. Then the expectation is written through `SettingsStore.expect_exits` or `expect_sleep`, which add to the dashboard layer under the store's lock without a version (a page saving from an older version gets the usual 409), under the key the host's settings already hold the service by, so a name-keyed hosts file entry is never hidden (#230). Last, an `expected` event says on the timeline what was recorded and from where, and the incident is closed with `IncidentRunner.end` ("Closed: you said this is expected.", also to the channels). It changes nothing on a host, so it needs no approval grant (#256).
- **The Telegram button** is on the incident-opened message and on a proposal's message, only for an incident where it applies. It carries no id: the incident comes from `telegram_messages`, as for Approve and Reject, and only the configured chat is answered. An opened message with the button is logged with an empty approval id instead of a new column, so no migration; a reply to it is answered with how to instruct and is never an instruction (#256).
- **Limits.** An `exits` entry applies to a service Bleep has listed: a `--rm` job of a project with no other container is placed in its service by its labels, but that service has no override in force until one of its containers has been listed. "This is expected" for exit-0 deaths records names, not a schedule; a job that stops running opens nothing (#260).

## Proposal: folded repeats (#84)

A design proposal for #84, not in the code yet: how a subject that breaks again and again becomes one group with a count.

- **The key.** `fold_key` = the subject key, the opening signal's kind and its target: `service:demo:demo/compose:shop|container_died|shop-web-1`, `…|url_failed|https://shop.example/health`, `host:macbook:|host_unreachable`. `oom`, `down_past_grace` and `container_died` share the death key; `restart_loop` and `unhealthy` have their own, so a loop is never counted as one more single death.
- **The window.** A new incident whose `fold_key` matches a finished incident opened within the last `fold_window_h` hours (a threshold, default 24, 0 turns folding off) of the group's latest occurrence is a repeat. The window slides, so a job that fails every morning stays one group ("seen 12 times since 1 Nov"). An open incident for the subject already takes the signals today (one open incident per subject), so folding only ever links to finished ones.
- **What a repeat is.** Its own incident row, run and timeline, linked by `fold_of` to the group's first incident. The count is the number of rows that share the root, so it needs no counter that two runs could race on. Reason: a repeat can need the human now (the fix did not hold, the service is still down), and the graph's checkpoint, approvals and action log are all per incident, so reopening a finished one would mix two runs.
- **Its notifications.** A repeat sends no "incident opened" message and its report stays on the dashboard; the first incident of the group was the one notification. What needs the human is never folded away: a proposal waiting for a yes, its reminders and a failed run are sent as for any incident, with "(seen N times since …)" in the title line. A repeat of a host-unreachable incident waits and closes without a message, as its first did.
- **Its investigation.** A repeat runs the graph like any incident, with the group's count and its last outcome in Gather's context, so the model sees "this happened 4 times today, last time: no action needed". Memory recall finds the earlier ones already.
- **On the incident page.** The group's first incident shows "Seen N times · last <time>" with the repeats listed (time, status, outcome, link); a repeat shows "Repeat N of <first incident's title>" with a link. The incident list shows a group as one row with a count, its status that of the latest occurrence; a repeat waiting for a yes is also its own row in "Needs you". `GET /api/incidents` carries `fold_of` and `repeats`.
- **Migration.** `ALTER TABLE incidents ADD COLUMN fold_key TEXT`, `ADD COLUMN fold_of TEXT REFERENCES incidents (id)`, and an index on `(fold_key, opened_at)`. Older incidents keep `NULL` and never fold.

### Migration and the split

One migration, `incidents.fold_key` and `incidents.fold_of`, taking the next free number when it lands. The backend (#258) and the dashboard (#259) are separate PRs, the dashboard stacked on the backend.

### Rulings on the open questions

1. **A repeat runs the graph**, silently: no "incident opened" message; proposals, reminders and failed runs still notify with "(seen N times since …)".
2. **A group folds over every outcome**: a fix that does not hold is worth a count, and the repeat's own proposal still asks for a yes.
3. **The window is 24 h sliding from the latest occurrence**, the threshold `fold_window_h`, 0 off.

## Signal contract for the watcher and manager

| Signal kind | Detail keys | Notes |
| --- | --- | --- |
| `container_died` | `exit_code`, `restart_policy`, and `expected_exit` and `compose_service` when they apply | `signal.container` must equal `ContainerSummary.name` |
| `oom` | none | treated as a death |
| `unhealthy`, `restart_loop`, `down_past_grace` | none | open directly |
| `url_failed` | `ok`, `latency_ms`, `url` | fed on every check, good or bad; the name means "URL check result" and `ok` says whether it passed (the kind is shared with the schema, so it is not renamed) |
| `disk` | `percent` | fed every poll |
| `memory` | `available_percent` | fed every poll |
| `load` | `load_per_cpu` | fed every poll |
| `host_unreachable` | `ok` | fed on every tick, `ok=True` resets; a failed one inside the grace window after Bleep's own wake is dropped before the detector |

`tick(now, states, host_id)` takes `host_id`'s fresh listing as `states`, keyed by service id, and judges only that host's deaths. The manager must handle `AttachSignals` (append to the incident just opened) as well as `OpenIncident`.
