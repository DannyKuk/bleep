# Notifications

How Bleep tells a human about an incident and takes their answer from Telegram (`backend/src/bleep/notify/`, templates in `backend/src/bleep/prompts/notify/`).

## Choices

- **Telegram is optional.** With no `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` the notifier is bus-only and nothing starts or fails; a token without a chat id logs a warning and stays off. Reason: the demo and a first run need no external account (#22).
- **The token is a `SecretStr` in `Settings`** (read from `TELEGRAM_BOT_TOKEN`, the name `.env` already uses), never stored in the database or put on the bus. It is part of every Bot API URL, so `TelegramClient` turns every transport error into `TelegramError("<method>: <ErrorType>")` without the URL, and `setup` raises the `httpx` logger above INFO, which would print the URL. Reason: the token must not reach a log (#22).
- **Raw Bot API over `httpx`, long polling.** `getUpdates` with a 30 s timeout (the request may take 40 s; every other call gives up after 10 s, so a hung Bot API holds the Approval node or a reminder only briefly, #72) and `allowed_updates` of messages and callbacks; the offset moves past each update before it is handled. A failed poll, whether a Bot API error or anything unexpected (a malformed update), is logged (an unexpected one at ERROR, by type only, since a message could quote the URL) and backs off 1 s, 2 s, ... up to 60 s, resetting after a good one; a failure on one update is logged and the loop goes on. Reason: no library for four calls, and a poller that dies on one bad update or an outage would silently stop the approvals (#22, #72).
- **One chat is answered.** Any update whose chat is not `TELEGRAM_CHAT_ID` is dropped, never answered, and written to the guard log as `foreign_chat` under the incident id `telegram` with the chat id only, not the text. Reason: anyone can message a bot, and a stranger must not approve a restart or even learn the bot reads anything (#22).
- **Buttons carry `approve:<approval id>` or `reject:<approval id>`,** at most 64 bytes. The incident comes from `telegram_messages` (message id to incident id and approval id), not from the button. Decisions go through `approvals.resolve(incident_id, decision, approval_id)`, and only the winner calls `runner.resume(incident_id, decision, approval_id)` with the same id. Reason: the same first-wins statement the dashboard uses, and a late tap on a replaced plan wins nothing (#20, #22).
- **The loser is told who won:** "Already decided on the dashboard" (or on Telegram, for a second tap), "That plan has been replaced" for an old plan, "Nothing is waiting" when none is pending. The buttons are removed after any tap. Reason: a human who lost a race must not wonder whether their tap did something (#22).
- **A reply to a proposal or reminder message is an `instruct` decision** for that message's plan, up to 1,000 characters. Text that is not a reply to one of those messages is answered with how to instruct, and decides nothing. Reason: an instruction needs to say which incident it is for, and a reply says that without commands (#22).
- **A proposal always lists every step's action, target and host; a plugin step's params follow it, redacted and cut to keep the line within 199 characters; the action, target and host are never cut, so a target too long to leave room shows its params as `(…)`** (`1. mcp.call shop-web-1 on demo (tool=pause_monitor, arguments={...})`), like the dashboard's plan card. A Docker step's params are never shown. Reason: a human approves an MCP tool and its arguments, not only the action's name; a cap per step means long arguments can never push a later step out of the 600-character field; and a Docker action ignores params, so they could only be model text in the approval (#43).
- **A `coolify.set_env` step's value is shown as `(hidden)`** (`1. coolify.set_env shop on demo (key=DATABASE_URL, value=(hidden))`), through `PlanStep.shown()`, as on the dashboard. Reason: an env value can be a secret; the human approves the key ([plugins](plugins.md#coolify)) (#38).
- **Every message is escaped for MarkdownV2, template text and values alike,** and templates are plain text. Values are redacted and capped at 600 characters first, and a message is cut at 4,096 characters without ending on a lone backslash. Reason: one unescaped `.` or `_` makes Telegram refuse the whole message, and a diagnosis is model text that may echo a log line (#22).
- **The templates are `.md` files in `prompts/notify/`, filled with `prompts.load`.** They are fixed text, not model prompts. Reason: the rule that every piece of fixed text is a file there (#22).
- **"Incident opened" goes out once per incident, from the runner.** `IncidentRunner` calls `Notifier.incident_opened` when it starts a new incident's thread (no checkpoint yet), before Gather, and not when a run goes on after a restart or a decision. A failure is logged and the run goes on. Reason: only `act` plans reach Telegram through the Approval node, so an incident that ends `no_action`, `unsure` or `budget` would otherwise be seen only on the dashboard; the runner is the one place every new incident passes through, whoever opened it (#72).
- **The notifier adds only `reminder` to the bus.** The nodes already publish `proposal`, `approval_requested`, `decision`, `notice` and `report` themselves. Reason: the same event twice would double the timeline (#22).
- **A Telegram outage never breaks a run.** `proposal` lets the error out, because the Approval node then tells the dashboard "answer it here"; the other calls log and go on. Reason: the dashboard is always a way to decide (#22).
- **`notify.setup(settings, db, bus, approvals, guard_log)` builds the notifier before the graph and `start(runner)` starts the poller after it.** Reason: the graph needs the notifier and the bot needs the runner (#22).
- **The report goes to Telegram for every outcome,** resolved, unverified, rejected, no action, unsure and budget alike: the title, the outcome text, the summary, the cause, the action ("nothing ran"), the decision ("you were not asked") and the follow-ups, without buttons (`prompts/notify/report.md`). Reason: an incident that ends without a plan to approve would otherwise end in silence on Telegram (#27).
