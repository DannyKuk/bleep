# Notifications

How Bleep tells a human about an incident and takes their answer from Telegram (`backend/src/bleep/notify/`, templates in `backend/src/bleep/prompts/notify/`).

## Choices

- **Telegram is optional.** With no `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` the notifier is bus-only and nothing starts or fails; a token without a chat id logs a warning and stays off. Reason: the demo and a first run need no external account (#22).
- **The token is a `SecretStr`** (read from `TELEGRAM_BOT_TOKEN`, the name `.env` already uses, or, when the env does not set it, from the dashboard's secret file with the chat id, [settings](settings.md#secrets-from-the-dashboard-135)), never stored in the database or put on the bus. A token or chat id changed on the dashboard stops the poller, builds the bot again and polls with it, keeping the notifier the graph holds (`NotifySetup.reload`, #135). It is part of every Bot API URL, so `TelegramClient` turns every transport error into `TelegramError("<method>: <ErrorType>")` without the URL, and `setup` raises the `httpx` logger above INFO, which would print the URL. Reason: the token must not reach a log (#22).
- **Raw Bot API over `httpx`, long polling.** `getUpdates` with a 30 s timeout (the request may take 40 s; every other call gives up after 10 s, so a hung Bot API holds the Approval node or a reminder only briefly, #72) and `allowed_updates` of messages and callbacks; the offset moves past each update before it is handled. A failed poll, whether a Bot API error or anything unexpected (a malformed update), is logged (an unexpected one at ERROR, by type only, since a message could quote the URL) and backs off 1 s, 2 s, ... up to 60 s, resetting after a good one; a failure on one update is logged and the loop goes on. Reason: no library for four calls, and a poller that dies on one bad update or an outage would silently stop the approvals (#22, #72).
- **One chat is answered.** Any update whose chat is not `TELEGRAM_CHAT_ID` is dropped, never answered, and written to the guard log as `foreign_chat` under the incident id `telegram` with the chat id only, not the text. Reason: anyone can message a bot, and a stranger must not approve a restart or even learn the bot reads anything (#22).
- **Buttons carry `approve:<approval id>` or `reject:<approval id>`,** at most 64 bytes. The incident comes from `telegram_messages` (message id to incident id and approval id), not from the button. Decisions go through `approvals.resolve(incident_id, decision, approval_id)`, and only the winner calls `runner.resume(incident_id, decision, approval_id)` with the same id. Reason: the same first-wins statement the dashboard uses, and a late tap on a replaced plan wins nothing (#20, #22).
- **The loser is told who won:** "Already decided on the dashboard" (or on Telegram, for a second tap), "That plan has been replaced" for an old plan, "Nothing is waiting" when none is pending, and "The incident was closed before anyone answered. Nothing will run." for a plan whose incident ended while it waited (quiet, a removed host; #277), to a tap and to a reply alike, and before the answers for a refused plan or one too long to approve here. The buttons are removed after any tap. Reason: a human who lost a race must not wonder whether their tap did something (#22), and a plan closed under them must not read as one nobody asked about (#277).
- **A reply to any message about an incident is an `instruct` decision**, up to 1,000 characters. A reply to a proposal, refused-plan or reminder message stays bound to that message's plan, so a replaced plan is answered "That plan has been replaced"; a reply to a message that showed no plan (the opener, a note, "Didn't hold", the end) binds to the plan that waits for a decision on its incident now, and with none waiting it is answered "Nothing is waiting for a decision on that incident" and decides nothing, also for a message of an earlier incident that has closed. Text that is not a reply to a logged message is answered with how to instruct. Reason: an instruction needs to say which incident it is for, and a reply says that without commands (#22); in a thread a person replies to whatever message is in view, and the stale-plan guard must hold all the same (#380).
- **A proposal always lists every step's action, target and host; a plugin step's params follow it, `tool` first, redacted and kept within 199 characters a line; the action, target and host are never cut** (`1. mcp.call shop-web-1 on demo (tool=pause_monitor, arguments={"name": "shop"})`), like the dashboard's plan card. A Docker step's params are never shown. Reason: a human approves an MCP tool and its arguments, not only the action's name; a cap per step means long arguments cannot push a later step out of the 600-character field, though long targets still can, so a plan whose steps overflow the field gets no Approve button (#38); and a Docker action ignores params, so they could only be model text in the approval (#43).
- **A plugin step whose params do not fit the line is never approved in Telegram**, as a cut `set_env` value is not (below): its params are cut and the line ends "(too long to show here: approve on the dashboard)", also when a long target leaves them no room at all (`(…)`); the proposal and its reminders get a Reject button only, and an Approve press that arrives anyway is refused (`format.shows_in_full`). A secret redacted inside the params (`arguments={"api_key": "<redacted>"}`) does not count as cut, but such a step never reaches an approval: the plan check refuses any step whose params redaction would change (`hidden_param`, [guard](guard.md#plan-check), #294), so it is only shown in a refused plan. `tool` goes first because the model writes the params in any order: a long `arguments` before `tool: drop_database` would hide the tool's name, and a `"then": "drop_database"` at the end of long arguments would be hidden by the cut; either would still have shown an Approve button. Reason: never approve blind (#38) holds for whatever a plugin step runs (#140).
- **A `coolify.set_env` step shows `KEY=value`, redacted, never hidden** (`1. coolify.set_env shop on demo (DATABASE_URL=postgres://shop:<redacted>@db/shop)`), through `guard/redact.redacted_step`, as on the dashboard (what is redacted and what is shown: [plugins](plugins.md#coolify)); a value redaction changes is only ever shown in a refused plan, since the plan check refuses it (`hidden_param`, #294). When the pair does not fit the line, the value keeps its start and end around "…" and the line ends "(value too long to show here: approve on the dashboard)"; that proposal, and its reminders, get a Reject button only, and an Approve press for it that arrives anyway is refused ("Approve it on the dashboard"), where the full redacted value is shown (`format.shows_in_full`). The same holds when the steps together overflow the 600-character field, since `render` would then drop a later step. Reason (#38): the person approving must see the value, since planted text could steer it to an attacker's host, so a value Telegram cannot show whole is never approved there.
- **A line break or control character inside a step reads `⏎`** (`\n`, `\r\n`, `\r`, U+2028, U+2029, NEL and the other C0 and C1 characters), **and a format character `�`** (Unicode category Cf: bidi overrides and isolates U+202A-202E and U+2066-2069, U+200E/F, U+061C, zero-width U+200B-200D, U+2060, U+FEFF), in a set_env key or value and in any plugin param such as an MCP `arguments` text. Reason: a param holding `a\n2. docker.restart shop-web-1 on demo` would otherwise show as a step of its own, and a bidi override can make text read in another order than it runs (#38).
- **The root cause and the plan's reason are one line each** (`format.prose_line`): redacted, then line breaks and control characters read `⏎`, format characters `�`, and a run of spaces is one space, in the proposal, and so are the cause, what ran and each follow-up in the end message. Reason: they are model or event text printed next to the step list, and a reason holding `\n1. coolify.set_env shop on demo (…)`, or a root cause holding `Proposed plan:` and a step, would read as a step the person approves; collapsing spaces keeps padding from pushing a fake step to the start of a wrapped line (#137).
- **Every message is escaped for MarkdownV2, template text and values alike,** and templates are plain text. Values are redacted and capped at 600 characters first, except the step list, which `steps_text` has already redacted step by step: redacting its `KEY=value` again would hide a place the approver must see (`AUTH0_DOMAIN=…`) (#38), and a message is cut at 4,096 characters without ending on a lone backslash. Reason: one unescaped `.` or `_` makes Telegram refuse the whole message, and a diagnosis is model text that may echo a log line (#22).
- **The templates are `.md` files in `prompts/notify/`, filled with `prompts.load`.** They are fixed text, not model prompts. Reason: the rule that every piece of fixed text is a file there (#22).
- **The opener goes out once per incident, from the runner.** `IncidentRunner` calls `Notifier.incident_opened` when it starts a new incident's thread (no checkpoint yet), before Gather, and not when a run goes on after a restart or a decision. A failure is logged and the run goes on. Reason: only `act` plans reach Telegram through the Approval node, so an incident that ends `no_action` or `budget` would otherwise be seen only on the dashboard; the runner is the one place every new incident passes through, whoever opened it (#72).
- **"It's expected" is a button on the incident-opened message and on a proposal's message, for an incident where "This is expected" applies** (`expected`, no id: the incident comes from `telegram_messages`). It goes through the same `Expectations.expected` as the dashboard, which rejects a pending plan first through `ApprovalStore.resolve`; the press is answered with what was recorded (cut at Telegram's 200 characters), and the buttons are removed only when it was done, so a press that fails leaves Approve and Reject to a plan that still waits. The button rides only on a message that goes out about the incident; the dashboard offers the action on every incident where it applies. An opened message is logged with an empty approval id, and a reply to it instructs the plan that waits, if any ([watcher](watcher.md#expected-exits-and-this-is-expected-84-256)). Reason: teaching Bleep that something is normal must take one tap where the page arrived (#256).
- **Buttons are removed when their question closes, not on the next press.** `IncidentRepo.on_finished` fires after any path makes an incident terminal (`set_status` to resolved, closed or failed, `close_unfinished` for a quiet close, a removed host or "It's expected"), and `ApprovalStore.on_decided` fires after a decision wins; `wiring.py` hooks `Notifier.incident_finished` and `Notifier.approval_decided` to them, so `incidents` never imports `notify`. An ended incident loses the buttons of every message in `telegram_messages` for it that has any (`buttons`, #380), the opener's "It's expected" included; a decision from either channel (approve, reject, instruct, a button or a reply) clears every message of the plan it answered, the proposal and its reminders, since a press clears only its own message and a reply none; a message logged after its incident ended or its plan closed (the run's Approval node can still send one just after an outside close) is cleared as it is logged. Clearing runs in the background, and each message is cleared on its own, and a failed `editMessageReplyMarkup` (message too old or deleted, Telegram down) is logged and swallowed ("message is not modified", a message already cleared, only at debug), so it never delays or fails a close or a decision; a press that still arrives is answered as closed as before (`answer_closed`). The message text is not edited: Telegram limits editing old messages, and the text stays a record of what was asked. Reason: a message that shows Approve or Reject must mean the question is still open (#291).
- **The notifier adds only `reminder` to the bus.** The nodes already publish `proposal`, `approval_requested`, `decision`, `notice` and `report` themselves. Reason: the same event twice would double the timeline (#22).
- **A Telegram outage never breaks a run.** `proposal` lets the error out, because the Approval node then tells the dashboard "answer it here"; the other calls log and go on. Reason: the dashboard is always a way to decide (#22).
- **`notify.setup(settings, db, bus, approvals, guard_log)` builds the notifier before the graph and `start(runner)` starts the poller after it.** Reason: the graph needs the notifier and the bot needs the runner (#22).
- **The report goes to Telegram for every outcome,** resolved, unverified, rejected, no action, replan limit and budget alike, as the incident's end message, without buttons. Reason: an incident that ends without a plan to approve would otherwise end in silence on Telegram (#27).
- **`GET /api/telegram/status` says whether the bot is set up, the chat id masked, when it last polled, and whether `TELEGRAM_BOT_TOKEN` is set** (`NotifySetup.status`, `schemas/telegram.py`). `configured` means a token and a chat id are both set, so the bot polls. The chat id is shown as `••••` plus its last two characters, or `••••` alone for an id of four characters or fewer; the token is only ever "set" or not. `last_poll` is the last `getUpdates` Telegram answered, set before the updates are handled, so a poller stuck in its backoff shows an old time. Reason: the settings page must tell a person whether approvals can come from Telegram without showing who the chat is or the token that controls it (#41).
- **Each incident is one thread in the chat**: an opener, replies to it, one end message (below). Reason: in a chat with several incidents every message used to look the same ("Incident inc_01M7…: container died on laptop/compose:shop"), so it was unclear which message started a problem, which belonged to one already running, which ended it, and that a third incident was the same broken container again (#380).
- **Every incident has a short name, `<subject> #<n>`** (`shop #14`, `M1 #3`), stored on the incident when it opens (`incidents.short_name`, migration 0027) and returned by the API with every incident. The subject is the service as the dashboard groups it (a Compose project, a Coolify app's resource name, a single container; the watcher passes the registry's name to `IncidentRepo.open_or_attach`), through `guard.titles.title_name` as in titles (#311), and the hosts file's `id` for a host; `n` counts every incident of the subject, counted inside the open's write transaction. It replaces the incident id in every message. Incidents from before it have none and show their id. Reason: two incidents on one service must read as such, and a later rename must not change old names (#380).
- **The opener is the only message of an incident that is not a reply.** It leads with `🔴 New: <short name> · <host>` (`· host` for a host incident) and one line of what was seen, from the incident's most telling signal (`prompts/notify/seen/`, the container's name through `title_name`). Every later message is a Telegram reply to it (`reply_parameters` with `allow_sending_without_reply`, so a deleted opener loses nothing). Every message is logged in `telegram_messages` with whether it has buttons; an incident's lowest message id is its opener. Reason: Telegram shows the opener as a quote on every message of the incident, and tapping it jumps there (#380).
- **Every message leads with an emoji and a word for what kind of moment it is**: 🔴 New, 🔁 Again, 🙋 Your call, 🛑 Plan refused, ⏰ Still waiting for you (with how long), ❌ Didn't hold, ℹ️ for a note in the middle of a run, and the end messages below. The templates are plain text; `format.bold_first_line` makes that line bold, the only markup. Reason: the chat list's preview alone tells what happened (#380).
- **The last message leads with the outcome**: ✅ Fixed in 4 min (`resolved`), ✅ Healthy again (`resolved` with no step of the plan that succeeded), ⚠️ Needs you · no action, ❔ Not verified, 🙅 Left to you (`rejected`, and a no-action run whose refused plan the person let go: Bleep had a plan, the person chose to leave it), 🛑 Stopped (budget, re-plans, with the fixed outcome text). It says the cause, what ran ("nothing" when nothing did), the checks of the last verification for a run that ended after one (from the `verification` event on the bus), at most 3 follow-ups and, when `BLEEP_DASHBOARD_URL` is set, a link to the incident's page; link previews are off. A passing verification sends no message of its own: it is told here. The summary and the "Decision" line are not sent: the thread shows the decision and the dashboard keeps the full report. Reason: one message per incident says how it ended, first (#380).
- **An incident that closes outside its run's report ends with one message of its own**: ✅ Back after 6 min (a waiting host answers again), 🤫 Quiet (made quiet, whether the run was going or waiting), 👍 Expected, ➖ Closed: host removed, ❗ Stopped on an error. `Notifier.notice` takes the `ending`, and `IncidentRunner.end` requires one from every caller (the watcher's removed host and quiet, "It's expected"). Pauses, the budget note and the watchdog stay ℹ️ notes. A notice is one line (`format.prose_line`), and a service's name in a quiet notice is quoted as in titles (`title_name`, #311), so a label cannot put a line that reads like an end inside it. Reason: exactly one message ends each incident, and it is the last one (#380).
- **One message of an incident at a time, and one end.** `Notifier._send` holds a lock per incident from the check for its opener to the log of what it sent (dropped when the incident finishes, unless a message still holds it), so two messages sent at once never both become openers. The end message is marked in `telegram_messages` (`is_end`); a close that lands after it (made quiet, "It's expected" or a removed host while the report node finishes) goes out as an ℹ️ note, and so would a report after a close. Reason: the race was real (a host that answers while its waiting message is being sent), and the design promises one end (#380).
- **Telegram's bookkeeping never fails a run.** A store error while threading a message (finding the opener, logging it) is logged and the message is dropped, as a Telegram outage is; the budget note in Investigate is guarded like every other call. Reason: before #380 a notice touched only Telegram, and a locked database must not turn a budget stop into a failed run (#380).
- **The few words built in code are templates too**: `where_host`, `ran_nothing` and the durations (`duration_min`, `duration_h`, `duration_days`), loaded through `format.phrase`. Reason: a translation (#375) changes files only (#380).
- **A repeat says so.** An incident is "Again" when it is folded (`fold_of`, [watcher](watcher.md#folded-repeats-84-258)) or its subject's last incident, of any kind, ended less than 24 hours before it opened (the longest repeat hold, #356, not tied to the fold window); its opener reads `🔁 Again: shop #16 · 1 h after shop #15` and replies to the earlier incident's last message, so the quote shows how that one ended. The Again line takes the place of the title's "(seen N times since …)" on Telegram. Reason: "after", not "same cause": the kind may differ (#380).
- **A folded repeat still sends no extra opener** (#258): its first real message (a plan, a refused plan or its end) becomes its opener and carries the Again line and what was seen; a folded host-unreachable incident's waiting message is its opener, and its ✅ Back goes out too, silently (`disable_notification`), so the thread ends and the pings stay as many as before. A message that becomes the opener because the opener never reached Telegram (Telegram was down, or the incident opened before this) works the same way with 🔴 New. Reason: no more messages than before (#380).
- **Button labels are unchanged** (Approve, Reject, It's expected, Let it go). Reason: the change is about telling messages apart; a label change is its own small choice (#380).
- **Limits of the threads (#380).** The lock is per process, which is all Bleep runs. Old incidents keep no short name. The dashboard does not show the short name yet.
