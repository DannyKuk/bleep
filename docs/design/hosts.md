# Hosts

How Bleep reaches its Docker hosts, groups containers into services, and reads host basics and GitHub.

- **Secrets by reference only.** A token is `{env: NAME}` or `{file: PATH}`, and a literal string where a reference is expected is rejected naming the field. Reason: secrets never live in the database, in YAML that gets committed, or anywhere the model can read them (#3).
- **`extra="forbid"` everywhere.** An unknown key is an error at startup. Reason: a typo such as `known_host_file` would otherwise silently drop a safety setting (#3).
- **One top-level GitHub token.** `github: {token: ...}` is a reference, shared by every service's `repo`. Reason: one token covers the repos of a small setup, and a per-service override can be added when a second token is needed (#3).
- **Two host kinds.** `ssh` (address, user, key file) for real servers and `socket` (a `unix://` or `tcp://` endpoint) for the demo stack and the machine Bleep runs on. Reason: the combination is validated so a half-filled host fails early (#3).
- **Key and known_hosts are mounted file paths.** The YAML holds the path, never the key. Reason: the key stays a mounted secret and the file is safe to share (#3).

## Store

- **Numbered SQL migrations in the package.** `store/migrations/NNNN_*.sql` run once each, recorded in `schema_version`. Reason: each feature adds its own tables without a migration framework (#3).
- **Migration 0013 is unused and must never be used; a new migration takes the number after the highest.** Each file runs once in number order among those not yet applied, so a 0013 added now would run after the later ones on a database that has them and before them on a fresh one, and the same files would build two schemas (#141).

## Hosts from the dashboard (#194)

A host can be added, changed and removed on the dashboard as well as named in the hosts file (`hosts/dashboard.py`, `api/host_settings.py`, the `dashboard_hosts` table from migration 0019). The hosts file wins for every host it names.

- **Only ssh hosts can be added on the dashboard; a socket host stays in the hosts file.** A body with `kind`, `endpoint`, `key_file`, `known_hosts_file` or `source` is a 422. Reason: an ssh host needs a private key the host accepts, so adding one proves the person already has access to it; a `unix://` path or a `tcp://` endpoint needs nothing, so a dashboard session could make Bleep the client of any Docker engine its own container can reach (the mounted socket, the demo's socket proxy, an unauthenticated TCP endpoint on a private network): every container's env and logs, and, after an approval the same session gives, stopping them. That is more than the operator who wrote the hosts file granted, and no check on the endpoint could tell an engine the person owns from one they do not (#194).
- **Where it lives.** The connection (id, name, address, port, user, Docker socket) is a row in SQLite: none of it is secret, and it is shown. The private key and the known_hosts line of the confirmed host key go to the secret file ([settings](settings.md#secrets-from-the-dashboard-135)) as `SSH_KEY:<id>` (the `multiline` kind: line feeds kept, a pasted CRLF made LF, every other control or invisible character refused) and `KNOWN_HOSTS:<id>` (one line). These names form a `SecretFamily`: never read from the env, never in `GET /api/secrets` or in the env view a plugin gets, and written only with `SecretStore.replace`, which sets or clears both in one write. An API shows each only as set or not, and no log line, error or trace carries either; a key that is not an unencrypted private key is refused in Bleep's words, never the parser's. What is stored is Bleep's own OpenSSH export of the key, not the paste, so text pasted around it is never kept, and a paste holding two keys is refused (#194).
- **Trust on first use is explicit.** `POST /api/settings/hosts/host-key` (`{address, port}`) fetches the host key the server offers without logging in (`hosts/ssh.fetch_host_key`, asyncssh's `get_server_host_key` with `config=[]`, at the vetted address below, within 5 s), keeps it ten minutes under a random `offer` id (at most 16, the oldest dropped) and answers its SHA256 fingerprint and type. Nothing is stored. `POST /api/settings/hosts` then takes the whole host with `ssh_key` and `host_key: {offer, fingerprint}`; the offer must be for the same address and port (422 otherwise), and the fingerprint must be the one offered (409), and it is used once, when the host is saved (a save that fails leaves it usable). The known_hosts line is built by Bleep from the key it fetched, never sent by the page. Check the fingerprint against `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` on the host: whoever sits between Bleep and the host at that moment is trusted otherwise, which is what trust on first use means (#194).
- **A dashboard host is never reached at loopback, link-local, unspecified or multicast addresses; private networks are allowed.** Its name is resolved once, and if any answer is loopback (127/8, `::1`), link-local (169.254/16, the cloud metadata address among it, `fe80::/10`), unspecified (`0.0.0.0/8`, `::`), multicast, one of the cloud metadata addresses outside link-local (`100.100.100.200`, `fd00:ec2::254`), in a translation range (`64:ff9b:1::/48`, SIIT `::ffff:0:0:0/96`), or an IPv6 form carrying one of those (IPv4-mapped, IPv4-compatible, 6to4, Teredo, NAT64), or is not an IP address at all, nothing is fetched or connected; else the first answer is the address used, so the connection goes where the check looked and a name rebound later (DNS rebinding) is checked again. This holds at the host-key fetch, when a host is saved or moved (a 422), and at every connect of the watcher (`hosts/ssh.vetted_address`, `is_refused`). The lookup is inside each one's time bound (5 s for the fetch and a save, the connect's outer bound for the watcher), so a hung resolver neither keeps the fetch busy nor holds a host's registry lock; a lookup that fails in any way counts as no answer. An IPv6 address with a scope id (`%`) is refused, since the scope may hold any text. 10/8, 172.16/12, 192.168/16, CGNAT (100.64/10) and `fd00::/8` stay allowed. Reason: SSH hosts live on private networks, so #135's public-only rule cannot apply, but nothing a person adds as a remote host is on Bleep's own machine or its cloud's metadata service, and those are where a session could reach what the operator never exposed (#194).
- **The host-key fetch says one sentence for every failure, and runs one at a time.** A name that does not resolve, a refused address, a closed port, a server that is not SSH, one that offers no key, one that stays silent and any error Bleep did not expect all answer 502 "Could not get an SSH host key from that address."; the cause is logged by its error type only. A second fetch while one runs is a 429. Reason: a session must not be able to map Bleep's networks (which ports are open, which speak SSH) through the wording; only the 5 s a silent address takes still differs, which no answer can hide without making every fetch wait that long (#194).
- **A dashboard host trusts only its confirmed key.** `SshSession` reads the key and the known_hosts line from the secret file at every connect and passes asyncssh the key and the one host key the line holds for the host's address and port, as a list rather than a lookup by name, since the connection goes to the pinned address; it never falls back to `~/.ssh/known_hosts` or a key file, and a missing key or host key refuses to connect with a sentence saying which. A host key that changed later refuses the connection, as for a hosts file host; the person fetches it again and sends the new fingerprint as `host_key` on `PUT`, which replaces it and keeps the key (#194).
- **A key is bound to its connection.** A `PUT /api/settings/hosts/{id}` that changes the address, port or user clears the key and the host key in the same write, unless new ones come in the same body (the host key's offer then for the new address). Every `PUT` and `DELETE` sends the host's `version` in `If-Match` (428 without it, 409 with the current one when stale); the version is a hash of the row, whose revision goes up with every change, a key's included. So a key typed for one connection is never stored with another, and a dashboard session can never point an existing key at a new server. The keys are written before the row: a crash in between leaves the old connection with keys its host key check refuses, or with none (#194).
- **Applied without a restart.** The change is told to the watcher manager, then the settings store (`DashboardHosts.subscribe`). Added: the registry gets the host and its loops start; the first tick connects. A new connection, Docker socket or key: the old connection is closed, the last listing dropped and the loops started again from nothing, so a listing of another machine is never diffed against the old one's as deaths. A new address, port or user (`HostChange.moved`) also drops the detector's pending deaths, streaks and timers for the host and its held URL failures, so nothing pending on the old machine opens an incident against the new one, and puts a notice on the host's open incidents that what Bleep reads from now on comes from the new connection (an approved plan cannot act across the move: Execute finds the targets' container ids changed and plans again). A new key alone keeps them: same machine. A new name alone changes the name. Removed: the loops stop, every open incident on the host (its services' included) is closed by `IncidentRunner.end` with the notice "Closed: the host was removed from Bleep on the dashboard, so it is not watched." on its timeline and in the channels (with "A step of the approved plan may already have run" when it was executing; an incident finished meanwhile is left as it is), the run is cancelled, a pending approval can no longer be decided from any channel (`ApprovalStore.resolve` refuses a finished incident), the detector forgets the host, the registry closes the connection (even when closing an incident failed, so the host can be added again), and the host's overrides are deleted, so a host added later under the same id starts with none (#194).
- **A decision that lands while a host is removed runs nothing.** `end` marks the incident ended before its first await, then closes it, which shuts `ApprovalStore.resolve` for it on every channel, then cancels its run. A yes that won just before is resumed into nothing: `_resume` and `_drive` refuse an ended or finished incident, Execute checks the incident is still open before it starts and before each step, and `IncidentRepo.set_status` never changes a finished incident's status, so a run racing the close cannot open it again. Reason: a Telegram tap can arrive at any moment, and while the incident is being closed the host's connection is still open (#194).
- **The hosts file wins.** A hosts file host shows as `source: "file"` and cannot be changed or removed on the dashboard (409), and no dashboard host may take its id. A dashboard host whose id the hosts file names later is left out at start with a warning; it can still be removed from the dashboard, which deletes its row and keys and leaves the file's host alone. Keys in the secret file for a host that no longer exists are removed at start (#194).
- **Ids, addresses and names are checked before anything else.** An id is `[a-z0-9][a-z0-9-]{0,39}` (it is part of every service id and of the secret names); an address is a host name or an IP literal, nothing an SSH client could read as a user, port, option or path; a user is a login name not starting with `-` or `.`; the Docker socket an absolute path without `.` or `..`; the name at most 80 characters without control characters. A 422 says where and why, never the value (#194).
- **Rules, URLs and protected containers of a dashboard host** are set like any host's (`PUT /api/settings`), all of them dashboard overrides, since no file layer lies below. Bleep's own containers (`bleep.self=true`) are left out of its services as on every host (#194).
- **A 422 from these routes names fields Bleep knows and nothing else the client sent:** a key Bleep does not know is `<unknown field>`, since a pasted key could arrive as a JSON key; values are never quoted; a body that is not JSON is a 422 (#194).
- **Limits.** The key is unencrypted at rest, as every value of the secret file is. A dashboard host's overrides (rules, URLs, protected containers) are stored by host id, so when the hosts file later names a host with that id they apply to it, and removing the shadowed dashboard entry leaves them; protection only ever adds, so this can protect more, never less. The routes rely on the session cookie's `SameSite=Lax` like the rest of the API, with no Origin check. If closing an incident fails at the database while its host is removed, the incident stays open but this process does not run it again until a restart (the host is dropped all the same). A decision that wins its approval in the instant before a removed host's incident is closed is answered "approved" on the dashboard or in Telegram, then the close notice follows and nothing runs.

## Engine connections

How Bleep reaches each host's Docker engine (`hosts/ssh.py`, `hosts/engine.py`). The mechanism was settled by a spike on two real hosts: [Docker over SSH](../decisions/docker-over-ssh.md).

- **One asyncssh connection per ssh host, with the Docker socket forwarded.** `SshSession` forwards the host's `docker_socket` to a local unix socket (`forward_local_path`), the docker SDK talks to that socket, and the same connection runs host commands. Reason: it needs no `docker` on the remote `PATH` (the Mac host has none) and keeps reconnecting in one place (#4).
- **The forward lives in a private temp dir (mode 0700), new on every reconnect.** Reason: only Bleep's user can reach the engine through it, and after a drop the old socket file is gone with the listener, so a fresh path is cleaner than reusing one (#4).
- **`open()` sweeps stale forward dirs.** It removes this user's `bleep-ssh-*` dirs that are older than 60 s, have no listening socket and are not used by an open session of this process. Reason: a crashed Bleep leaves its dirs behind, and a dir younger than 60 s may belong to a session that is still opening (#4).
- **The host key is always checked.** `known_hosts_file` pins it. When the field is unset, the `known_hosts` argument is left out, so asyncssh checks `~/.ssh/known_hosts`. With neither file, Bleep refuses to connect. There is no setting that turns checking off. Reason: passing `known_hosts=None` would silently trust any key (#4).
- **The address is lowercased before connecting.** OpenSSH does the same for its lookup. Reason: asyncssh matches known_hosts names case-sensitively, so a mixed-case name such as `Mac-Mini.local` misses its lowercase `mac-mini.local` entry, as it did in the smoke test (#4).
- **Only `hosts.yaml` decides how Bleep connects.** It passes `config=[]` and `agent_path=None`. Reason: asyncssh's default `config=()` loads `~/.ssh/config`, which could redirect a host or change its key without anything in `hosts.yaml` showing it (#4).
- **Keepalive every 15 s, 3 misses.** Reason: a network path that vanishes without a reset closes the connection after about 45 s, which ends the event stream instead of leaving it blocked (#4).
- **Every SDK call runs in `asyncio.to_thread`, the client constructor included.** Reason: the SDK blocks, and on an ssh host the forward is served by the same event loop, so a call on the loop would wait for itself (#4).
- **The event stream has a reader thread of its own.** It hands events to the async side through an `asyncio.Queue`. Reason: it blocks for days, and in the default executor it would hold one of the few workers that every other SDK call needs (#4).
- **The event queue holds at most 1,000 unread events.** On overflow the stream ends with `EngineUnavailable` ("event backlog"), and the watcher reconnects and replays with `events(since=...)`. Reason: a stuck consumer must not grow memory without bound, and events are never dropped silently (#4).
- **A stop that arrives while a stream is still opening is kept.** `stop_events()` bumps a counter, and the stream checks it, together with `close()`, once the initial `events` request returns. Reason: otherwise a stop during that request would be lost and the stream would run on (#4).
- **The drop contract.** A lost connection makes every engine call raise `EngineUnavailable(host_id, cause)`. `stream_events()` raises it as well when its stream ends without being asked to, because the SDK ends the iterator silently on a drop. It returns normally only after `stop_events()`, `engine.close()` or `SshSession.close()`, each of which sets its stop flag before closing. Reason: an exception handler alone never sees a silent end, and a deliberate stop must never look like a lost host (#4).
- **The engine never reconnects on its own.** The watcher owns reconnect with backoff: `SshSession.ensure_open()` (a new connection and forward when the old one is gone), then `engine.reconnect()` (a new SDK client against the current forwarded socket, then a ping). Reason: one owner for backoff and for marking a host unreachable, and an engine that is honest about being down (#4).
- **`events(since, until)` pings after reading its window.** Reason: a window cut short by a drop ends just like a complete one, so the ping tells them apart (#4).
- **Events are filtered on the engine to container life-cycle actions,** and `exec_*` events are dropped if any get through. Reason: on a Coolify host health-check `exec_*` events were every event in the saved sample (108 in 30 s), and their action text carries the full command line (#4).
- **`containers()` uses the sparse list plus targeted inspects.** The sparse list (`GET /containers/json`, one request) has state, labels and, on API 1.56, health, but no restart policy or start and finish times, which the detector needs. Each container is inspected again when its list row's State or Status text changed since its last inspect. Docker's Status (`Up 2 hours`, `Exited (1) 2 minutes ago`, `(healthy)`) changes on most restarts, exits and health changes. It is humanized, though, so in a crash loop two polls can show the same text with a new start time. Rows that can repeat across a restart are therefore always inspected: State `restarting`, and an age in seconds (`Up 5 seconds`, `Less than a second`). An act on a container, or a streamed or replayed event for it, also drops its cached inspect. Measured: the spike's Linux host listed 10 containers in 602 ms with `sparse=False` (one inspect each, one after another) and in 80 ms sparse. On a local engine with 8 containers, `sparse=False` took 33.4 ms, sparse 13.7 ms, and `containers()` 19.9 ms cold and 13.1 ms warm (medians of 5). Reason: the 15 s poll costs about a sparse list in the steady state, and the inspects that remain run 8 at a time (#4).
- **Each host's watcher tick calls `Registry.refresh`** (and `reconnect` when the host is down), so the read API serves the same snapshot the watcher judged. `Registry.snapshot(host_id)` returns every container of the last listing, Bleep's own included, which the service view leaves out (#10, #13).
- **`SshSession.open()` and `ensure_open()` are bounded by `CONNECT_TIMEOUT_S` + 5 s, and the socket forward by `CONNECT_TIMEOUT_S`.** asyncssh's own `connect_timeout` does not cover every stage with a host that vanished without a FIN, and a connect that never returns would hold the session lock and block `close()`. Reason: the watcher's reconnect must fail fast and release the lock (#4, #5, #13).
- **Typed errors.** `EngineUnavailable` (unreachable: retry later), `ContainerNotFound`, `EngineError` (the engine answered and refused, for example a socket proxy's 403), and `SshUnavailable` from the session. Reason: the watcher reconnects only on the first; the others are answers (#4).
- **Host commands take an argv list only.** `run` refuses a string and joins the list with `shlex.join`. Reason: SSH exec takes one string for the remote shell, so every argument is quoted and nothing free-form reaches it (#4).
- **A command that hangs or floods is ended.** `run` reads stdout and stderr as bytes, in chunks, up to 1,000,000 bytes each. On the 20 s timeout or on the cap it terminates the remote process and closes its channel. Reason: an abandoned channel holds one of sshd's sessions (10 by default), and when they run out every later command fails. In the smoke test, 12 timed-out `sleep 30` calls in a row left no process and no session behind (#4).
- **`ContainerDetail.env` is raw.** Reason: the engine reports what Docker says. Redaction (`guard.redact_env`) happens in the tools, before anything reaches a model, a log or the database (#4).

## Service discovery and the registry

How containers become services and how Bleep keeps track of each host (`hosts/discovery.py`, `hosts/registry.py`). The label evidence is in [Docker over SSH](../decisions/docker-over-ssh.md#coolify-labels-the-grouping-rule-5).

- **Service key: `coolify.applicationUuid`, else `id:<coolify.applicationId>`, else `compose:<com.docker.compose.project>`, else `container:<name>`.** The display name is `coolify.resourceName` for a Coolify app, else the project or container name (no prefix). Reason for the prefixes: a single container `app` and a compose project `app`, or a project named like a UUID or `x-pr-1`, would otherwise merge silently (#5).
- **Display names are not unique, keys are.** A Coolify app's name is `coolify.resourceName`, else its key. Reason: the UUID is unique and groups an app's containers, while `resourceName` is only a name that two apps can share, and merging them would merge their incidents (#5).
- **Coolify membership is `coolify.type == "application"`, or, without that label, the presence of `coolify.applicationId`.** Only members use the Coolify keys; a Coolify database or service falls back to its compose project or name. Reason: other resource types were not seen on a real host, and the fallback groups them safely (#5).
- **A preview deployment (`coolify.pullRequestId` present and not `0`) is its own service,** keyed `<key>-pr-<n>` and named `<name> (PR <n>)`. Reason: a pull request's incident must not merge into the live app's, and the name keeps it from taking the app's overrides (#5).
- **Coolify's own containers are not excluded.** They group by compose project, then by name. Reason: a dead `coolify-proxy` takes every app on the server down, so it must be watched (#5).
- **`source` is `coolify`, `compose` or `single`,** by the label that decided the key (#5).
- **Overrides in `hosts.yaml` match the service key or the display name; the key wins on a conflict.** If an override key matches no service key but the display names of two or more services, discovery raises `AmbiguousOverride` naming the keys to use. Reason: a human writes `shop` or `dkwebsite`, not `compose:shop` or a UUID, but a name that fits two services must not pick one silently (#5).
- **A service takes every override that matches it, by key and by display name: the protected containers of both are unioned, and the URLs, repo, docs paths and rules come from the key's override when there is one, else the name's.** `group_services` used to drop a name override once the service also had one under its key, so a hosts file's `shop: {protected_containers: [shop-db-1]}` was lost from the service as soon as the dashboard stored a URL under `compose:shop`. The plan check and the act tools read every override's protected containers on the host (`protected_names`), not the service's, so they kept refusing; the service page's lock and `hosts_file_protected_containers` did not. A name shared by services that have overrides under their keys still goes, whole, to the one that has none, and `AmbiguousOverride` is raised as before only when that leaves more than one. Reason: the dashboard can never unprotect what the hosts file protects ([settings](settings.md)), whichever key either of them used (#230).
- **`protected` is the override's `protected_containers`, by container name.** Reason: act tools check a container, not a service (#5).
- **Containers labelled `bleep.self=true` are left out of every service.** Reason: Bleep must never open an incident on itself or offer to restart itself (#5).
- **`Registry.start()` connects all hosts at once and never raises.** A host that fails stays in the registry with `reachable=False` and the error text. Reason: Bleep must start while a host is down, and the watcher brings it back (#5).
- **`refresh(host_id)` lists the containers.** On success the host is reachable with `last_seen` set to now. On `EngineUnavailable` it is marked unreachable, and the last snapshot and `last_seen` stay. Reason: tools and the host incident need to say what was last seen and when (#5).
- **`reconnect(host_id)` is `SshSession.ensure_open()`, then `engine.reconnect()`,** or the connector again for a host that never connected, and then a refresh, so `reachable` reflects reality. It catches every exception, records it on the host and returns whether the host is reachable; it never raises. Reason: the watcher owns the backoff and the decision to give up, and must not need a handler for each kind of failure (#5).
- **One lock per host serializes connect, reconnect and refresh.** Reason: two concurrent reconnects on a down host would both build a session and engine, and the first would leak (#5).
- **A service override that matches several display names does not make the host unreachable.** `refresh` keeps the previous services (so protected containers stay protected), or groups without overrides on the first poll, stays reachable, puts the message in `HostState.error`, and logs it once per distinct text. Reason: it is a config problem that depends on which containers are live, and it must neither crash a poll nor hide the host (#5).
- **After `close()`, refresh and reconnect do nothing.** `close()` takes each host's lock, and a reconnect that finishes connecting after `close()` closes what it opened. Reason: a watcher task still running at shutdown must not reopen what was just closed (#5).
- **`container(host_id, ref)` takes a name, an id, or a unique id prefix of at least 12 characters;** an ambiguous prefix gives None. Reason: tools and humans copy the short id Docker prints (#5).

## Host shell and host basics

The allowlisted, read-only shell and what is read through it (`hosts/shell.py`, `tools/host_read.py`).

- **A command runs only if, after `shlex.split`, it equals one argv template exactly.** Extra arguments, `;`, `&&`, `|`, `$(...)`, backticks, redirects, globs, `FOO=1` prefixes, paths like `/bin/df` and an empty string all fail the match. Reason: the allowlist is enforced by the tool, never by the prompt, and an exact match leaves no syntax to smuggle a second command into (#7).
- **No shell ever sees the text.** The parsed list goes to `SshSession.run`, which quotes each argument. Reason: a metacharacter that somehow survived parsing would still be a plain argument (#7).
- **Commands per OS.** Both: `uname -s`, `df -P`, `uptime`. Linux: `free -b`, `cat /proc/loadavg`, `nproc`, `top -b -n 1`, `journalctl -n N --no-pager [-u UNIT]`. macOS: `vm_stat`, `sysctl -n hw.memsize hw.ncpu vm.loadavg`, `top -l 1 -n 15`. A command from the other OS is refused with the OS named. Reason: these were captured on a real Ubuntu and a real macOS host, and each OS's `top`, memory and load tools differ (#7).
- **`journalctl` takes at most 500 lines and a unit matching `[\w@.-]+` that does not start with `-`.** Reason: bounded output, and a unit must not be able to pass an option such as `-f` that follows the log forever (#7).
- **Host command output is untrusted.** `host_command` redacts, cleans and wraps it like the Docker tools, and a refused command is returned as text and recorded as `refused_command` in the guard log. Reason: journal lines are written by whatever runs on the host (#7).
- **`host_command` is not offered to the model on a socket host.** `ToolSpec.offered` decides per incident host, and the tool needs an ssh session. Reason: there it could only answer "host commands need an SSH host", which wasted two of the eight Investigate calls in the first live run (#75).
- **Darwin memory available = (free + inactive + speculative + purgeable) pages x the page size from `vm_stat`; total is `hw.memsize`.** Reason: macOS has no "available" figure, and these pages can be handed out without swapping (#7).
- **Darwin load comes from `sysctl vm.loadavg`** (`{ 1.15 1.80 3.61 }`), Linux from `/proc/loadavg`. Reason: `uptime` text differs per OS and locale (#7).
- **`df -P` rows are filtered.** Dropped: `tmpfs`, `devtmpfs`, `overlay`, `shm`, `squashfs`, `devfs`, `map ...` automounts, and on macOS every `/System/Volumes/*` mount except `Data`. Repeated mounts are shown once. Reason: the Coolify host listed one overlay per container (9 identical rows), and macOS lists seven system volumes that share one disk (#7).
- **A field that cannot be read is None and logged; it never raises.** A lost connection is the exception: it propagates. Reason: one odd `free` output must not blank the host's other numbers, but a dead connection must not be mistaken for an empty host (#7).
- **Basics are refreshed with the container list but at most every 60 s, a failed read included, and a failure keeps the old basics.** A socket host uses the engine's `info` (CPUs and memory, no disks or load). Reason: 60 s is the host probe cadence, six SSH commands do not belong in every 15 s poll, and unreadable basics must not mark a reachable host down (#7).
- **`BasicsView` numbers are nullable.** Reason: a socket host has no load and a parse can fail, and a made-up 0 would read as a real value (#7).

## GitHub

How Bleep reads a service's repo (`hosts/github.py`, `tools/github.py`).

- **One small REST client, beside the hosts file.** `GithubClient` reads a repo's commits (`commits`, `commit`), its README (`readme`) and the files under a folder (`list_files`, `read_file`), over `httpx`, nothing else. It lives in `hosts/` because the token and each service's `repo` are set in the hosts file, and so that both the GitHub tools and the knowledge ingest (#39) can import it without `knowledge` importing `tools`. Reason: one client, one place for the token and the error handling (#37).
- **A service names what knowledge search reads of its repo with `docs_paths` and `readme`; the rules for both are in [knowledge](knowledge.md).** Reason: the hosts file is where a service's `repo` is set, so its docs are named beside it (#142).
- **The token is optional.** `github_token` resolves the hosts file's `github.token`; when that is `{env: GITHUB_TOKEN}` or there is no `github` section, the token is `GITHUB_TOKEN` from the env or the dashboard's secret file, read at every request (`wiring.github_token_source`, [settings](settings.md#secrets-from-the-dashboard-135), #135). A token set in neither place, an unset variable or an empty one all mean no token, never an error; an unset variable the hosts file names otherwise is logged as a warning, since the hosts file asked for one. Without one Bleep reads public repos only, at GitHub's 60 requests an hour per IP; `config/hosts.demo.yaml` points at `GITHUB_TOKEN`, which is empty in `.env.example`. Reason: the demo must run with no GitHub account, and a missing token is not a reason to refuse to start (#37).
- **The token goes only into the `Authorization` header.** Bleep's own errors never carry GitHub's message, a URL with a query or the token. Reason: secrets never reach the model or the logs (#37).
- **Every failure is a `GithubError` with Bleep's own words**: `NotFound` for 404 and 422, with its `kind` (`repo`, `commit` or `file`; a private repo without a token looks like no repo, and a commit's 404 is the repo's, its 422 the sha's), `RateLimited` for 429 or a 403 with `x-ratelimit-remaining: 0`, `retry-after` or "rate limit" in its body (GitHub sends some secondary limits with neither header), carrying the reset time from `x-ratelimit-reset` or `retry-after`, `GithubUnavailable` for a network error, a timeout or a 5xx, and a plain `GithubError` for a 401, any other status or an answer that is not the expected JSON. Reason: the tools turn each into one readable sentence, and the ingest can skip a repo on any of them (#37).
- **Repo names, shas and paths are checked before any request.** A repo is `owner/name`, not `.` or `..`, and the hosts file refuses any other `repo` at startup; a sha is 7 to 40 hex characters; a path is relative, with no empty, `.` or `..` part, backslash or control character, and is URL-quoted, so `docs/Getting Started.md` or `docs/c#.md` is read as itself. Reason: the sha comes from the model and a path can come from a repo's own listing, so neither may change the request's URL, while ordinary file names must still be readable for the knowledge ingest (#37).
- **Redirects are followed.** Reason: GitHub answers a renamed or moved repo with a 301, and httpx drops the `Authorization` header when a redirect leaves the host (#37).
- **`list_files` walks sub-folders breadth first, at most 30 folders and `max_files` files (200).** A sub-folder that 404s is skipped; the folder asked for raises `NotFound`; a listing that stops at a limit logs a warning. Reason: each folder is one request against the rate limit (#37). With `suffixes` it lists only the files whose name ends with one of them, in any case, and only those count toward `max_files`; the knowledge ingest passes the markdown suffixes. Reason: images or data files listed first would otherwise fill the cap (#142).
- **A file over 1 MB is `TooLarge`,** a `GithubError` of its own: the contents API serves it without its text. Reason: the knowledge ingest skips such a file, and a README that size, while it keeps the doc of a file that failed in any other way (#142).
- **A new `httpx.AsyncClient` per request.** Reason: a few requests per incident or per daily ingest do not need a pooled client, and none has to be closed at shutdown (#37).
- **The tools are `recent_commits(since_hours=48, path=None)` and `commit_diff(sha, max_chars=8000)`, offered only for a service with a `repo`.** `ToolContext` carries the incident's service id for that, and a host incident gets neither. Reason: a tool that could only answer "no repo" wastes a call (#37).
- **Commit text is untrusted, like host output.** Both results go through the guard, so they are redacted, cleaned and wrapped, both descriptions tell the model the data was written by whoever can push to the repo, and an escaped wrapper tag in either names "commit messages and diffs of the service's repo" in the report's planted-orders sentence (the `commits` planted source). Reason: anyone who can push to the repo writes those messages (#37).
- **The list shows at most 20 commits, newest first, each message cut at 600 characters and each author at 80,** stops with "N more commits not shown" before the guard's limit, and says when GitHub was asked for no more than 20. **A diff is cut from its end:** its head (sha, author, date, the message and the changed files with their line counts, "and N more files not listed" past it) takes at most half of `max_chars`, then the patches follow in order, and a cut names the files not shown in full. Every piece is measured as the guard will write it, redacted and escaped, since `<redacted>` can be longer than the secret it hides. Reason: the guard keeps a text's tail, which suits logs; for commits the newest and for a diff its head matter most, so these tools cut first and the guard never has to; a diff of short tokens would otherwise have been cut by the guard to its tail, losing the sha and the file list (#37).
- **Every GitHub failure comes back as a sentence the model can go on from**, for example "GitHub's rate limit is spent until 12:40 UTC. Without a token (GITHUB_TOKEN) it is 60 an hour. Go on without the repo." Reason: a missing repo or a spent limit must not end the investigation (#37).
