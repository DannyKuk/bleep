# Hosts

How Bleep is told which Docker hosts to watch.

- **Secrets by reference only.** A token is `{env: NAME}` or `{file: PATH}`, and a literal string where a reference is expected is rejected naming the field. Reason: secrets never live in the database, in YAML that gets committed, or anywhere the model can read them (#3).
- **`extra="forbid"` everywhere.** An unknown key is an error at startup. Reason: a typo such as `known_host_file` would otherwise silently drop a safety setting (#3).
- **One top-level GitHub token.** `github: {token: ...}` is a reference, shared by every service's `repo`. Reason: one token covers Danny's repos, and a per-service override can be added when a second token is needed (#3).
- **Two host kinds.** `ssh` (address, user, key file) for real servers and `socket` (a `unix://` or `tcp://` endpoint) for the demo stack and the machine Bleep runs on. Reason: the combination is validated so a half-filled host fails early (#3).
- **Key and known_hosts are mounted file paths.** The YAML holds the path, never the key. Reason: the key stays a mounted secret and the file is safe to share (#3).
- **Numbered SQL migrations in the package.** `store/migrations/NNNN_*.sql` run once each, recorded in `schema_version`. Reason: later tasks add their own tables without a migration framework (#3).

## Engine connections

How Bleep reaches each host's Docker engine (`hosts/ssh.py`, `hosts/engine.py`). The mechanism was settled by a spike on two real hosts: [Docker over SSH](../decisions/docker-over-ssh.md).

- **One asyncssh connection per ssh host, with the Docker socket forwarded.** `SshSession` forwards the host's `docker_socket` to a local unix socket (`forward_local_path`), the docker SDK talks to that socket, and the same connection runs host commands. Reason: it needs no `docker` on the remote `PATH` (the Mac host has none) and keeps reconnecting in one place (#4).
- **The forward lives in a private temp dir (mode 0700), new on every reconnect.** Reason: only Bleep's user can reach the engine through it, and after a drop the old socket file is gone with the listener, so a fresh path is cleaner than reusing one (#4).
- **`open()` sweeps stale forward dirs.** It removes this user's `bleep-ssh-*` dirs that are older than 60 s, have no listening socket and are not used by an open session of this process. Reason: a crashed Bleep leaves its dirs behind, and a dir younger than 60 s may belong to a session that is still opening (#4).
- **The host key is always checked.** `known_hosts_file` pins it. When the field is unset, the `known_hosts` argument is left out, so asyncssh checks `~/.ssh/known_hosts`. With neither file, Bleep refuses to connect. There is no setting that turns checking off. Reason: passing `known_hosts=None` would silently trust any key (#4).
- **The address is lowercased before connecting.** OpenSSH does the same for its lookup. Reason: asyncssh matches known_hosts names case-sensitively, so `MacBook-Pro-M1.local` missed the `macbook-pro-m1.local` entry in the smoke test (#4).
- **Only `hosts.yaml` decides how Bleep connects.** It passes `config=[]` and `agent_path=None`. Reason: asyncssh's default `config=()` loads `~/.ssh/config`, which could redirect a host or change its key without anything in `hosts.yaml` showing it (#4).
- **Keepalive every 15 s, 3 misses.** Reason: a network path that vanishes without a reset closes the connection after about 45 s, which ends the event stream instead of leaving it blocked (#4).
- **Every SDK call runs in `asyncio.to_thread`, the client constructor included.** Reason: the SDK blocks, and on an ssh host the forward is served by the same event loop, so a call on the loop would wait for itself (#4).
- **The event stream has a reader thread of its own.** It hands events to the async side through an `asyncio.Queue`. Reason: it blocks for days, and in the default executor it would hold one of the few workers that every other SDK call needs (#4).
- **The event queue holds at most 1,000 unread events.** On overflow the stream ends with `EngineUnavailable` ("event backlog"), and the watcher reconnects and replays with `events(since=...)`. Reason: a stuck consumer must not grow memory without bound, and events are never dropped silently (#4).
- **A stop that arrives while a stream is still opening is kept.** `stop_events()` bumps a counter, and the stream checks it, together with `close()`, once the initial `events` request returns. Reason: otherwise a stop during that request would be lost and the stream would run on (#4).
- **The drop contract.** A lost connection makes every engine call raise `EngineUnavailable(host_id, cause)`. `stream_events()` raises it as well when its stream ends without being asked to, because the SDK ends the iterator silently on a drop. It returns normally only after `stop_events()`, `engine.close()` or `SshSession.close()`, each of which sets its stop flag before closing. Reason: an exception handler alone never sees a silent end, and a deliberate stop must never look like a lost host (#4).
- **The engine never reconnects on its own.** The watcher owns reconnect with backoff: `SshSession.ensure_open()` (a new connection and forward when the old one is gone), then `engine.reconnect()` (a new SDK client against the current forwarded socket, then a ping). Reason: one owner for backoff and for marking a host unreachable, and an engine that is honest about being down (#4).
- **`events(since, until)` pings after reading its window.** Reason: a window cut short by a drop ends just like a complete one, so the ping tells them apart (#4).
- **Events are filtered on the engine to container life-cycle actions,** and `exec_*` events are dropped if any get through. Reason: on a Coolify host health-check `exec_*` events were every event in the saved sample (108 in 30 s), and their action text carries the full command line (#4).
- **`containers()` uses the sparse list plus targeted inspects.** The sparse list (`GET /containers/json`, one request) has state, labels and, on API 1.56, health, but no restart policy or start and finish times, which the detector needs. Each container is inspected again when its list row's State or Status text changed since its last inspect. Docker's Status (`Up 2 hours`, `Exited (1) 2 minutes ago`, `(healthy)`) changes on most restarts, exits and health changes. It is humanized, though, so in a crash loop two polls can show the same text with a new start time. Rows that can repeat across a restart are therefore always inspected: State `restarting`, and an age in seconds (`Up 5 seconds`, `Less than a second`). An act on a container, or a streamed or replayed event for it, also drops its cached inspect. Measured: the spike's Linux host listed 10 containers in 602 ms with `sparse=False` (one inspect each, one after another) and in 80 ms sparse. On a local engine with 8 containers, `sparse=False` took 33.4 ms, sparse 13.7 ms, and `containers()` 19.9 ms cold and 13.1 ms warm (medians of 5). Reason: the 30 s poll costs about a sparse list in the steady state, and the inspects that remain run 8 at a time (#4).
- **Typed errors.** `EngineUnavailable` (unreachable: retry later), `ContainerNotFound`, `EngineError` (the engine answered and refused, for example a socket proxy's 403), and `SshUnavailable` from the session. Reason: the watcher reconnects only on the first; the others are answers (#4).
- **Host commands take an argv list only.** `run` refuses a string and joins the list with `shlex.join`. Reason: SSH exec takes one string for the remote shell, so every argument is quoted and nothing free-form reaches it (#4).
- **A command that hangs or floods is ended.** `run` reads stdout and stderr as bytes, in chunks, up to 1,000,000 bytes each. On the 20 s timeout or on the cap it terminates the remote process and closes its channel. Reason: an abandoned channel holds one of sshd's sessions (10 by default), and when they run out every later command fails. In the smoke test, 12 timed-out `sleep 30` calls in a row left no process and no session behind (#4).
- **`ContainerDetail.env` is raw.** Reason: the engine reports what Docker says. Redaction (`guard.redact_env`) happens in the tools, before anything reaches a model, a log or the database (#4).
