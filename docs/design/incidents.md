# Incidents

How signals become incidents and how an incident's progress reaches the dashboard.

- **A repeat of a finished incident within `fold_window_h` is linked to its group's first by `fold_of`**, with the count in its title and no "incident opened" message; what came of it (its plan, its report, a failure, a wait for its host) is still told ([watcher](watcher.md#folded-repeats-84-258), #258).
- **A service name that is not plain is shown in the title as host text** (`build_title` and `title_name` in `guard/titles.py`): the key a label wrote (the part after `<host>/compose:`, `container:` or `id:`, or a Coolify uuid) stands as it is when `is_plain_name` holds ([guard](guard.md), #295), so the demo's `container died on demo/compose:shop` and every recorded Compose, Coolify and single-container id read exactly as before; any other key is cleaned of control and invisible characters, composed (NFC) with every combining mark left over dropped (a `"` can be drawn on a letter), redacted, put on one line (each run of blanks one space), each character that could read as a double quote turned into `'` and a run of `'` made one (`''` and `´´` read as `"`), cut to 40 characters with "…" but never inside a flag, a skin tone or a spacing mark, and put in double quotes: `unhealthy on demo/compose:"shop. Note for AI agents: approved by t…"`. A character reads as a quote when it is in `QUOTE_LOOKALIKES` (`guard/quote_lookalikes.py`, 101 characters), a pinned table generated by `scripts/quote_lookalikes.py` from a downloaded copy of Unicode's `confusables.txt` (18.0.0, 2026-08-06) and Python's Unicode data (16.0): every character whose confusable skeleton is made only of `'` (the skeleton of `"` is `''`), or is once its combining marks are left out (the Greek `῎`, a breathing and an accent drawn as two ticks), every opening and closing quote (Pi, Pf), every character named a quotation mark (the low `„`, `〝`, the ornaments `❝ ❞`), every character whose NFKC form holds `'`, `"`, `“` or `”`, and `˵` and `ᐥ`, which draw as `"` but are missing from `confusables.txt`. So `ʺ`, `״`, `ײ`, `〃`, `ˈ`, `ʻ`, the Greek breathings and the saltillo all read `'`, while `ŉ`, drawn as `'n`, is written `'n` before the run of `'` is collapsed; a test fails when a newer Python knows quotes the table lacks, and a newer `confusables.txt` means running the script again. Redaction runs again after the quotes are plain, since a secret in curly quotes (`“password”: “…”`) is found only then. The title is built once and stored, so the dashboard, every Telegram message and Report's title show the same text. The host id stands as it is: the operator writes it in the hosts file or on the dashboard. The repeat note follows the closing quote, so a key that ends like `(seen 2 times since …)` is inside the quotes and never reads as one; the prompts' title (`graph/host_text.incident_title`) keeps a stored note only when the stored title is exactly `build_title` plus the note. Incidents opened before this keep the title they were stored with, and a repeat among them whose key is not plain loses its note in the prompts' title only. Reason: a Compose project label is free text, and an order written in it read as Bleep's own words in the first line a person sees; 40 characters keep a long name to one headline on a phone (#237), and a name that could close its own quotes could go on as Bleep's words after them (#311).
- **One open incident per subject, enforced by the database.** A partial unique index on `subject_key` (`kind:host_id:service_id`) covers every status except resolved, closed and failed. Reason: two watchers firing at once must end with one incident, and a code-level check alone loses that race (#11).
- **`open_or_attach` takes the write lock first.** It begins an immediate transaction, so concurrent callers serialize on the lock and the second sees the first's incident and attaches. The unique index, with one re-select and attach on conflict, is only the backstop. Reason: callers wait instead of failing (#11).
- **A host that is unreachable absorbs its services' signals.** A service signal attaches to the host's open incident when that incident has a `host_unreachable` signal. Reason: when the host is down every service on it looks down, and one incident per service would page about one cause many times (#11).
- **A finished incident absorbs nothing.** Resolved, closed and failed incidents leave the index, so the next signal opens a fresh incident. Reason: a recurrence after a fix is a new story with its own diagnosis and report (#11).
- **Ids are `inc_` plus a ULID-like string.** Ten characters of millisecond time then eight random ones, from the injected clock. Reason: ids sort by creation without a new dependency (#11).
- **The bus persists before it fans out.** `publish` writes the event with `seq = max + 1` for its incident inside one immediate transaction, then pushes it to subscribers. Reason: a crash or a dropped subscriber never loses an event, and `seq` has no gaps or duplicates (#11).
- **Persist and fan-out run under one lock.** Reason: subscribers always receive events in seq order, never seq 2 before seq 1 (#11).
- **Subscribing is a context manager that registers on enter.** The catch-up pattern is subscribe, fetch `history`, then iterate de-duplicating by seq. Reason: an event published between the history read and the first read of the stream is not lost (#11).
- **Subscriber queues are bounded and drop the oldest.** Each subscriber has a queue of 256; when it is full the oldest event goes and publishing never waits. Reason: one stalled browser tab must not slow the agent, and the client fills the gap from `history(incident_id, after_seq)` (#11).
- **`subscribe(None)` receives every incident.** Reason: the overview page shows all incidents live (#11).
- **Subscribers unregister on exit or cancel.** Reason: a closed SSE connection must not leave a queue filling forever (#11).
- **Clocks are injected, timestamps are UTC.** Stored as ISO strings. Reason: tests control time and ordering without sleeping (#11).
- **The app shares one `ApprovalStore` and one `GuardLog`.** `build_parts` passes them to the graph, the runner, the API and the reminder loop; the lifespan starts the reminders with the watcher, stops them first, and flushes the guard log after the runs and the watcher stop. Reason: a decision recorded by the API or Telegram must be the one the run and the boot recovery read, and a guard record made while shutting down must not be lost (#21).
- **A notice is stored in English with the template it was made from** (#427). The runner, the watchdog, "This is expected", the watcher, the graph's nodes and the bot publish a notice (and an `expected` event) through `graph.shown.shown_payload`: `{"text": <English>, "shown": <the Shown>}`, where the English is the same words as before #427 and what the report's facts and the chat's snapshot read. `IncidentRunner.end` and `Notifier.notice` take a `schemas.shown.Shown`, so the channels say it in the person's language; `Expectations.expected` answers with one (`Answer.said`), rendered by whichever channel asked. Reason: the person reads the language they picked while every model keeps reading English ([notify](notify.md), [app](app.md)).

## Statuses

An incident's status says what Bleep is doing, in this order for a fix that is approved: `open` (just opened) → `investigating` (Gather, Investigate, Diagnose, Propose) → `awaiting_approval` (stopped at the interrupt) → `executing` (a yes was delivered; Execute runs) → `verifying` (Verify runs) → `resolved` or `closed`. `paused` replaces any of the working statuses while the model is unavailable, and the run goes back to `investigating` (or `executing`, `verifying`) when it is tried again. `failed` is the end of a run that raised an error that is not the model being unavailable. `waiting` is a host-unreachable incident that runs no graph while its host does not answer and closes when it answers again ([watcher](watcher.md#bleeps-own-sleep-hosts-that-may-sleep-and-recovery-85), #85).

- **The graph sets the status for the node it is about to run, before it publishes `node_started`.** `graph/build.py` maps gather, investigate, diagnose and propose to `investigating`, execute to `executing` and verify to `verifying`; approval and report set nothing. Reason: the dashboard reads the incident again on every event, so the status must already be written when `node_started` reaches it; the runner could only react to the event afterwards, and the graph already holds the incident repository in its deps, so this adds no new dependency (#101).
- **The runner sets the status when it starts driving a run.** A yes sets `executing` at once; a new run, a restart from a checkpoint, a no and an instruction set `investigating`, and the next node corrects it. Reason: an approval must never flash back to `investigating`, and a loop back from Execute, Approval or Verify to Propose or Investigate shows as `investigating` again because those nodes set it (#101).
- **`awaiting_approval`, `paused`, `waiting`, `resolved`, `closed` and `failed` are the runner's.** Reason: only the runner knows the run stopped at the interrupt or finished after its last checkpoint (#16, #28).

## Model outages and stuck incidents

- **Every model call has a timeout, 120 s by default (`Budgets.model_timeout_s`, a whole number of seconds, editable in the dev panel like the other budgets).** `llm/guard.py` (`ModelGuard`) wraps each call the graph makes (Investigate, and the structured calls of Diagnose, Propose and Report) in `asyncio.timeout`. Bleep's own wrapper enforces it so a model that never answers is cut off the same way for every provider, and a test can use a fake model that hangs without touching the network. A change applies to the next call (#86).
- **The provider client gets the same timeout plus 5 s, in the unit the client takes.** ChatOpenAI (the local provider) takes seconds; ChatOpenRouter takes milliseconds, so it is given `(timeout + 5) * 1000`. Reason: the guard decides when a call is over, and the client's own timeout is only a backstop for a connection the guard did not reach. A value in the wrong unit would cut every OpenRouter call off after a hundred milliseconds (#86).
- **A timeout, a connection error, a 429, a 408 or a 5xx is retried twice, after 2 s and then 4 s.** The transient transport errors are httpx timeouts, network errors and remote protocol errors, and the SDKs' equivalents. An HTML error page from a proxy (a 502 or 504 the OpenRouter SDK cannot parse as JSON) is told by its status. A configuration error (an unsupported URL scheme, a local protocol error) fails the run. A connection refused by a wrong local URL cannot be told from an outage and is retried like one. The provider clients are built with `max_retries=0` so the guard is the only place retrying happens. A rejected request (4xx), a bad key or a reply that does not validate is never retried: the same call would fail the same way (#86).
- **After the retries the run is paused, not failed.** The guard raises `ModelUnavailable` (it names the error type only, since a provider's message may quote its endpoint or key); the runner sets the incident `paused`, publishes one notice, tells the channels once, and tries the run again from its checkpoint: after `Budgets.paused_retry_min` minutes (5 by default), then 10, 20, 40, and every 60 after that (never less than the first wait, if that is set above 60). A run that has been paused for an hour by the clock (counted from its first pause, so at the first pause after that hour) gets one more notice, on the dashboard and on the channels, and then no more. A retry adds no second `node_started` for the node it runs again, so the timeline does not fill up. The pause counts are kept in memory. `recover_on_boot` picks a paused run up at once. Any other exception still sets `failed`, since it is a bug and retrying would hide it. Reason: a provider outage must not turn an incident into a dead end that a human has to restart, and `failed` has to keep meaning "look at the backend log" (#86).
- **Report writes from the record when the model is unavailable,** as it does for any model failure, so a verified fix still settles `resolved` (#86).
- **A restart or a retry takes its status from the node the run goes on at.** A run resumed before Report after a Verify that passed shows `verifying`, not `investigating`; after a failed Verify it shows `investigating`. Reason: a fix that was verified must never look unfinished (#86).
- **A watchdog notices an incident that stopped moving.** `incidents/watchdog.py` (`Watchdog`, ticking every 60 s like the reminders) looks at each unfinished incident except `awaiting_approval` (it has reminders), `paused` (it has said so already), `waiting` (it waits for its host, which it said when it opened, #85) and any run the runner is retrying after a pause (`runner.retrying`; a retry publishes no event while it waits on the model, and the runner already reports on it). When the newest event that is not a notice is older than `Budgets.stuck_after_min` (30 by default), it publishes one notice and sends it to the channels. A new notice needs the incident to move first, so a stuck stretch gets exactly one and a later stretch gets its own. Reason: a run held by a slow host or a sleeping laptop must not sit unseen for hours, and notices must not repeat every tick (#86).
- **Each incident is checked on its own,** so one that fails to publish does not skip the rest (#86).
- **What the watchdog already noticed is kept in memory.** Reason: a restart notices a still-stuck incident once more, which is cheaper than a column and harmless (#86).

## Quiet services and hosts (#220)

- **Quiet states are rows in `quiet` (scope, target id, mode, until, since), one per target.** `QuietStore` in `incidents/quiet.py` sets, clears, lists the active ones and tells its listeners (the watcher) when a quiet started or ended; a snooze whose time has passed is not active even before the loop deletes it. Reason: it is state a person sets, not a secret, and it must survive a restart (#220).
- **A host removed on the dashboard takes its quiet states with it** (`QuietStore.forget_host`: the host's row and every service row under `{host_id}/`), without telling the listeners. Reason: a host added again under the same id must not come back silently left alone, and a host that is gone is not judged again (#220).
- **The graph stops a run once its service or host is quiet, before Gather, Investigate, Diagnose, Propose or Approval start** (`QUIET_STOPS` in `graph/build.py`; the node raises `IncidentQuiet`). The incident is closed with the quiet notice, once; a failed check after the quiet started closes the incident instead of proposing again while loop-backs remain, and once they are spent Verify routes to Report as usual and the incident ends `failed` with its report, because an approved plan acted on the host and reports say what happened. A passing check still resolves it as fixed. Reason: a new plan and a new approval request is exactly what quiet rules out (#220).
- **A quiet that starts after a yes but before the plan's first step stops the run at Approval, since no step has run.** A plan already executing or verifying finishes its step and its check. Reason: nothing was changed on the host yet, so stopping is safe, while a half-run plan is not (#220).
- **The notice says "Closed: you told me to leave {name} alone." or "Closed: you snoozed {name}; I look at it again when the snooze ends."** The server text has no time. Reason: the server does not know the browser's time zone, so "until 18:00" is shown by the dashboard pill instead (#220). Telegram's end message for a snooze leads with "🤫 Quiet until 18:00", in Bleep's time zone, or "17:00 UTC" when none is set ([notify](notify.md), #389, #400). A snooze's `until` is stored in UTC whatever offset the request gave it (#400).
- **API: `PUT` and `DELETE /api/quiet/services/{service_id:path}` and `/api/quiet/hosts/{host_id}`.** A snooze needs a zone-aware `until` in the future and at most 7 days ahead, leave alone takes none (422 naming `until` or `mode`); an unknown service or host is 404; a delete is 204 also when nothing was set. Reason: the browser sends an absolute time and the server judges "quiet now" against its own clock (#220).

## A look on request (#403)

`incidents/looks.py` (`Looks.look(service_id, via)`). The person asks in the chat ("look at shop-web again"), confirms with one tap, and Bleep opens an incident for the service ([notify](notify.md#talking-to-bleep-390) for the offer and the thread).

- **Only the tap opens it, through the watcher's path.** One `look_requested` signal (detail `via`, the channel that asked) goes through `IncidentRepo.open_or_attach`, then `IncidentRunner.start`: the one open incident per subject holds, and the run gathers, investigates, diagnoses and proposes as for any incident, so a plan still waits for a yes. Its title is "look requested on <service>" and its short name the service's next number. No container is named, so the run reads every container of the service and a plan may act on any of them but not stop one, as for an incident opened by a URL check alone ([guard](guard.md)). Reason: one way to open and run an incident, and every change on a host still goes through an approved plan (#403).
- **It opens nothing, and says why, for a service that has an open incident** (its own, or its host's waiting `host_unreachable` one that takes its signals: `IncidentRepo.open_target`, named by short name), **that is quiet** (itself or through its host), **that Bleep does not know** (removed since the offer, or Bleep's own: `bleep.self` containers are in no service, and a service holding one is refused anyway), **whose host does not answer**, or **when the day's cost cap is spent** (`daily_cost_usd`, the one incident runs count against; the chat's own cap is apart). All of it is checked at the tap, whatever the offer saw: an offer lives 10 minutes. Reason: a look must never add a second run to a service already being looked at, nor start one Bleep has been told to leave alone or cannot pay for (#403).
- **A look never attaches to an open incident** (`open_or_attach(…, attach=False)`): an incident the watcher opened in the moment before the look's write is named, and its signals stay what the watcher saw. Reason: the press must say what it did, and a look signal on another incident would change neither its run nor its plan, only its report (#403).
- **A look is never a repeat, and a bare look never holds one back.** It joins no fold group, so its opener always reaches the chat, and a look may open during a hold. A bare look, one that took no watcher signal while it was open (its fold key is its subject's, `look_requested` and no target, and every signal on it is the look), is left out of `IncidentRepo.finished_since`, so the watcher's repeat holds neither count it nor wait for it ([watcher](watcher.md#a-failure-that-outlives-its-incident-356)), and of `IncidentRepo.previous`, so the next incident's "Again" names the incident before it. A look that took a failure while open (the watcher's signals attach to it as to any open incident) counts like any incident that took it: the failure waits out its hold after the look. Reason: the hold keeps Bleep from running again on a failure it could not fix by itself, and what the watcher holds back must not depend on whether someone asked; review of #403 found the first version let a failure that attached to a look skip its hold.
- **Only a service.** A host is answered "I look at a service on request, not a whole host". Reason: a host incident's run and its check read the host's readings (disk, memory, load, reachability), and a look gives none to check against; a service has containers and URLs to read and verify (#403).
- **A bare look tells the graph that nothing was seen failing** (`graph/look.py`, #410). When every signal of the run is the look, Investigate, Diagnose and Report each get a rule of their own (`prompts/graph/look_*.md`): the look's `via` names where the person asked, not a part of the service; a run that finds nothing wrong says so, rates how sure it is that the service is healthy, and its report calls it no issue. Any other run's prompts stay byte for byte as they were. Measured on the demo shop while it was healthy (`look-healthy`, [report](../evals/look-on-request-2026-11-10.md)): before the rule, 3 of 3 runs proposed no action but read `via: dashboard` as a dashboard failure nobody could reproduce (confidence 0.35 to 0.43, reports "the issue remains unconfirmed" with follow-ups to reproduce it); with it, 3 of 3 diagnosed "nothing is wrong" at 0.96 to 0.98, proposed no action, and reported the service healthy with no follow-ups. Reason: a look on a healthy service must end without a plan and say nothing is wrong (#410).
- **Limits.** The look eval covers a healthy service only; a look at a service that is quietly failing (one the watcher has not flagged) is not measured. A look started while the host is reachable but its engine hangs fails its reads as any run does (#403).

## A service healthy again on its own while its plan waits (#571)

- **An incident that waits for a yes closes as recovered on its own once its service has been healthy for five minutes and Verify's checks pass.** `watcher/recovery.py` (`RecoveryWatch`) gets each judgement the watcher makes of a host's services, after every poll tick and every round of URL checks: a service counts as healthy when `service_health` is `ok` and every one of its URLs passed its last check (a stale or missing result is not a pass). The first healthy judgement of an incident's service starts a hold and takes Verify's first reads (`verify.check_recovery`); five minutes later the same checks run again against those reads: every container of the service and every container the incident's signals name running and healthy (or with no healthcheck) and not started again since, every URL of the service and every URL the signals saw fail passing the hosts file's check. Only then `IncidentRunner.healthy_again` closes it, with one notice ("Closed: shop is healthy again on its own; nothing was changed. The plan that waited for a yes was not run.") and one Telegram message in its thread (✅ Back on its own after 1 h). The check publishes no `verification` event and the outcome is never `resolved`: nothing ran, so nothing is called fixed. Reason: on 2026-11-13 shop #10 kept asking for a yes, with a reminder an hour later, for a fault that was gone (#571).
- **It covers `awaiting_approval` only, on a service.** A run in flight (`open`, `investigating`) reads the service as it is and ends with its own report, so it is not cut off; `paused` goes on from its checkpoint with its own retry; `executing` and `verifying` are never touched; `waiting` closes on its host's return (`host_back`). A host incident's readings (disk, memory, load) have their own thresholds and are left to the person. The hold starts only while the incident waits for a yes. Reason: closing a run mid-node is riskier than letting it finish, and "nothing was changed" can only be said of a run parked at its question (#571).
- **Five minutes, and any doubt starts the hold again.** A judgement that is not healthy, a new signal on the incident (a death between two ticks that both saw it running), Bleep's own wake, a host that may sleep and does not answer, a host out of contact, and Verify's checks failing at the end each end the hold, and the next healthy judgement starts a new one with its own first reads. The holds live in memory, so a restart of Bleep starts them again. Five minutes is twenty poll ticks and ten URL rounds, as long as a host must be out of contact to open an incident (`host_unreachable_s`); it is a constant (`watcher/recovery.HOLD`), not a setting. Reason: a flap must not close a real problem, and an hour of reminders is worse than five minutes of waiting (#571).
- **A plan that would have acted closes unrun, as a plan of no action does.** Its approval is closed with the incident (migration 0026), so no grant can be issued and a late Approve, on Telegram or the dashboard, is answered "closed before anyone answered"; the buttons go (`on_finished`, #291) and no reminder comes. If the problem comes back, it opens a new incident: closing it this way is a pass for its containers' loops in the detector, as a verified fix is (`WatcherManager._loops_over`), so a relapse is not held back by the repeat hold ([watcher](watcher.md#a-failure-that-outlives-its-incident-356)). Reason: running a fix on a service that is healthy changes a working system for nothing, and the safe direction is to change nothing (#571).
- **Exactly one outcome when a yes races the close.** `IncidentRepo.close_unanswered` closes in one statement only while the incident is `awaiting_approval`, its approval is still `pending` and no step of any plan of it is in the action log. A yes that won first (its resume not driven yet, the status still `awaiting_approval`) keeps the incident open and its plan runs; a yes after the close finds the approval closed. Poll tick and URL round judge one at a time per host, and a second close finds nothing to close, so there is one notice and one message. An incident back at Approval after an earlier plan of it ran (Verify's loop-back) is never closed this way, since something was changed. Reason: a person told "approved" must see the plan run, and "nothing was changed" must be true (#571).

## Action log

`incidents/action_log.py` (`ActionLog`), table `action_log` (migrations 0009 and 0012). Execute's ledger, so a crash or restart mid-Execute never runs a step twice ([graph](graph.md#crash-safe-resume)).

- **One row per step, keyed by incident, plan key and 0-based step index.** The plan key is `<plan hash>:<approval id>`. Reason: a loop back to Propose makes a new plan with its own hash, so its steps get rows of their own and the old plan's rows stay as history (#24), and the same plan approved a second time (after Verify's loop-back) has the same hash and must run again ([graph](graph.md#execute), #25). The column was `plan_hash` until migration 0012 renamed it to `plan_key` for what it holds; existing rows keep their values (#87).
- **`started` is written before the engine call, `done` or `failed` after it; a step after a failed one is `skipped`.** `start` returns the time it wrote, or None when the step already has a row, so a step can never be started twice: not when it finished, and not when it is still `started`, since it may have reached the engine before a crash (#87). `finish` changes only a `started` row and keeps the start time written before the call. `skip` never overwrites an existing row, because a started step may already have reached the engine. Reason: a resumed run must tell "never ran" from "may have run" from "ran", and each write is one statement whose result says whether it took (#24).
- **`steps(incident_id)` reads the rows back as `LoggedStep(plan_key, host_id, status, result: StepResult)`, in the order they were first written.** Only Execute reads it, to decide what to skip, re-check or confirm. The dashboard reads the `action` events and the report reads `step_results`, both in the act tools' `StepResult` shape. Reason: the ledger exists for crash safety; the bus history already holds every step in order (#24, #87).
- **The rows reference `incidents (id)`.** Reason: an action is always part of an incident, unlike the guard log, which also records for self-recoveries (#24).

## Limits

- **A run resumed from a checkpoint runs its last node again from the start.** After a pause, Investigate's partial round re-runs its read tools and Propose records its violations again. Reads are repeatable and the write path is gated by the action log, so nothing is done twice, but the work and the guard records of that node are duplicated (#86).
- **What closes on its own when it is healthy again is narrow (#571).** A host incident, a paused run and one back at Approval after an earlier plan ran keep waiting for a person even when all is well again, and so does a service with nothing to check (no container and no URL Bleep knows). A restart of Bleep starts every hold again, so a backend that restarts more often than every five minutes never closes one.
